# 原子产品 Release 与双宿主分发

状态：accepted

## 问题

NekroNXT 把 UI、Host、DSH Runtime、Extension Runtime、Core SQLite、DSH Session 和用户本地资源完整部署到用户设备，不存在由平台方先行升级并持续保持最新的中心后端。若 Desktop 独立投放 Web UI，或允许 UI、Host、DSH 和 migration 使用不同版本，旧实例会出现客户端契约不匹配、插件 Client/Host Bridge 分裂和旧二进制读取新数据等不可恢复组合。

Desktop 与 Server 又必须复用同一 Runtime、数据格式和 Web UI，不能各自形成一套发布与迁移实现。

## 决定

NekroNXT 的最小发布单位是原子的 Product Release。每个 Release 同时包含：

- Web UI 生产构建；
- Server Host 与领域 API；
- 锁定版本的 DSH Host/Client 组合；
- Extension Host/Client Bridge、SDK 与 Builder；
- 当前格式所有者的 migration 与升级前检查。

Product Release 使用单一 `releaseId = <产品版本>+<commit 前 12 位>`。Desktop 只启动当前安装包内的 Server 生产入口，并只加载该 Host 同包托管的 Web dist；Host readiness 必须返回相同 `releaseId`。Server 镜像同样把 Server、Web dist 和完整生产依赖构建为一个镜像，不从运行容器执行 `git pull`。

不提供 UI、Host、DSH 或 Extension Runtime 的独立产品更新，也不建立远程 UI 资源投放通道。用户保存的 Extension Revision、Activation、Asset、Credential 和工作区是数据，不并入程序 Release；构建缓存可以按版本失效重建。

## Desktop

Electron 拥有窗口、单实例、外部链接、系统通知、实例 Profile、安全凭据和本地 Host 进程生命周期。自带 Host 在隔离 utility process 中运行；每次 Desktop 运行只分配一个随机 loopback 端口，异常退出后的替代进程继续使用同一 Origin，并受有界退避和滚动崩溃预算约束。Renderer 保持 `contextIsolation: true`、`nodeIntegration: false` 和 `sandbox: true`。BrowserWindow 使用可替换 Product View 加载本地或远程实例自己的同包 Web UI；实例切换与设备信任边界见 [Desktop 多实例与设备鉴权](../implemented/2026-08-23-Desktop多实例与设备鉴权.md)。management descriptor 是 Product Release 之间唯一窄协商层：Server 的 loopback HTTP 与固定 SPKI HTTPS 始终发布 protocol 1，以继续兼容只接受 protocol 1 的既有 Desktop；显式未加密远程 HTTP 才发布 protocol 2，并由不支持它的旧 Desktop 安全拒绝。新 Desktop 对 wire 新增字段保持前向可解析，但不会把未知协议或 transport 当作可执行能力。Desktop 退出会取消恢复任务，并等待 Host 子进程静止。

当前未获得平台开发者证书，因此只产出未受平台开发者身份担保的完整安装包并采用手动完整包更新：Windows x64 NSIS、macOS arm64 与 x64 两个独立 DMG、Linux x64 AppImage。macOS 应用包仍执行完整 ad-hoc 签署，并在生成后重新挂载 DMG 做严格签名校验；这避免残留的 Electron linker signature 被 Gatekeeper 判为应用损坏，但不代替 Developer ID 签名与 Apple 公证。macOS 不再产出 Universal 包；arm64 包面向 Apple Silicon，x64 包面向 Intel，两个 DMG 各自生成独立 receipt（`platform=mac`、`arch=arm64/x64`）供 CI 内部校验，server-runtime 的双架构 N-API prebuild 按 `process.arch` 选择且不参与架构合并。未来平台签名只改变分发可信度和完整包替换方式，不改变 Product Release 原子边界。

Desktop 只有 `preview` 和 `stable` 两个发行通道，不设置 beta。两者使用独立 appId、Windows NSIS GUID、展示名、可执行文件名和 Electron `userData/data/`，可以同时安装且默认不共享数据库：

- stable：appId `ai.nekro.nxt`，GUID `2BED256D-E4EA-4EA9-B730-6B63FF416CE8`，展示名 `NekroNXT`，既有数据目录和可执行标识 `NekroNxt`；
- preview：appId `ai.nekro.nxt.preview`，GUID `D4FFCCE1-474A-47FC-819B-DA8E5BF5378C`，展示名 `NekroNXT Preview`，既有数据目录 `NekroNxt Preview` 与可执行标识 `NekroNxtPreview`。

品牌大小写调整只改变用户展示名，不迁移 appId、GUID、数据目录、可执行文件、包名、协议或 Release 工件 slug。

仓库根 `package.json#version` 是唯一手工版本源，必须是无预发布后缀的 `X.Y.Z`。Web 与 Server 构建从根清单注入该值，Desktop 的运行清单和安装包版本由 Product Release 脚本写入；`apps/*` 与 `packages/*` 中私有 workspace 包的版本只描述内部包，不参与产品版本，也不随产品版本同步修改。stable Release 直接使用 `X.Y.Z`；preview Release 按 Git commit 秒级时间与 commit 前 12 位确定性派生为 `X.Y.Z-YYYYMMDD-HHmmssutc.g<短哈希>`，例如 `0.0.0-20260825-131100utc.g0123456789ab`，使不同 commit 的版本与附件名必然不同。Preview 已由产品名和产物前缀表达，版本号不重复加入 `preview`。公开 stable 制品的 `vX.Y.Z` Git tag 必须指向 receipt 记录的 commit。每个平台制品生成包含 channel、版本、commit、正整数 bytes 和 SHA-256 的 receipt；本地构建命令只生成文件，不隐式上传。最终发布 job 上传前重新计算安装包的 bytes 与 SHA-256，并核对 GitHub 安装包附件的 size，GitHub API 提供 digest 时还核对 `sha256:<receipt.sha256>`。

相关 main 提交通过质量检查后自动构建 Preview。产品差异从“最近成功 Preview → 当前提交”比较，纯文档和测试改动不触发，但不会跳过此前尚未发布的产品变化；未知路径按有产品影响处理。手动 workflow_dispatch 可为当前 main 强制构建完整候选。Node 22 在质量任务执行覆盖率与全部 Node 测试，Node 24 只执行一次兼容测试；组件浏览器场景和生产旅程分开运行。

平台 job 将完整安装包及 receipt 保存为 Actions Artifact，Server 候选镜像使用精确 commit 标签并记录不可变摘要；失败不修改当前成功 Preview。所有平台成功后，串行最终任务先核对四个安装包的本地摘要和 receipt，再上传并核对 GitHub 附件；发布前再次确认目标仍是 main HEAD。Server 按不可变摘要提升，Preview 正文记录成功 commit 和镜像摘要，随后清理旧附件。发布中途失败尝试恢复旧 Tag、正文和 Server 镜像并清理候选，恢复失败明确报错。只读质量任务可被新提交取消，最终发布任务不自动取消。重复执行已经成功的同 commit 保留现有完整产物。preview 是唯一允许移动的发布 tag；正式版本 tag 永久不可移动。

正式版更新内容来自 `docs/releases/current.md`，并在发布前由用户审查。`pnpm release <X.Y.Z>` 显式核对参数、根版本、`main`、远端 HEAD、已经完成的 Preview、目标 Tag 与 Release；交互确认后只推送不可移动的正式 Tag。Tag 触发正式工作流，三个原生 runner 从同一 Product Release 生成四个客户端安装包，Server job 生成提交绑定的候选镜像。最终 job 验证内部 receipt 和文件摘要，使用已审查的可变内容与自动生成的版本、下载、镜像、DSH、Release ID、Commit、许可证和文档入口构造正文，再发布版本镜像、Latest Release 与 `latest` 镜像。正式 Release 不公开内部 receipt。

版本修订遵循 SemVer：兼容性修复递增 patch；新增用户能力或向前迁移递增 minor；公开契约、部署边界或数据恢复语义发生有意破坏时递增 major。发布下一个正式版本前先修改根版本，再从该版本构建任意数量 preview，最后从选定 commit 构建 stable；不得通过修改 Desktop 子包版本制造第二版本源。

## Server

Server 使用 glibc 系 Node 运行镜像、非 root 用户、单一 `/data` 和同包 Web dist。容器启动同一个生产 Server 入口并显式监听 `0.0.0.0`；外部入口自动生成 TLS 并要求设备鉴权，内部 DSH WebServer 只监听随机 loopback。Runtime 完整恢复后发布匿名 liveness 与 readiness。当前 Server 的 loopback 与 TLS descriptor 均保持 `managementProtocol = 1`；它不因新 Desktop 支持 protocol 2 而抬高兼容 transport 的协议号。镜像构建拒绝脏工作树，版本与 Desktop Product Release 使用同一产品版本和 commit 身份。安全入口见 [Desktop 多实例与设备鉴权](../implemented/2026-08-23-Desktop多实例与设备鉴权.md)。

### 候选镜像验收

Server 候选镜像的交付验收要求在隔离容器内完成：核对 `/health/ready` 的预期 Release ID，经 Host API 写入并重新读取临时凭据，安装并启用合成 DSH 插件，重启验证 Loader 恢复，最后关闭并移除插件。文件清单、镜像大小、摘要或一次 health 不能单独证明交付制品具备完整生命周期。Desktop 最终打包目录的对应验收由 [Desktop README](../../../apps/desktop/README.md) 说明。

这项 Server 要求尚未完整落地：[Preview CI](../../../.github/workflows/ci.yml) 检查 readiness 成功和插件安装、重启恢复、关闭移除，但未断言 readiness 的 Release ID 值，也未执行独立的凭据写入重读；[正式发布工作流](../../../.github/workflows/release.yml) 从已验证的 Preview 提交构建新镜像，没有对新候选重跑完整闭环。当前工作流不能作为上述完整镜像验收已经实现的证据。

## 升级与恢复

Product Release 标识程序包，DSH 兼容性清单分别标识 Session、设置与扩展运行接口；二者不能混用。版本矩阵由 [dsh-compat](../../../packages/dsh-compat/README.md) 拥有，具体步骤见 [DSH 升级维护指南](../../dsh-upgrade.md)。

宿主在打开存储所有者前持有数据根锁，创建并校验完整恢复点，再执行迁移与 Runtime 恢复。Core、DSH Session、Host Profile、Client 和 Extension 各自拥有格式与验证；宿主协调顺序、journal、进度、失败恢复和就绪。通用 checkpoint 不能代替各所有者的事务凭据，也不能跳过本次进程的服务装配。

当前 Session 路径是已识别的 SQLite schema 15/17 → 整体归档 → JSONL V4。Core 同事务关闭旧 Episode、取消未完成 Admission、中断创造任务、登记绑定的入站截止边界与迁移凭据；保留聊天、附件、Revision、Binding 和扩展记录，旧积压不补答。迁移 ID 绑定旧数据身份，后续产品修复版不能重复清空新会话；未知格式仍拒绝。正常关闭的 inbox 短期 journal 随完整备份保留，只用于同一 Session 重启恢复，不突破升级重置边界。

可选模型配置与扩展不兼容时逐对象隔离并保留安装/启用意图；诊断绑定实际版本、配置修订和环境指纹。重试调用实际恢复路径，不静默更换模型或改写旧验证证据。必需服务与资源静止失败仍阻止启动。

Desktop 启动页消费带本次 run ID、PID 和 Release 的可信进度，支持安全取消、失败重试、诊断和离线恢复；有有效升级心跳时不受普通启动期限限制。它最终仍以同包 HTTP `/health/ready` 开放产品页面，不能仅凭 journal/进度 ready。远程 Profile 始终加载该远程 Server 自己的同包 Web，不与 Desktop 本地 Release 比较。

Web 构建注入所属 Server 的 `NEKRO_RELEASE_ID`，当前页面通过同源版本检查拒绝旧页面写入并保留输入，提示用户刷新；频道草稿支持同标签页恢复，其他表单不承诺自动迁移。发布链必须验证 Web、API 与 readiness 身份一致，不能用缺少构建身份时的首次快照基线代替制品身份验证。

当前已有完整数据恢复点与 `--restore-upgrade <backupId>` 维护入口。恢复先保留失败现场，校验并还原 manifest 中的根目录；成功后退出新程序，要求使用匹配的旧完整包。代码 downgrade 不受支持，不能让旧程序直接读取新数据，也不在升级失败后擅自自动回退。

恢复点暂未完整记录源程序身份，外置工作区续跑依赖当前 Core 推导，Admission 与最终 HTTP 就绪仍有先后窗口。限制与验收要求集中在 [DSH 升级维护指南](../../dsh-upgrade.md#5-验收要求与实现限制)。这些实现不等于候选容器、Desktop 所有平台产物和升级真实旅程已验证。平台签名、整包自动替换、跨设备同步和社区插件分发不由本次升级扩展实现。

## 影响

- `apps/desktop` 是 Product Release 的 Desktop 宿主，也是多个独立 NekroNXT 服务实例的本地管理客户端；
- `apps/server` 同时提供可由 `node` 启动的生产入口和 Desktop 可启动的无副作用入口；
- Web 只面向同包 Host 契约构建；Desktop 通过窄 management/chrome protocol 门禁选择是否加载远程实例，不维护任意历史业务 API 的在线兼容层；
- Desktop 与 Server 对同一旧数据 fixture 必须得到相同升级结果；
- 产品 Release 签名与未来社区 Extension 供应链是不同问题，本决定不提前建设社区签名或市场。

## 未来方向检查

关联方向：Desktop/Server 双宿主、多设备同步、社区扩展、远程管理与长期升级。

保留接缝：单一 Product Release 身份、稳定数据根、格式所有者 migration、不可变 Extension Revision、Host ready 门禁和完整包替换。

避免的锁死：不把 Desktop 做成中心平台薄客户端；不允许 UI/Host 混搭；不把 Electron IPC 变成第二套领域 API；不让程序 Release 覆盖用户扩展与数据。
