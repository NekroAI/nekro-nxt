# 扩展形态统一

状态：accepted（2026-10-09 用户批准；分期实施，未落地部分见 §9）

本决定取消扩展的 `agent` / `host-adapter` / `host-ui` 三选一形态，把一个扩展统一为「一个本机实例 + 可选的智能体挂载」，用 Manifest V7 承载。它替换[客户端体验重构与扩展界面统一](2026-10-04-客户端体验重构与扩展界面统一.md)中「每种 scope 的贡献组合」与[扩展宿主能力与生态移植](2026-10-07-扩展宿主能力与生态移植.md)§2.1「Manifest 保持 V6、只做加法」的约定；其余领域不变量不变：用户可见发言只来自通信工具，新消息可靠入库，扩展通过不可变 Revision 演进，动态运行、保存、安装、给智能体启用是独立动作。

## 1. 理由

`scope` 一个字段同时决定了绑定对象（本机、智能体、连接）、运行位置（宿主单例、会话插件、浏览器）和授权时机（安装时、启用时），所以一个扩展只能选一种形态。后果是：

- 「智能体工具 + 管理页面」这类最常见的组合必须拆成多个扩展，分别安装、分享、升级，彼此没有数据通道；
- 智能体扩展的界面数据接口拿不到频道上下文，页面扩展的服务端不能联网、存储或使用凭据；
- Webhook、命令、出站观察、导航入口这类本机级能力没有自然的归属；
- 社区按形态分类，一个功能被拆成多个条目。

社区刚上线、尚未宣传分发，没有第三方扩展，存量只有 10 个官方智能体扩展与开发机上的个别扩展。现在一次性改造，不做长期兼容。

## 2. 用户已确认的取舍

| # | 决定 |
| --- | --- |
| K1 | 采用「本机实例 + 智能体挂载」两层模型，取代 `scope`；不做「套件」，也不做全局扁平 |
| K2 | 每台机器上一个扩展只有一个当前版本；智能体层只保留启用与否和自己的配置；灰度改用候选版本试运行 |
| K3 | 直接切到 Manifest V7，不再读取 V6，不保留兼容执行模式 |
| K4 | 本机层开放联网、凭据、存储、渲染解析、定时任务、Webhook、命令；模型调用首批不开放（2026-10-11 起由[表情包与扩展素材能力](2026-10-11-表情包与扩展素材能力.md) S10 开放本机层模型调用） |
| K5 | 命令可以由扩展直接回复：作为「扩展回复」独立事实，界面标注来源，只能回复触发命令的那条消息 |
| K6 | Desktop 的 Webhook 首版只提供本机或局域网地址，并提示用户自行配置穿透；社区中转暂不做 |
| K7 | 页面贡献可声明 `rail` 注册导航轨入口，每个扩展最多 1 个，位于主空间下方，用户可在设置中隐藏，可由扩展更新数字徽标；不提供用户钉选 |
| K8 | 新界面 Slot 先做消息操作菜单与输入框动作（产出管理员消息），再做概览卡片；不做设置分区 |
| K9 | 出站事件观察只读：发送提交后通知，含平台消息 ID 与投递结果；不能拦截或改写 |
| K10 | DSH 插件可在 `nekroNxt` 元数据中声明能力后注入 `nxt`，审批与 NXT 扩展一致 |
| K11 | 社区按「提供什么」打标签（智能体能力、页面、平台适配、MCP）；社区接口直接改造，不兼容旧版客户端 |
| K12 | 进程隔离只针对社区来源与用户导入的扩展，放在最后一期 |

## 3. 模型

一个扩展在一台机器上有一份**安装**（本机实例），以及零到多份**智能体挂载**：

- **本机实例**：安装时创建，整台机器只有一个。Host 入口的 factory 只在这里执行一次。它拥有界面数据接口（RPC）、适配器、页面、富消息渲染器、扩展与连接锚点的面板，以及后续的命令、Webhook、出站观察和本机定时任务。本机层能力与浏览器侧权限在安装时批准。
- **智能体挂载**：给某个智能体启用时创建。factory 返回的插件按该智能体的每个 DSH Session 挂载，提供工具、提示词贡献，并承载入站钩子与定时任务处理对该智能体的调用。智能体层能力在启用时批准，配置按智能体保存。

只有智能体层的扩展，安装步骤在首次给智能体启用时自动完成；只有本机层的扩展没有挂载。两层在同一进程内直接调用，不经存储或 RPC 绕行。

## 4. Manifest V7

`schemaVersion: 7`，去掉 `scope`。每个贡献的归属由种类决定：

| 贡献 | 归属 |
| --- | --- |
| `tool`、`tool-view`、`panel`（`agent` / `channel` 锚点） | 智能体挂载 |
| `rpc`、`adapter`（最多 1 个）、`host-page`（最多 8 个）、`message-renderer`、`panel`（`extension` / `connection` 锚点） | 本机实例 |

频道锚点的面板出现在响应智能体启用了本扩展的频道，以及本扩展适配器所属连接的频道。

```jsonc
{
  "schemaVersion": 7,
  "extensionId": "ext_…",
  "revisionId": "rev_…",
  "entrypoints": { "host": "source/host.ts", "client": "source/client.ts" },
  "contributions": [ /* 上表中的贡献 */ ],
  "permissions": {
    "permissions": ["agents.read"],            // 浏览器侧：页面与面板经 host.call 的产品读写
    "networkOrigins": [],
    "host":  { "network": { "mode": "domains", "domains": ["api.example.com"] }, "storage": {} },
    "agent": { "history": { "read": true } }   // 原 permissions.capabilities
  },
  "config": { "host": { "schema": {} }, "agent": { "schema": {} } }
}
```

- `permissions.permissions`、`networkOrigins` 与 `permissions.host` 组成本机授权，`permissions.agent` 组成智能体授权；两者各有权限摘要，各自绑定精确 Artifact 摘要。能力扩大的判定按层进行，只重新批准扩大的那一层。
- `config.host` 与 `config.agent` 各是一份序列化 Schemastery；两份 Schema 的字段名不得重复。凭据字段（`meta.role: 'secret'`）两层都可声明，`ctx.nxt.secrets.get(key)` 按声明它的那一层取值。
- 声明了智能体层贡献或 `permissions.agent` 的扩展才有智能体挂载；`permissions.agent` 中的 MCP、入站钩子等沿用 2026-10-07 决定的语义。
- `.nxt-extension` 传输格式升级为 v2：扩展身份不再带 `scope`，改为由 Manifest 推导的 `provides` 标签。

## 5. SDK

```ts
export default defineHostExtension(({ harness, nxt }) => {
  // 本机实例：整台机器只执行一次
  harness.handle('items.list', async (input, caller) => nxt.storage.list({}))  // caller 说明调用位置
  harness.onInbound?.(async (message, agentNxt) => ({ trigger: 'default' }))     // 对每个启用的智能体调用
  return {
    inject: ['tools', 'nxt'],
    apply(ctx) {
      // 智能体挂载：每个启用的智能体的每个 Session
      const config = ctx.config()   // 该智能体的配置
      harness.registerTool(ctx, harness.defineTool({ /* … */ }))
    },
  }
})
```

- `harness.config()` 返回本机配置；智能体配置在挂载内用 `ctx.config()` 读取，`onInbound` / `onJob` 处理函数的 `nxt.config()` 同样返回该智能体的配置。
- factory 参数中的 `nxt` 是本机层服务：`http`、`secrets`、`storage`（本机分区，即原 `shared`）、`render`、`parse`，按 `permissions.host` 检查。
- RPC 处理函数的第二个参数 `caller` 说明调用来自页面、哪个锚点的面板，以及可得到的智能体、频道、连接；面板调用由宿主核对锚点，扩展不需要自己校验。
- 适配器注册、入站钩子、定时任务处理只能在 factory 阶段注册，与现在相同。
- `EXTENSION_SDK_LEVEL` 提升，创造智能体使用的编写参考与 SDK 同步更新。

## 6. 生命周期与数据

1. 保存或导入得到不可变 Revision，与现在相同。
2. **安装**：批准本机授权，填写本机配置；执行 factory，注册适配器与页面目录。
3. **给智能体启用**：批准智能体授权，填写该智能体的配置；在安全间隙挂载。
4. **切换版本**：本机实例与全部挂载在各自的安全间隙停止，用新版本重新加载并挂载，全部成功才提交；任一失败整体回滚到原版本。哪一层能力扩大就只重新批准那一层。
5. **停用 / 卸载 / 删除**：停用只撤下该智能体的挂载；卸载先撤下全部挂载再停本机实例；删除清理存储、定时任务与不再引用的凭据。

- 每个扩展都有 `host_extension_installations` 记录；`agent_activations` 的版本列始终等于安装版本，由协调器在切换时同一事务内更新。
- `local_extensions.scope` 改为 `provides`（由 Manifest 推导的标签数组），只用于展示与筛选。
- 本机存储即现有 `shared` 分区；定时任务允许归属本机实例（第四期）。
- 读不出的 V6 Revision 标记为「格式不受支持」：不能安装或启用，工坊提示从社区更新或让智能体重新创造。V6 源码中按智能体执行一次 factory 的语义无法安全地自动转换，因此不做自动迁移。

## 7. 社区与官方扩展

- 社区只接受 V7 包；`packages/inspect` 按本机授权与智能体授权两段输出权限摘要，组合风险规则跨层检查；AI 审查提示说明两层结构；市场按 `provides` 标签筛选；开放接口直接换成新结构。
- NXT 解析社区响应改为容忍未知字段，避免以后新增字段再次破坏旧客户端。
- 10 个官方扩展全部迁移到 V7，与去掉 V6 的 NXT 版本同一窗口发布，并撤回社区上的 V6 发布。

## 8. 分期

1. 契约与格式：Manifest V7、传输格式 v2、SDK、`contracts` 与 `extension-format` 新主版本。
2. 运行时与迁移：统一的安装与挂载协调器、两层授权、导入与动态验证、Host API 与工坊、导航轨 Slot、编写参考。
3. 社区与官方扩展：社区包检查、数据库、接口、审查提示与市场；官方扩展迁移。
4. 事件入口：命令与扩展回复、Webhook、出站事件观察、本机定时任务。
5. 界面 Slot：消息操作菜单、输入框动作、概览卡片、入站钩子管理界面。
6. 加固：社区来源扩展的进程隔离与资源上限。

共享包、社区与官方扩展仓库按「NXT 契约 → 发布共享包 → 社区 → 官方扩展」的顺序推进，去掉 V6 的 NXT 版本与另两处改造同一窗口上线。
