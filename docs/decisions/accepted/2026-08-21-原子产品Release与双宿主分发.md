# 原子产品 Release 与双宿主分发

状态：accepted

## 问题

NekroNXT 把 UI、Host、DSH Runtime、Extension Runtime、双 SQLite 和用户本地资源完整部署到用户设备，不存在由平台方先行升级并持续保持最新的中心后端。若 Desktop 独立投放 Web UI，或允许 UI、Host、DSH 和 migration 使用不同版本，旧实例会出现客户端契约不匹配、插件 Client/Host Bridge 分裂和旧二进制读取新数据等不可恢复组合。

Desktop 与 Server 又必须复用同一 Runtime、数据格式和 Web UI，不能各自形成一套发布与迁移实现。

## 决定

NekroNXT 的最小发布单位是原子的 Product Release。每个 Release 同时包含：

- Web UI 生产构建；
- Server Host 与领域 API；
- 锁定版本的 DSH Host/Client 组合；
- Extension Host/Client Bridge、SDK 与 Builder；
- 当前格式所有者的 migration 与升级前检查。

Product Release 使用单一 `releaseId = <产品版本>+<commit 前 12 位>`。Desktop 只启动当前安装包内的 Server 生产入口，并只加载该 Host 同包托管的 Web dist；Host readiness 必须返回相同 `releaseId`。Server 镜像同样把 Server、Web dist 和完整生产依赖构建为一个镜像，不从运行容器执行 `git pull`。

不提供 UI、Host、DSH 或 Extension Runtime 的独立产品更新，也不建立远程 UI 资源投放通道。用户保存的 Extension Revision、Activation、Asset、Credential 和工作区是数据，不并入程序 Release；构建缓存可以按版本失效重建。

## Desktop

Electron 拥有窗口、单实例、外部链接、系统通知、实例 Profile、安全凭据和本地 Host 进程生命周期。自带 Host 在隔离 utility process 中运行；每次 Desktop 运行只分配一个随机 loopback 端口，异常退出后的替代进程继续使用同一 Origin，并受有界退避和滚动崩溃预算约束。Renderer 保持 `contextIsolation: true`、`nodeIntegration: false` 和 `sandbox: true`。BrowserWindow 使用可替换 Product View 加载本地或远程实例自己的同包 Web UI；实例切换与设备信任边界见 [Desktop 多实例与设备鉴权](../implemented/2026-08-23-Desktop多实例与设备鉴权.md)。management descriptor 是 Product Release 之间唯一窄协商层：Server 的 loopback HTTP 与固定 SPKI HTTPS 始终发布 protocol 1，以继续兼容只接受 protocol 1 的既有 Desktop；显式未加密远程 HTTP 才发布 protocol 2，并由不支持它的旧 Desktop 安全拒绝。新 Desktop 对 wire 新增字段保持前向可解析，但不会把未知协议或 transport 当作可执行能力。Desktop 退出会取消恢复任务，并等待 Host 子进程静止。

当前未获得平台证书，因此只产出未签名完整安装包并采用手动完整包更新：Windows x64 NSIS、macOS arm64 与 x64 两个独立 DMG、Linux x64 AppImage。macOS 不再产出 Universal 包；arm64 包面向 Apple Silicon，x64 包面向 Intel，两个 DMG 各自携带独立 receipt（`platform=mac`、`arch=arm64/x64`），server-runtime 的双架构 N-API prebuild 按 `process.arch` 选择且不参与架构合并。未来平台签名只改变分发可信度和完整包替换方式，不改变 Product Release 原子边界。

Desktop 只有 `preview` 和 `stable` 两个发行通道，不设置 beta。两者使用独立 appId、Windows NSIS GUID、展示名、可执行文件名和 Electron `userData/data/`，可以同时安装且默认不共享数据库：

- stable：appId `ai.nekro.nxt`，GUID `2BED256D-E4EA-4EA9-B730-6B63FF416CE8`，展示名 `NekroNXT`，既有数据目录和可执行标识 `NekroNxt`；
- preview：appId `ai.nekro.nxt.preview`，GUID `D4FFCCE1-474A-47FC-819B-DA8E5BF5378C`，展示名 `NekroNXT Preview`，既有数据目录 `NekroNxt Preview` 与可执行标识 `NekroNxtPreview`。

品牌大小写调整只改变用户展示名，不迁移 appId、GUID、数据目录、可执行文件、包名、协议或 Release 工件 slug。

仓库根 `package.json#version` 是唯一手工版本源，必须是无预发布后缀的 `X.Y.Z`。stable Release 直接使用 `X.Y.Z`；preview Release 按 Git commit 秒级时间与 commit 前 12 位确定性派生为 `X.Y.Z-YYYYMMDD-HHmmssutc.g<短哈希>`，例如 `0.0.0-20260825-131100utc.g0123456789ab`，使不同 commit 的版本与附件名必然不同。Preview 已由产品名和产物前缀表达，版本号不重复加入 `preview`。公开 stable 制品的 `vX.Y.Z` Git tag 必须指向 receipt 记录的 commit。每个平台制品生成包含 channel、版本、commit、正整数 bytes 和 SHA-256 的 receipt；本地构建命令只生成文件，不隐式上传。平台 job 上传前重新计算安装包的 bytes 与 SHA-256；最终发布 job 核对 GitHub 安装包附件的 size，GitHub API 提供 digest 时还核对 `sha256:<receipt.sha256>`。

`main` 的 push 在完整 CI 通过后分别在 macOS、Windows 与 Linux 原生 GitHub runner 构建 Preview。平台 job 把版本化安装包与 receipt 直接上传到固定 `preview` tag 对应的滚动 Prerelease，不把客户端作为 Actions Artifact 分发；macOS job 一次上传 arm64 与 x64 两个 DMG 及各自 receipt。最终发布 job 按 `platform` 与 `arch` 验证 8 项附件（Windows 2 项、Linux 2 项、macOS 4 项）的 receipt 与 Product Release commit 一致，并再次确认候选 commit 仍是远端 `main` 最新 HEAD；满足条件后强制前移可移动的 `preview` tag、更新 Prerelease 身份并删除上一版附件。失败或已被更新 commit 超越的构建只在 `preview` tag 尚未指向候选 commit 时删除自己的候选附件；同 commit workflow 重跑失败时保留已经发布的当前附件。上一版完整 Preview 始终保持可下载。`preview` 是唯一允许移动的发布 tag；正式 `vX.Y.Z` tag 永久不可移动。

版本修订遵循 SemVer：兼容性修复递增 patch；新增用户能力或向前迁移递增 minor；公开契约、部署边界或数据恢复语义发生有意破坏时递增 major。发布下一个正式版本前先修改根版本，再从该版本构建任意数量 preview，最后从选定 commit 构建 stable；不得通过修改 Desktop 子包版本制造第二版本源。

## Server

Server 使用 glibc 系 Node 运行镜像、非 root 用户、单一 `/data` 和同包 Web dist。容器启动同一个生产 Server 入口并显式监听 `0.0.0.0`；外部入口自动生成 TLS 并要求设备鉴权，内部 DSH WebServer 只监听随机 loopback。Runtime 完整恢复后发布匿名 liveness 与 readiness。当前 Server 的 loopback 与 TLS descriptor 均保持 `managementProtocol = 1`；它不因新 Desktop 支持 protocol 2 而抬高兼容 transport 的协议号。镜像构建拒绝脏工作树，版本与 Desktop Product Release 使用同一产品版本和 commit 身份。安全入口见 [Desktop 多实例与设备鉴权](../implemented/2026-08-23-Desktop多实例与设备鉴权.md)。

## 升级与恢复

正常 Runtime 打开数据库前，宿主必须读取安装 Release 与数据 Release，获取单实例升级锁，并在任何 migration 前创建恢复点。Core、DSH、Client 和 Extension 仍由各格式所有者迁移；宿主只负责顺序、journal、备份、失败恢复和 ready 门禁。

代码 downgrade 不受支持。新 Release migration 失败时，不能让旧二进制读取已经前移的数据；回退程序必须同时恢复升级前备份。DSH Session schema 没有公开迁移路径时，升级入口只能继续使用旧 DSH、拒绝升级，或执行产品明确实现的一致性归档与新库重建；禁止修改 DSH 私有表。当前 schema 15 → 17 路径先归档旧库并关闭引用旧 Session 的 Episode，再由 rc.2 创建 schema 17 新库；未知格式仍在 preflight 阶段拒绝。

当前实验首先验证同一 Server 入口、同包 Web dist、releaseId 握手、生产容器和 migration 前 SQLite 恢复点。完整数据根备份、自动恢复交互、平台签名、整包自动替换、跨设备同步和社区插件分发不在本实验中实现。

## 影响

- `apps/desktop` 是 Product Release 的 Desktop 宿主，也是多个独立 NekroNXT 服务实例的本地管理客户端；
- `apps/server` 同时提供可由 `node` 启动的生产入口和 Desktop 可启动的无副作用入口；
- Web 只面向同包 Host 契约构建；Desktop 通过窄 management/chrome protocol 门禁选择是否加载远程实例，不维护任意历史业务 API 的在线兼容层；
- Desktop 与 Server 对同一旧数据 fixture 必须得到相同升级结果；
- 产品 Release 签名与未来社区 Extension 供应链是不同问题，本决定不提前建设社区签名或市场。

## 未来方向检查

关联方向：Desktop/Server 双宿主、多设备同步、社区扩展、远程管理与长期升级。

保留接缝：单一 Product Release 身份、稳定数据根、格式所有者 migration、不可变 Extension Revision、Host ready 门禁和完整包替换。

避免的锁死：不把 Desktop 做成中心平台薄客户端；不允许 UI/Host 混搭；不把 Electron IPC 变成第二套领域 API；不让程序 Release 覆盖用户扩展与数据。
