# NekroNxt 参考项目复用指南

> 文档性质：新架构与新能力的参考取舍约束
>
> 目标：只借鉴可验证机制与失败经验，不把参考项目的私有背景、代码形状或兼容负担带入 NekroNxt

## 1. 证据顺序

设计和实现外部集成时，按以下顺序取证：

1. NekroNxt 当前 accepted/implemented Decision、协议、类型和测试；
2. 依赖的公开 API、已安装精确版本、公开类型声明和可复现行为测试；
3. 公开上游仓库的文档、源码和测试；
4. 历史项目中已经脱敏的机制与失败经验。

相邻仓库、本机路径、企业业务背景、未公开提交和私有部署信息不能成为公开设计、构建或测试的前置条件。公开文档必须让外部贡献者只依赖本仓库和公开上游资料理解决定。

## 2. 通用复用流程

新架构或新能力开始前：

```text
确认本仓当前所有者与事实流
→ 找到参考项目中对应的公开机制和测试
→ 记录可复现行为，不复制目录和内部实现
→ 明确借鉴、拒绝与兼容边界
→ 通过本仓公共契约实现最小垂直切片
→ 用真实入口或契约场景验证
```

只有名称相似、代码可复制或未来可能有用，不构成复用理由。新增抽象必须有当前消费者，并能指出删除后会失败的行为或测试。

## 3. DSH

优先借鉴：

- Cordis 可逆 effect、Plugin 生命周期和 Scope；
- DSH Session、Agent Loop（智能体运行循环）、Tool Pipeline、Preset、Bundle/Profile 和 Client Slot；
- 动态 Cordis 的 inspect、define、run、stop、undefine 行为；
- 真实公开入口组装、精确依赖版本和恢复测试。

必须拒绝：

- 深 Fork、私有源码路径和读取 DSH 私有数据库表；
- 把共享进程内动态 Registry 当持久层；
- 把 `node:vm` 或 in-process Realm 宣称为安全隔离；
- 把 DSH 模型原始文字自动投递为频道消息；
- 因上游包粒度成熟而在 NekroNxt 提前复制同样数量的空包。

DSH 行为以当前 lockfile 中精确版本的公开导出、发布包说明和本仓兼容测试为准。dist-tag、相邻源码仓库和聊天中的旧分析不是事实源。

## 4. Nekro Agent 与聊天平台参考

Nekro Agent 只提供群聊产品、Adapter、媒体积累、部署门槛和社区扩展方面的历史经验。首期 QQ Adapter 可以参考其公开 QQ OpenClaw 行为与测试，但必须重新落到 NekroNxt 的 Connection、Channel、Binding、MessagePart、Asset、Outbox 和 Receipt 契约。

必须拒绝旧数据迁移、旧插件兼容、Python 主栈、旧 chat key、文本 AT 标记、主进程插件直连数据库、布尔发送结果和复杂 Docker 编排。外部平台账号称“机器人账号”，不能与产品中的智能体混为一体。

平台 SDK 或公开实现只能说明平台能力和故障行为，不能把平台对象直接泄漏进 Core。QQ 等具体协议由 Adapter 拥有；Core 只保存规范化事实和稳定身份。

## 5. 按任务记录取舍

涉及参考项目的实现或 Decision Note 至少简短记录：

```text
参考对象：公开 DSH rc.6 动态 Cordis 工具
借鉴：会话拥有的动态定义、可逆运行与停止、Client Slot
拒绝：共享进程影响范围、进程内 Registry 持久化、把 vm 当安全边界
落点：目标智能体 Scope、ExtensionDraft、不可变 Revision、独立 Activation
验证：智能体间不可见；停止后 Tool、Listener、Timer 与 Slot 均消失
```

若参考机制不能通过公开来源或本地可复现测试确认，应将其标为假设并先做 Spike，不把它写成 implemented 事实。

## 6. 与未来方向的关系

参考项目用于保留稳定接缝，不要求提前实现未来能力。每次交付仍需说明关联方向、当前接缝、是否锁死未来和明确未实现的范围；不得以“上游已有”为理由提前引入社区市场、供应链、远程 Runtime、复杂权限系统或多平台特例。
