# 智能体扩展配置与凭据

状态：accepted（2026-10-20 批准，2026-10-21 实施；2026-10-21 修订 C1–C3、新增 C16：GitHub 账号移出凭据，成为「关联账号」，2026-10-22 设置页与能力页实施；频道层配置未实施，尚未发布）

动态创造一碰到凭据或配置就只能请人去后台：测试凭据要到创造任务页填写，正式配置要到工坊的扩展详情里填写，缺必填项的启用会被转到后台。同一个 API 密钥要在扩展、创造任务、MCP 和命令账号里各填一次，智能体也看不到扩展当前的配置和报错。本决定让智能体在用户划定的范围内自己把扩展配到能用，同时保证凭据原文不进入模型上下文。

## 1. 场景与目标

- 群里提出需求后，智能体能自己完成「写扩展 → 用测试配置试运行 → 绑定凭据 → 启用 → 按需要调整配置」，不需要有人中途打开后台。
- 凭据只添加一次，可以被多个扩展、命令和智能体复用；用户决定能用什么、能用在哪，智能体决定什么时候用，每次使用都有记录。
- 智能体知道凭据存在、能看到用途说明，永远看不到原文。
- 智能体的配置修改有历史、能回退，并且记录是谁的请求。

## 2. 决定

| # | 决定 |
| --- | --- |
| C1 | 设置中的「账号与服务」分为「凭据」和「关联账号」。凭据是具名条目：名称、说明、值（只写不读）、使用方式、允许的域名、可用智能体（默认全部）、自动使用。GitHub 这类平台账号不是凭据，放在「关联账号」（C16）。值仍保存在本机凭据存储中，不加密（沿用[命令账号授权](2026-10-11-命令账号授权.md)） |
| C2 | 使用方式分两档。「仅用于网络请求」是默认档：扩展只拿到占位符，宿主在 `nxt.http.fetch` 发出请求时才把值填进去，并且只对允许的域名填写。「允许程序读取」需要用户主动选择：命令、SDK 和扩展代码能拿到原文，选择时就地提示风险。GitHub 账号不在这里，命令通过关联账号拿到它（C16） |
| C3 | 自动使用打开时，智能体在凭据的可用范围内直接使用；关闭时，智能体使用前要发起申请，管理员在聊天里用 `/ext approve` 批准。本条只适用于凭据：凭据自带可用范围，不在每个智能体上单独授权。关联账号仍按命令账号授权的 A1、A2 在智能体上授权（C16） |
| C4 | 模型供应商作为一种特殊凭据列在凭据页，开关决定是否开放给智能体和扩展。调用一律由宿主代发，密钥不交给代码。扩展的 `models` 能力只能看到已开放的供应商。已有供应商默认开放，之后新加的默认关闭。模型密钥仍在模型设置中管理 |
| C5 | 宿主在取值时检查授权：该字段在 Manifest 中声明为凭据，当前智能体在凭据的可用范围内，使用方式允许这种取值。任一项不满足都当作未设置。此前只按引用格式取值 |
| C6 | 工具结果进入上下文之前，宿主统一替换已登记的凭据值，覆盖原文、base64 和 URL 编码三种形式。工具参数中出现凭据值时拒绝执行，读取凭据存储目录也拒绝。群友发来的消息和扩展的上下文贡献同样先替换再入库。替换发生在超大结果另存之前 |
| C7 | 智能体可以查看扩展详情：配置结构、当前值（凭据只显示是否已设置或绑定的名称）、校验问题、启用前提、运行状态、最近的报错，以及自己每种操作会被直接执行、申请还是转到后台 |
| C8 | 创造任务的测试配置覆盖所有字段。智能体可以提供非凭据字段，取值顺序为：默认值、智能体提供的值、用户在任务页填的值，后者优先。凭据字段由用户填写或绑定凭据 |
| C9 | 字段按影响分级：普通、影响网络去向、凭据、仅管理员。影响网络去向的字段由 Manifest 中 `config` 模式的网络字段推导，智能体写入后不作为放行内网的依据，必须申请。仅管理员字段由作者声明 `meta.agentWritable: false`，动态创造的扩展不能使用这个标记，只有导入或社区安装的扩展可以使用 |
| C10 | 智能体通过 `configure` 动作修改正式配置，判定复用扩展流转治理的 `assess`：本机层修改影响所有智能体，需要申请；网络字段需要申请；仅管理员字段转到后台；其余按扩展自主权处理。修改在回合结束后生效，同一回合内的多次修改合并为一次 |
| C11 | 新增智能体设置「谁可以让它改配置」，默认只有管理员。设为所有人时，群友只能让它修改智能体层的普通字段；网络字段、本机层和凭据绑定只接受管理员的请求 |
| C12 | 扩展配置有历史版本，界面和智能体的每次写入都生成一个版本，记录来源、发起请求的成员和原因。回退就是把旧版本写成一个新版本。修改后扩展重载失败时自动回退，并唤醒智能体说明原因 |
| C13 | `enable` 可以同时提供初始配置，与启用一起判定。此后不再要求智能体层的必填项必须有默认值 |
| C14 | 智能体不能扩大自己的范围：不能修改系统访问级别、扩展自主权、「谁可以让它做扩展」「谁可以让它改配置」、管理员、模型供应商和平台连接，也不能批准自己发起的申请 |
| C15 | 智能体缺凭据时发起申请，附带建议名称、用途和域名。通知里的链接打开已预填的添加表单，用户保存后智能体自动继续 |
| C16 | 设置新增「关联账号」，按平台分组列出账号（账号名、权限范围、授权给哪些智能体、最近使用），每个平台可以添加账号并管理平台工具（GitHub：下载或移除 gh）。账号只在智能体上授权：能力里的 `commandAccounts` 决定哪个智能体的命令以哪个账号工作，每个平台一个，子智能体沿用，默认为空，账号库本身不授予任何权限，也没有可用范围和自动使用。平台通过注册表接入，本次只有 GitHub。`GH_TOKEN` 等账号使用的环境变量不能再给凭据使用；旧数据里凭据与账号设置同一个变量时，账号的值生效并记录日志 |

## 3. 边界

- 「允许程序读取」的凭据，代码在执行时可以把它发到外部，也可以把它变形后再打印，例如倒序或拆成单个字符。替换只能防止意外出现在上下文里，挡不住有意外发。缓解手段是：默认使用「仅用于网络请求」，使用权限收窄的专用 token，关闭「命令联网」，并查看使用记录。
- run_code 的子进程会清空 `process.env`（`dsh-ptc-runtime-node` 0.2.1-alpha.2），程序只能通过它调用的命令拿到「允许程序读取」的凭据。
- 完全访问的智能体仍能用不经过工具的方式读取凭据文件，例如先用脚本复制再处理。替换只能拦住直接读取。
- 扩展在进程内运行，可以绕过 SDK 直接读文件或联网。真正的隔离属于 Process Runtime，见[扩展宿主能力与生态移植](2026-10-07-扩展宿主能力与生态移植.md)。
- 少于 8 个字符的凭据误伤太多，不做替换，录入时提示。

## 4. 备选

- **凭据只保管、授权全部在智能体页**：更安全，但每加一个智能体都要去后台勾选，解决不了在群里打断用户的问题。
- **只做「仅用于网络请求」**：最安全，但命令行工具和必须拿到原文的 SDK 都用不了。
- **频道层配置**（`config.channel`）：用于「每个群一份」的值，需要升级 SDK 并改动配置契约。本次只保证智能体工具的结构以后能加这一层，暂不实施。

## 5. 契约入口

- 凭据库（C1）：表 `credentials` 与 `credential_uses`（`packages/storage-sqlite/src/repositories/credentials.ts`，迁移 `0051_credentials`）。使用记录每个凭据保留最近 500 条，且不超过 90 天；命令的使用每个智能体每 10 分钟最多记一条。服务在 `apps/server/src/credentials-library.ts`：值只写不读，启动时载入并以凭据名称登记到隐藏列表，少于 8 个字符的值在视图里标为 `redactable: false`；「仅用于网络请求」的凭据至少要有一个允许的域名。
- 接口：`packages/contracts/src/credentials.ts` 的视图与请求结构，`packages/contracts/src/host-api.ts` 的 `getCredentials`、`createCredential`、`updateCredential`、`replaceCredentialValue`、`removeCredential`（凭据在用时先返回使用者，带 `confirm` 才删除）、`getCredentialUses`、`dismissCredentialRequest`、`setModelProviderAccess`；路由在 `apps/server/src/host-routes-credentials.ts`。扩展配置的更新请求以 `credentialBindings` 绑定凭据，视图以 `boundCredentials` 列出绑定。凭据只有通用一种，旧的 `/api/settings/command-accounts` 接口已移除。
- 取值授权（C5）：扩展凭据字段可以保存 `credential:named:<凭据编号>`，旧的 `credential:local:` 引用照常可用。`apps/server/src/extension-host-backends.ts` 的 `resolveExtensionSecret` 按绑定声明的凭据字段（`NxtServiceBinding.declaredSecrets`）、凭据的可用范围和使用方式取值，本机实例只能用对所有智能体开放的凭据。管理员在配置里绑定即视为同意，取值时不再看「自动使用」。
- 占位符（C2）：`nxt.secrets.placeholder(key)`，扩展能力等级 12（`EXTENSION_SDK_LEVEL`，登记为 0.7.0）。`apps/server/src/extension-host-service.ts` 收集请求里的占位符，`apps/server/src/extension-egress.ts` 在每一跳按凭据的域名填入。「允许程序读取」且没有填域名的凭据，可以发往扩展网络权限允许的任何地址。
- MCP：`ExtensionMcpValueSchema` 的 `{ credential: 名称或编号 }`；环境变量要求允许程序读取，请求头只发往凭据允许的域名（`apps/server/src/mcp-servers.ts`）。
- 命令（C2、C3、C16）：「允许程序读取」的凭据可以填一个环境变量名（`envName`），`GH_TOKEN`、`GH_CONFIG_DIR` 等账号与 `gh` 使用的变量保留不可用（`CredentialEnvNameSchema`）。智能体的命令拿到的是：可用范围包含它、有环境变量名，并且自动使用打开或管理员已为它同意的凭据（同意记在凭据的 `approvedAgentIds` 上），再加上它被授权的关联账号；两者设置同一个变量时账号生效，并记一条日志。可用范围重叠的两个凭据不能用同一个环境变量名，保存时报出占用它的凭据。命令环境与提示词在 `apps/server/src/command-account-env.ts`：提示词先列账号（平台、账号名、使用提示），再列凭据名称和变量名，都不含值。
- 关联账号（C16）：平台接口与注册表在 `apps/server/src/linked-accounts/platform.ts`（`LinkedAccountPlatform`：添加方式、取 token、验证、是否同一账号、命令环境、提示词、平台工具），GitHub 实现在 `linked-accounts/github.ts`（`GH_TOKEN`、临时 `GH_CONFIG_DIR`、内存中的 git 凭据助手、下载的 gh 放到 `PATH` 前面）。账号库 `linked-accounts/library.ts` 用表 `linked_accounts` 与 `linked_account_uses`（迁移 `0053_linked_accounts`），token 存在本机凭据存储，启动时载入并以 `<平台> <账号名>` 登记到隐藏列表（替换后显示 `[凭据:GitHub 账号名]`）。使用记录与凭据相同：每个账号最近 500 条、不超过 90 天，每个智能体每 10 分钟最多一条。接口为 `getLinkedAccounts`、`addLinkedAccount`、`replaceLinkedAccountToken`（只能换成同一账号的 token）、`removeLinkedAccount`（已授权时先返回 `grantedAgentIds`，带 `confirm` 才移除，下一条命令起失效）、`getLinkedAccountUses`，路由在 `apps/server/src/host-routes-linked-accounts.ts`；gh 的下载与移除仍是 `downloadGithubCli`、`removeGithubCli`（`host-routes-runtimes.ts`）。授权在 `updateAgentCapabilities` 的 `commandAccounts` 中修改，服务端检查账号存在、平台一致、每个平台一个。`nekro_nxt_credential_list` 另列 `accounts`（平台、账号名、`grantedToYou`）。
- 迁移：首次启动时，命令账号库（系统设置 `command-accounts`）里的每个账号成为编号 `acc_<账号编号>` 的关联账号，沿用原来的 token 文件，原设置在同一事务里清空。此前已迁成凭据的 GitHub 账号（`credentials` 中 `kind = 'github'` 的行，编号 `crd_<后缀>`）成为 `acc_<后缀>` 的关联账号，沿用 token 文件和命令使用记录，凭据行在同一事务里删除，token 文件保留；两种迁移重复启动都不会再迁。智能体修订里的旧授权不改写：不带 `acc_` 前缀的 `accountId` 在读取时按 `acc_<accountId>` 解析（`linkedAccountIdOfGrant`），界面拿到的授权已换成账号的当前编号。凭据可用范围本来就由授权同步而来，迁移后只看授权；只在凭据页把 GitHub 凭据开放给某个智能体、却没有授权的，需要在能力页重新授权。
- 模型供应商（C4）：系统设置 `model-provider-access`（`apps/server/src/model-provider-access.ts`）。首次启动时开放当时已有的全部供应商，之后添加的默认关闭；扩展的 `models.list` 只列开放的供应商。
- 智能体工具（C8、C15）：`nekro_nxt_credential_list`、`nekro_nxt_credential_request`（`apps/server/src/extension-governance/agent-tools.ts`），以及 testConfig 中的 `{ credential: 名称 }` 绑定；用户在任务页用 `setAuthoringTestConfig` 的 `credentialBindings` 绑定，任务视图以 `boundCredentials` 列出用户或智能体绑定的凭据。凭据不存在时，申请会通知管理员添加；凭据存在但需要同意时，申请和 testConfig 绑定都会生成 `use-credential` 扩展请求，管理员 `/ext approve` 后把智能体加进该凭据的 `approvedAgentIds`。缺少的凭据记录在系统设置 `credential-requests`（`apps/server/src/credential-requests.ts`），通知链接为 `/settings/credentials?add=1&name=…&purpose=…&domains=…&usage=…&request=…`，保存同名凭据后唤醒发起申请的智能体。
- 字段级别（C9）：`configFieldLevel` 与 `meta.agentWritable`（`packages/contracts/src/config-schema.ts`）。一个字段同时符合多级时按「仅管理员 > 凭据 > 网络 > 普通」取最严的一级。动态创造在定义和保存时由 `assertAgentAuthoredConfig`（`packages/extension-format/src/manifest.ts`）检查：新扩展不能带这个标记，修改任务必须原样保留基线版本已有的标记。导入和社区安装不检查。
- 修改配置（C10、C11）：`nekro_nxt_extension_action` 的 `configure` 与 `revert_config`，判定在 `apps/server/src/extension-governance/actions.ts`。顺序是：仅管理员字段转到后台；请求者不是管理员时，`AgentCapabilities.extensionConfigRequesters` 为 `admins`（默认）则婉拒，为 `everyone` 则只放行智能体层的普通字段；手动档转到后台；本机层与网络字段申请；需要同意的凭据申请；管理员确认档申请；其余直接执行。请求者按发起这一轮的消息判断，智能体自己醒来时按普通成员处理。直接执行的修改在回合结束后由 `ExtensionRequestService.scheduleConfigure` 写入，同一回合内同一层的修改合并为一次。网络字段只能经管理员同意后写入，同意即视为用户填写，扩展实例与挂载因此按用户填写的地址放行内网。
- 写入与历史（C12）：所有来源都经 `ExtensionConfigService.write`（`apps/server/src/extension-governance/config-service.ts`），控制台的两个配置路由也走这里。表 `extension_config_versions`（迁移 `0052_extension_config_versions`）按扩展、层、智能体编号，来源为 `console`、`agent`、`chat-admin`、`revert`、`auto-revert`；控制台写入、智能体修改、启用时的初始配置和随数据迁移的配置都记录。接口为 `getExtensionConfigVersions`、`revertExtensionConfig`。恢复时绑定的具名凭据一并恢复，手填后又被替换的凭据保持当前值。新配置让扩展启动失败时，生命周期保留原挂载；原挂载也没有回来时重新写入上一版并记为 `auto-revert`，两种情况都以系统通知告诉智能体原因。
- 启用时配置（C13）：`enable` 的 `values`、`credentials` 与启用一起判定。`enablementProblem` 只在缺少仅管理员字段或本机配置时转到后台，缺少智能体可以填写的必填项时由 `enablementMissing` 提示它在启用时提供。智能体层必填项不再要求默认值；已启用的智能体切换到新增了必填项的版本时，`carryAgentConfigLeniently` 保留仍然有效的值，配置问题在查看结果里列出。
- 不扩大自身范围（C14）：智能体工具与扩展动作都不涉及能力、管理员、模型供应商和平台连接，申请只能由管理员处理；验证见 `apps/server/tests/extension-configure.spec.ts`。
