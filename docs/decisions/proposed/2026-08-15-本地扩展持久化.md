# 提案：本地扩展持久化、构建与启用

状态：proposed

## 问题

DSH 动态 Package 只存在于当前进程内，重启后消失，也不会自动转成磁盘插件。NekroNxt 需要把验证过的动态产物保存为可审查、可重建、可回滚的本地 Extension Revision，并在用户明确选择后给指定智能体启用。

必须保持三个动作分离：

```text
动态运行 ≠ 保存为本地扩展 ≠ 给智能体启用
```

## 目标

- Extension 身份稳定；
- Revision 不可变，源码与 Manifest 可追溯；
- 构建结果可重建，不依赖动态进程内对象；
- Activation 明确指向智能体和 Revision；
- 坏扩展不会阻止系统恢复启动；
- Desktop 与 Server 使用相同格式；
- 未来社区分发无需重写首期本地扩展。

## 方案比较

### 方案 A：保存源码 Revision，启动或启用时重建

优点：目录简单，源码是唯一持久事实，产物不会与源码长期漂移，也符合一期先验证本地创造闭环的目标。

代价：首次启用或缓存失效时需要构建；构建器和依赖输入必须由宿主固定；坏 Revision 必须隔离，不能拖垮启动。

结论：一期采用。

### 方案 B：保存源码、锁定清单、构建产物和验证证据

保存时在临时目录完成构建和验证，成功后原子提交不可变 Revision。启动优先加载已验证产物，产物缺失或摘要不符时进入“需要重建”，不静默执行未验证源码。

结论：未来确有离线分发、快速冷启动或强验证证据需求时再演进，一期不实现。

### 方案 C：只保存打包产物

优点：启动最快，分发简单。

问题：不能继续让智能体修改源码，难以审计和重建，也不符合本地创造产品目标。

结论：只适合未来社区二进制分发，不适合本地创造。

## 已确认持久化模型

### `LocalExtension`

- `id`：稳定随机 ID，不使用目录名或 npm 名作为身份；
- `slug`、`displayName`、`description`；
- `origin`：`local-created`、`local-imported`、未来 `community`；
- `createdByAgentId?`；
- `createdAt`、`deletedAt?`；
- `defaultRevisionId?`：只作为未来 Activation 默认值，不改变已有 Activation。

### `ExtensionRevision`

- `id`：ULID/UUID；
- `extensionId`；
- `revisionNumber`：扩展内单调递增展示号；
- `contentDigest`：清单、规范化源码和锁定输入的 SHA-256；
- `manifestSchemaVersion`、`extensionApiVersion`；
- `sourceKind`、`sourceDynamicPackageRef?`；
- `lastBuildStatus?`、`lastValidationStatus?`：运行状态或缓存索引，不属于 Revision 身份；
- `compatibleNekroNxtRange`、`compatibleDshRange`；
- `createdAt`。

Revision 一经提交不得原地修改。其身份只由规范化源码、Manifest 和固定构建输入决定；构建产物位于可丢弃缓存中，不作为持久 Revision 的组成部分。修改源码必须产生新 Revision。

### `AgentActivation`

- `id`、`agentId`、`extensionId`、`extensionRevisionId`；
- `configRevision` 或配置快照；
- `state`：`pending`、`active`、`waiting-safe-switch`、`failed`、`disabled`；
- `runtimeKind`：首期 `in-process`；
- `createdAt`、`activatedAt?`、`disabledAt?`；
- `lastError?`。

Activation 必须直接指向 Revision，不能只指向“最新版本”。

## 磁盘布局

建议：

```text
/data/extensions/
  <extension-id>/
    extension.json
    revisions/
      <revision-id>/
        manifest.json
        source/
          host.ts
          client.tsx
          ...
        source-input.json
    staging/
    quarantine/

/data/cache/extensions/
  <revision-id>/
    <build-key>/
      host.mjs
      client.mjs
      build.json
      validation.json
```

规则：

- 路径只承载存储，不作为公开身份；
- `manifest.json` 与源码属于事实输入；
- `source-input.json` 记录固定 SDK/API、构建器协议和允许依赖集合，不承担完整 npm lockfile；
- `/data/cache/extensions` 中的 bundle、构建日志和验证结果均可删除并重建；
- 缓存 `build-key` 由 Revision digest、构建器版本、Node ABI、目标宿主和 SDK 版本共同计算；
- UI 展示的验证结果来自真实构建、调用、渲染和停止检查，不把“智能体声称成功”作为证据；一期不承诺将完整证据作为永久发布档案保存；
- Secret 只保存引用，不进入清单、源码、构建日志和摘要输入；
- 源码不得持久化宿主绝对路径。

## Manifest 最小字段

```ts
interface ExtensionManifestV1 {
  schemaVersion: 1
  extensionId: string
  revisionId: string
  name: string
  apiVersion: string
  entrypoints: {
    host?: string
    client?: string
  }
  contributions: ExtensionContributionDeclaration[]
  requestedCapabilities: CapabilityRequirement[]
  configSchema?: JsonSchema
  compatible: {
    nekroNxt: string
    dsh: string
  }
}
```

首期不加入 Publisher、签名、SBOM、审核等级和远程下载地址。

## 从动态 Package 到 Revision

当前 DSH Registry 不是持久事实源。NekroNxt 创造工作台必须同时维护自己的 `ExtensionDraft` 和不可变 `DraftPackage`：

```text
用户描述需求
→ 智能体调用 DSH cordis_define/run 实验
→ NekroNxt 记录 DraftPackage 源码、目标智能体和验证计划
→ 真实运行/调用/渲染/停止验证
→ 用户点击“保存为本地扩展”
→ Materializer 生成正式 TS 源码与 Manifest
→ 在 staging 原子保存源码、Manifest 和 source-input
→ 创建不可变 ExtensionRevision
→ Builder 构建到可丢弃缓存
→ Validator 对缓存产物运行关键场景并记录当前结果
→ 用户另行选择“启用给某智能体”
```

DSH 动态 `dyn-*` ID 只能作为本次创造会话的来源引用，不能成为 Extension ID 或 Revision ID。

## 构建策略选项

### 选项 1：受控 bundler 输出单文件 ESM

使用固定版本的 esbuild/tsdown，把 Host 和 Client 分别构建为 ESM bundle。只允许导入 Extension SDK 和清单声明的内置依赖。

优点：启动简单、依赖封闭、摘要稳定、适合 Desktop/Server。

缺点：需要定义动态 import、native dependency 和 source map 策略。

推荐：首期采用。

### 选项 2：`tsc` 保留模块树

优点：最接近源码，类型行为标准。

缺点：运行时依赖解析和复制复杂，用户扩展容易依赖宿主 node_modules。

结论：不推荐首期。

### 选项 3：直接用 tsx 执行源码

优点：开发方便。

问题：用户机器启动依赖开发工具链，验证产物与运行输入不稳定。

结论：只可用于开发模式，不能作为正式本地扩展加载方式。

## 依赖策略选项

### Alpha 推荐：无任意第三方依赖

- Extension 只能导入版本化 `@nekro-nxt/extension-sdk` 和明确的 Web 标准；
- 常用能力通过宿主 Service/Contribution 提供；
- Builder 拒绝未声明 bare import；
- 不在保存过程中动态执行 `pnpm install`。

这能先验证创造闭环并保证安装即用。未来出现真实依赖需求后，可增加“宿主 allowlist 依赖”或“每 Revision 锁文件 + 构建隔离”，不在首期提前实现完整 npm 供应链。

## 原子保存与构建缓存

推荐提交步骤：

1. 为保存请求创建数据库 `saving` 记录和唯一 operation ID；
2. 在 `staging/<operation-id>` 写入规范化源码、Manifest 和 source-input；
3. 校验文件边界、imports、Manifest 和 content digest；
4. 将 staging 原子 rename 到 `revisions/<revision-id>`；
5. 在 Core SQLite 事务中插入 Revision 并标记 `saved`；
6. 按用户验证或启用动作构建到独立缓存临时目录，成功后原子替换该 build-key 的缓存；
7. 从缓存产物启动实例，完成 Tool、UI、停止/卸载和目标场景验证；
8. 崩溃恢复扫描 staging、孤儿 Revision 和不完整缓存，按 operation ID 恢复或隔离。

文件系统 rename 与 SQLite 不能形成真正跨介质事务，因此使用 operation journal 和幂等恢复，不伪造原子性。数据库已提交但源码目录缺失时 Revision 标记损坏；缓存缺失则正常重建。任何构建失败只影响对应 Revision/Activation，不阻止 Core 和其他扩展启动。

## 加载与作用域

1. 启动系统 Bundle 和 Core；
2. 读取 active Activation；
3. 校验 Revision 和 API 兼容范围，命中缓存则复用，否则受控重建；
4. 构建失败则只将该 Activation 标记 failed；构建成功后在对应智能体作用域挂载 Cordis Plugin；
5. 注册 Tool/Service/Slot 等 Contribution；
6. 记录加载结果；
7. 任一加载失败只将该 Activation 标记 failed，不阻止 Core 启动。

首期可以为每个智能体 Activation 创建独立插件实例，先保证作用域正确，再优化共享实例。禁止为了复用实例把扩展注册到 global scope。

## 更新与回退

- 新修改产生新 Revision；
- “设为默认版本”只影响未来 Activation，不移动现有引用；
- “切换到此版本”创建 Activation 变更并等待安全间隙；
- 当前 Tool 完成后关闭旧 Episode、卸载旧实例、挂载新 Revision、创建新 Episode；
- 回退使用同一流程，不修改旧 Revision；
- 删除 Extension 前必须没有 active/pending Activation。

## 恢复模式

- 正常启动连续失败或用户显式选择时，跳过全部非 System Extension Activation；
- UI 展示失败扩展、Revision、错误和最近日志；
- 用户可以单独重试、停用或回退；
- 不自动删除源码与 Revision；
- 插件 dispose 必须有超时和资源清理诊断，但首期不宣称 in-process 是安全隔离。

## 待决策项

1. 构建器：esbuild 还是 tsdown；推荐先 Spike 两者，偏向 esbuild 的小 API 面；
2. Revision ID：ULID + digest 还是 digest 直接做 ID；推荐 ULID + 独立 digest，避免身份与内容策略耦合；
3. 构建缓存保留策略；推荐按磁盘上限 LRU 清理，当前失败摘要进入数据库，完整日志只随缓存保留；
4. 是否允许导入 npm 依赖；推荐 Alpha 禁止任意依赖；
5. Client bundle 是否与 Host 同 Revision 提交；推荐同 Revision、独立 entrypoint 和 digest，避免两半漂移。

## 验证

- 删除全部扩展构建缓存后，系统能仅凭源码 Revision 重建并恢复 Activation；
- 动态 Tool 和 Client UI 保存后重启可恢复；
- Extension 保存后未创建 Activation 时不影响任何智能体；
- 给智能体 A 启用后，智能体 B 看不到 Tool 和 Slot；
- Plugin dispose 后 Tool、Listener、Timer、RPC 和 Slot 全部消失；
- 故意损坏一个 Revision，Core 仍能进入恢复模式；
- 回退到旧 Revision 不修改旧源码；旧缓存不存在时可重新构建；
- staging 每种崩溃点都能幂等恢复或隔离。

## 未来方向检查

关联方向：Process/Remote Runtime、多设备同步、社区市场、智能体自迭代。

保留接缝：稳定 Extension ID、不可变源码 Revision、独立 Activation、`RuntimeKind`、API 版本、来源字段、可重建缓存和 Secret 引用。未来可以在不改变 Revision/Activation 语义的前提下追加持久 artifact 与 evidence。

避免锁死：不以本地路径作为身份，不让安装自动全局生效，不把 Core 数据库暴露给插件，不要求未来社区格式重写。

本次不做：签名、SBOM、云构建、第三方强隔离、任意 npm 安装、Process/Remote Runtime。

## 参考证据

- DSH Dynamic Cordis define/run/stop 生命周期和 Scope；
- DSH Client Slot 可逆注册；
- Nekro Agent 动态插件直连主进程和持久化耦合的反例。

借鉴机制：不可变版本、可逆 effect、构建产物与源码分离、失败恢复。

明确拒绝：不复制 DSH 进程内 Registry 作为持久层，不复制 Nekro Agent 的插件直连数据库，也不提前建设社区供应链。
