# NekroNXT 开发与测试规范

> 文档性质：开发者和 AI 编码工具共同遵循的公共工程规范
>
> 目标：让每次改动保持边界清楚、证据充分、可以回退，避免随着智能体参与开发而积累重复抽象、隐式状态和不可验证行为

## 1. 知识与决策

文档按事实所有者分工，阅读按任务需要定位到相关章节。已知局部问题可以直接进入源码、测试和对应契约；[公开索引](README.md)、[Apps](../apps/README.md) 和 [Packages](../packages/README.md) 帮助查找未知来源，不是每次编辑前的必读序列。

| 来源 | 职责 |
|---|---|
| 根 `AGENTS.md` | 项目特有的常驻边界、授权与完成条件、简短任务路由 |
| 专题协议与设计文档 | 当前行为、数据或界面契约的完整说明 |
| 包 README | 包职责、公开入口、消费者、包级运行与恢复操作 |
| Decision | 决策理由、重要取舍、状态和当前契约链接 |
| 本地文档 | 本机服务所有者、端口、路径、恢复方法与私有参考入口 |
| 归档 | 已被替代的设计和过程证据，不指导当前实现 |

用户明确决定约束任务与产品方向。核对冲突时区分“应当怎样”和“目前怎样”：前者查用户决定与对应契约，后者查当前实现、锁定依赖和可复现测试；代码也可能有缺陷。Decision 的状态标签不自动覆盖根规则或当前契约。能依据证据解决的冲突直接修正，只有缺少真实产品选择时才向用户澄清。与本次无关的独立差异按 §2 记录，不强制扩大任务。

Decision 状态：`proposed` 是待选择方案；`accepted` 是已确认目标，必须说明未落地部分；`implemented` 表示决定已经落实，应链接当前契约与验证入口；`rejected` 记录仍有参考价值的否决理由。被替代决定进入归档。已有独立承载契约的 Decision 可继续作为该事实的唯一来源，索引应说明其职责；把契约迁入专题文档时，原处改为链接，不能两处完整维护。

公共协议、跨包职责、持久格式、DSH 集成、Extension/Adapter 生命周期或测试策略发生重要选择时，新增或更新相关 Decision，说明理由、影响与证据。机械同步、普通局部修复和单纯字段更名无需新增记录。决策背景可以保留在 Decision；不要把实施日志追加到现行协议，也不为普通功能写里程碑日记。

### 1.1 文档自维护

行为或已记载事实变化时，在同一改动更新它的唯一来源；实现重构但契约不变时无需制造文档 diff。

| 变化 | 完整事实来源 |
|---|---|
| 产品常驻边界 / 用户术语 | `AGENTS.md` / [术语规范](01-术语与文案规范.md) |
| 页面对象、按钮后果 / 跨页用户路径 | [交互模型](NekroNxt界面交互模型.md) / [产品旅程](NekroNxt产品形态与用户旅程.md) |
| 消息内容、投递、媒体、通信工具 | [消息协议](03-消息内容与投递协议.md)；专题独立契约由该文档链接 |
| 一期状态 / 未启动方向 | [一期计划](04-一期开发计划与决策清单.md) / [未来方向](02-未来扩展方向.md) |
| 视觉 Token、布局、组件 / 实现验证 | [设计规范](05-桌面UI与动效规范.md) / 本文 §5–6 |
| 工程规则、文档维护、提交格式 | 本文 |
| Server↔Web 接线 / 包运行与数据恢复 | [宿主设计](08-接线与Server宿主设计.md) / 对应包 README |
| 发布授权、流程与更新内容 | [发布规范](09-正式发布与更新日志规范.md) |

一项改动可能改变多个不同事实，分别更新各自所有者；不因多个文件提到同一事实就要求逐份复述。Decision 只在决定、理由、状态或契约链接变化时同步。现行正文用现在时，过期描述整段修正，不追加“后续说明”掩盖矛盾。

新增、移动或归档受维护文档时接入最近的领域索引，运行 `pnpm check:docs` 检查链接、标题片段、状态和根可达性。公开文档从 `AGENTS.md` 可达；私有资料只有根文件允许链接可选的本地一级索引。检查器不证明语义正确，仍需对照受影响契约与实现。

本地孤岛检查限定在明确维护的知识区域，其他本地文档仅沿索引链接纳入；测试报告、运行数据和第三方工作区不因包含 Markdown 就成为知识文档。具体发现范围由 `scripts/check-doc-links.mjs` 定义，本地索引描述本机使用方式。

### 1.2 提交说明

提交说明使用英文类型前缀和中文一行主题：

```text
type(scope): 中文动词短语
```

- 类型前缀固定使用英文 `feat`、`fix`、`refactor`、`docs`、`test`、`merge`，不得翻译为“功能”“修复”“文档”等中文前缀；CI 或单包可用 `fix(ci)`、`feat(web)` 这种范围；
- 冒号后是现在时中文动词短语，说明做了什么，例如 `接入`、`分离`、`恢复`、`约定`、`忽略`；
- 不写英文长句、不写 Conventional Commit 英文描述、不加正文堆砌过程；必要时用括号补范围，例如 `docs: 注明创造工作台已接入真实 Host`；
- 一个提交只表达一件能独立理解的事；文档自维护随对应实现提交，不为“补文档”单独制造空提交，除非本轮只有文档变化。

## 2. 实现工作流

根据请求确认结果与边界，定位相关实现、测试和契约，然后完成修改与足够的验证。需要解释架构、数据所有权或兼容性选择时先给简短方案；普通局部修复可直接执行。不要求每项任务都查未来规划、参考项目或写执行计划。

在已授权范围内，使用隔离测试夹具与端口，运行相关检查、修复本次导致的失败并重试，无需逐步请求确认。正式发布仍遵循独立的用户审查边界；真实账号、常驻数据和付费模型验收不能与可丢弃夹具混为一谈。

本次造成的缺陷和阻塞本次正确交付的问题必须修复，包括相关文档失真。独立历史问题记录并报告；很小且属于授权范围的修复可以一并完成，不自动接管无关重构、全仓文档清理或视觉整改。已有用户改动要保留。

完成条件是请求范围已实现，相关检查与需要的真实页面验收通过，受影响文档一致，触发重载的开发服务恢复可访问。新增代码、失败或未解决风险才需要扩大或重复检查。无关既有失败单独报告，不能冒充本次回归、隐藏失败或降低门禁；受影响验证受阻时明确说明尚未完成的部分。

## 3. 包与代码边界

- 安装代价较小、安全与维护风险较低、且在同类问题中属于主流选择的框架或库，直接引入并在现行文档写明选型；禁止为了少一个依赖或“更可控”而手写拖拽、虚拟列表、富文本、日期解析等同等复杂度的交互或算法内核；
- 每个包必须有当前职责、当前消费者和独立验证价值；不得为了未来可能复用而创建空包、空接口或无消费者的状态机；
- 包之间只通过公开导出、Service、事件或 Contribution 交互，不跨包导入 `src/internal`、读取对方数据库或共享可变单例；
- Core 保存产品事实，DSH 保存自身 Session 事实，Client store 只保存交互状态；同一业务事实不得同时复制到 Runtime、Zustand 和请求缓存；
- 外部输入、配置、持久数据、模型工具 JSON、进程和网络边界必须运行时校验；同进程的已类型化内部调用信任 TypeScript，不堆重复校验和兜底；
- 跨持久或进程边界的 ID 使用不透明类型，不把普通 `string` 当作所有身份；
- 可扩展联合保留明确 discriminant；封闭联合使用穷尽检查，开放联合保留有说明的默认路径；
- 配置默认值在所属实现的一处显式解析，不能散落 `?? default`；错误配置在最早可判定点失败，不静默跳过；
- 注释和 JSDoc 说明非显然的行为、失败、时序、所有权和兼容承诺，不复述代码或保留推理过程。

任何新增抽象都应能回答：“谁拥有它、谁现在使用它、删除它会破坏哪条测试？”无法回答时先不引入。

## 4. 生命周期与并发

- Cordis 注册、监听器、计时器、Slot 和 Tool 都是可撤销 effect；卸载测试必须观察它们全部消失；
- 一个异步操作只有一个生命周期所有者或事务控制器；取消、完成、回滚和释放由同一处收敛；
- dispose 不只发出 abort/kill，还要等待子任务停止并让系统达到静止；先关闭通知入口，再终止可能产生迟到回调的工作；
- 状态和事件只在真实提交点发布；数据库或外部操作失败时不能先让 UI、缓存或下游看到成功；
- 独立结果独立表达，例如 `timedOut`、`exitCode`、`signal`、`partial`、`unknown`，不能用一个布尔值覆盖多个事实；
- 用户或 Extension 回调的异常由调度器隔离和记录，不能阻断同批其他回调或 Core 生命周期；
- 并发测试优先使用 Fake Clock、受控 Promise 和显式 checkpoint，不使用依赖机器速度的长时间 sleep。

涉及消息、工具执行、恢复、迁移和 Extension 卸载时，根据改动识别崩溃、重复输入、乱序、取消和部分成功风险，并用相关测试验证；不要求为未改变的路径重复列清单。

## 5. 测试设计

测试分为四层，按改动风险选择最窄且足够的组合：

1. **单元/领域测试**：验证纯逻辑、边界值、错误路径、事件顺序和状态机；
2. **契约场景测试**：用 Fake Adapter、Fake Gateway、Fake Clock 或临时数据库验证跨组件行为；
3. **真实组装测试**：通过实际 Bundle、Loader、公开 package entry 和构建产物启动，外部网络或模型可以替换为可控实现；
4. **产品旅程测试**：驱动真实页面验证用户可见闭环、平台行为和升级恢复；仓库默认入口是 `pnpm test:journey`，该命令先构建 Web 与 Server 生产入口，再驱动真实 Host 和页面。

用户可见的布局、样式、路由、客户端状态或渲染数据发生变化时，在上述测试之外还必须完成 §5.1 视觉验收。视觉验收不是第五层可跳过的自动化，而是与四层测试同级的完成条件。

通用规则：

- 仓库内夹具、原型和示例只使用虚构发送者、标题、群名、文件名和 `*.test` 主机。真实入站 dump、个人昵称、群 OpenID、平台临时 CDN、`rkey` 和文件内容哈希不得进入 Git；需要覆盖拍扁协议时，用合成文本复现标记，不粘贴一次真实消息。真实账号旅程在本机运行，原始 payload 不入库。公开边界见 `00-文档公开边界.md`；
- 只 mock 昂贵、不可控或非确定性的边界，边界之后尽量使用真实实现；
- 验证外部世界，不相信智能体或被测代码自称成功：重新读取文件、数据库、频道事件、回执或页面状态；
- 测试描述行为，不锁定私有实现、CSS class、渲染次数和无意义快照；
- 每个回归测试必须证明修改前会失败；每个失败路径必须断言没有发布错误成功状态；
- Registry/Slot/Listener 必须测试注册、更新和 dispose；
- Product-visible Extension 必须有真实组装测试，手工拼一个 `ctx` 的单元测试不能代替；
- React 的 `renderToStaticMarkup` 只验证静态结构，不执行 Effect、事件、浏览器导航、SSE 或外部 Store 订阅生命周期，不得归类为产品旅程或真实浏览器组装；
- 用户可见 Web 改动运行生产 bundle 下受影响的产品旅程；共享导航、全局状态或壳层变化扩大到相关一级路由，CI 与交付复核运行完整旅程。被测路由断言主内容可见、根节点非空，并把 `pageerror`、React `console.error`、未处理 Promise 拒绝和整页错误兜底视为硬失败；动效相关旅程必须覆盖 `prefers-reduced-motion`，截图须等 Presence 结束；
- 代表性稳定页面使用 Playwright `toHaveScreenshot` 与仓库基线比较；仅附加 PNG 只用于人工验收记录，不算自动视觉回归。现有基线覆盖浅色频道会话和深色外观设置；主题风险另由双主题旅程及 §5.1 验收覆盖；
- 频道会话、连接、外观设置和全局命令面板运行 Axe WCAG 2/2.1 A、AA 扫描，critical 或 serious 违规是硬失败。Axe 不能替代键盘、缩放、真实像素和文案验收；
- API、领域测试、类型检查和构建全部通过仍不能替代产品旅程。实现者必须用当前环境能驱动真实页面的手段跑通用户可见闭环；仓库内 `pnpm test:journey` 是默认自动化入口。没有任何真实页面驱动手段时，不得宣称 Web 交付完成；
- 交互测试必须经过真实 DOM 事件和路由切换；仅断言 API 成功不能证明按钮、表单、错误反馈或草稿保留可用；
- Vitest 与 Web Vite 测试服对 workspace 包必须解析到当前源码，不能依赖本机上次留下的 `dist`；别名由 `scripts/workspace-source-aliases.mjs` 从各包 exports 的 source 条件读取，新增或改名只维护包声明。TS references 从生产 workspace 依赖生成，`pnpm sync:references` 显式同步，`pnpm check:references` 只比较不写文件。`pnpm build` 独立验证发布产物。
- Node 单元、契约与静态渲染测试使用 Vitest；真实 DOM 场景位于各应用 `browser-tests/`，通过 `pnpm test:browser` 运行 Playwright。生产旅程位于 Web `e2e/`，使用生产 Web/Server 产物；本地 `test:journey` 自动构建，CI 完整 build 后调用 `test:journey:built`，不重复构建。
- 产品页中的 Button/IconButton 必须具备真实点击、指针或键盘处理器，或位于 ui-kit 语义触发器内，或承担表单提交 / 永久禁用状态。条件性 `disabled` 不能掩盖无处理器控件；空函数、返回 `undefined` / `null` 的处理器仍视为空操作。`check:ui-actions` 只输出静态建议，不属于根 check 门禁；关键动作由生产旅程验证外部结果；
- 用户可见 UI 改动同时完成源码审查与 §5.1 视觉验收；影响本次交付的失败必须修复，独立历史问题按 §2 处理；
- 基础 UI primitive 由唯一 ui-kit owner 提供；业务页面不得直接导入 Radix 或 `motion`，也不得复制 Button、Select、Switch、Tabs、Dialog、Tooltip 的交互状态机。依赖边界由根检查维护；
- Portal 型组件必须使用统一动态层级：同层 `overlay < content < floating`，后打开 Modal 的 overlay 高于前层 floating。层叠修复必须进入 ui-kit 测试，不能在业务页面增加局部 z-index；
- 每个用户可见 mutation 必须覆盖 pending、防连点、失败恢复和成功后的权威结果刷新；处理器内部静默 return、fire-and-forget 或仅乐观改前端状态都不能通过空操作门禁；
- 布局回归按风险加入几何断言：Hover 前后正文宽度稳定、同类状态灯共享视觉轴、内容宽度 Hover 不扩成整行、最后消息不被浮动 Composer 遮挡、消息左右方向符合频道视角、标题不会在窄窗压成逐字竖排。几何断言补充 §5.1，不能替代；
- 迁移测试覆盖空库、保留数据升级、SQL 和外键失败后的事务回滚与重试、当前版本完整性检查和未来版本拒绝；已发布迁移不可改写，旧实验库拒绝策略保持独立。

### 覆盖率门禁

覆盖率的唯一执行入口是 `pnpm test:coverage`，配置权威源是根目录 `vitest.config.ts`。`pnpm check` 和 `pnpm test` 都不会代跑覆盖率；局部修改先按影响运行相关测试；完整覆盖率在集成验收执行一次，以命令退出码为准。只有新的修改、失败或未解决风险才扩大或重复验证，不因修改任意测试文件而重跑全仓。

当前使用 V8 Coverage。Package 源码整体纳入；应用层纳入 Server 的启动、Host API、扩展/DSH 生命周期、Host UI、SSE 和管理边缘，Web 的 Host Port、事件流、Store 与动态 Client 协调，以及 Desktop 的 Host 监管、实例配置、远程配对/Session、Credential 和任务串行化模块。生成式 SQLite Schema `packages/storage-sqlite/src/schema.ts` 与 Web 声明文件排除。整页 React、Electron `main`/preload 和操作系统凭据库由真实浏览器、Electron afterPack 与平台矩阵验证，不用低质量的 Node 插桩数字代替。浏览器场景使用独立 Playwright 运行器，不在 Vitest include 内；移动应用模块时同步 coverage include，保留原范围阈值。

当前阈值是：

| 统计范围 | Lines | Branches |
|---|---:|---:|
| 全部纳入统计的 Package 源码 | 90% | 80% |
| 纳入统计的 Server 组合模块 | 72% | 52% |
| 纳入统计的 Web Host/状态协调模块 | 70% | 45% |
| 纳入统计的 Desktop 生命周期模块 | 80% | 70% |
| `packages/core/src/**` | 90% | 80% |
| `packages/channel-runtime/src/**` | 90% | 80% |
| `packages/storage-sqlite/src/**` | 90% | 80% |
| `packages/contracts/src/**` | 90% | 80% |
| `packages/extension-runtime/src/**` | 90% | 80% |

各范围阈值按表中 glob 的整体结果计算，不要求其中每个文件分别达到同一阈值；Statements 和 Functions 当前没有独立阈值。Package 原有 90%/80% 门禁没有因纳入应用层而降低；应用层阈值以当前真实测试证据为基线并保留至少约 2 个百分点余量。CI 的 quality Job 按 `pnpm check` → `pnpm test:coverage` → `pnpm build` → `pnpm test:browser` → `pnpm test:journey:built` 执行，覆盖率失败会直接跳过构建和产品旅程；`pnpm verify:product` 执行同一套 Coverage 门禁。

覆盖率用于发现未测试代码、错误路径和死分支，不能代替场景测试、真实入口验证或视觉验收。门禁失败时补充能证明真实行为的测试，不删除有效场景、不降低阈值、不添加无依据的排除项，也不要以文本报告显示的四舍五入百分比自行判断；接近阈值时应覆盖实际缺失分支并留出余量。调整阈值、统计范围或排除策略属于测试策略变更，更新实际配置与本节；决策理由或覆盖责任变化时同步相应 Decision，不能只为通过门禁降低标准。

### 5.1 用户可见界面的视觉验收

用户可见的布局、样式、路由、客户端状态或渲染数据发生变化时，同时审查源码和真实产品画面。源码审查验证状态所有权、组件复用、错误处理与实现边界；视觉验收验证布局、可见功能、美观、合理性和可读性。两者都与相关测试同等必要。

#### 真实画面与覆盖范围

验收对象是当前改动实际服务出来的产品画面。可使用当前环境能提供真实渲染帧的任何手段；静态 HTML、设计稿、DOM 文本、计算样式、无障碍树和测试日志不能代替看画面。能理解图像的实现者必须亲自阅读；不能阅读图像时，由能看见画面的人完成视觉验收，未完成前如实标记交付缺口。

覆盖改动涉及的真实用户路径，并按共享组件、状态或数据的影响扩展到有风险的代表页面。选择足够的组合，不要求查看所有消费者或执行全部笛卡尔积：

| 风险 | 代表场景 |
|---|---|
| 视口与布局 | 在 `1100×720`、`1440×900`、`1920×1080` 中选择会受压或发生布局变化的档；响应式变化覆盖断点两侧 |
| 主题与对比 | 涉及颜色、描边、表面或对比时检查浅色和深色 |
| 动效 | 检查连续性与抖动；动效改动另看 Reduced Motion，稳定截图等待 Presence 结束 |
| 操作状态 | 受影响的默认、选中、加载、空态、错误、禁用和焦点状态 |
| 浮层与共享面 | 打开受影响的菜单、对话框、提示或检查器；共享变更覆盖不同布局或交互方式的消费者 |

基础组件或设计语言变化使用[设计规范 §13](05-桌面UI与动效规范.md#13-验收清单)确定更广的缩放、键盘和主题组合。局部文案修改只需验证实际呈现与相关交互，不自动升级为全产品设计验收。

#### 判定标准

- **布局**：内容有稳定的四边安全区，标题与正文轴对齐；无重叠、裁切、逐字竖排或意外横向滚动，Composer 不遮挡消息。Host/Extension 背景、边距与滚动所有权符合 `05` §7.7.1。
- **可见功能**：页面对象、选中项和操作结果可辨；控件有真实反馈，禁用和未开放状态明确，详情与当前对象一致。
- **美观与工艺**：密度、字号、间距、圆角、表面和状态色符合 Token 与相邻页面；无孤立色块、表面拼接、滚动条侵入或导航抖动。
- **合理性**：信息层级、标题职责和导航位置清楚，相关操作成组，危险操作可区分，同一动作没有竞争的主按钮。
- **可读性**：明暗主题对比足够，长名称、中英混排、消息、代码与表格可读，截断不挤掉同一行的必要信息。

影响本次交付的明显缺陷必须修复并重新查看受影响画面；独立历史问题按 §2 处理。审查顺序和次数由问题决定，不强制固定两遍或修一处就从头重复。功能可用、Console 无错、几何断言通过或“比上一版好”均不能单独证明视觉质量。

涉及页面骨架、分栏、边距、页头、滚动或 Extension UI 时，生产旅程保留可确定的几何断言：

- 主画布、Host 内容框、PageHeader 和首个正文区块通过 `getBoundingClientRect()` 验证；Host 四边匹配 `05` §7.7.1 的 Page Inset Token，亚像素容差不超过 `1 CSS px`；
- PageHeader、Toolbar、首个正文区块和主要数据区的外部内容轴差不超过 `1 CSS px`，局部内部 padding 不参与比较；
- 非 Portal 顶级内容不越过 Host 内容框，无意外横向滚动；涉及对象列模式时覆盖 `navigation` 和 `hidden`；
- 在受影响的代表视口执行，失败信息提供实测 Insets。几何断言补充真实画面阅读，不能代替。

完成说明简要列出实际查看的页面、关键状态、视口与主题，说明看到的结果或缺陷；几何变更提供测量证据或对应测试结果。截图可作附件，但仅有附件不算验收结论。公开截图遵循[公开边界](00-文档公开边界.md)，不提交真实聊天或个人标识。

### 5.2 自动扩展创造的真实模型验收

本节只用于任务包含自动扩展创造的真实模型验收时；普通单测、文档或局部页面修改不触发这一流程。

自动扩展创造另有开发阶段黑盒验收：使用真实 Playwright 页面和 `deepseek-official/deepseek-v4-pro`，像普通用户一样描述目标，不在用户消息中提供内部工具名、协议、Slot、React 或实现步骤；观察智能体能否自行发现 Inspect、定义、运行、修复、验证和保存路径。验收按用户可见结果判断，不把“两个可切换视图”写死成两个顶级侧栏入口：一个应用入口下两条真实导航和不同画布同样成立。页面型任务必须硬刷新后仍能恢复预览，保存后必须等待扩展详情标题和主内容真实可见，并检查 HTTP、Console、UI Kit 使用证据和真实像素；不能只看到 `ready`、URL 改变或成功通知。原生控件、表格和留白差异作为视觉建议；明暗主题不可读、关键操作不可见或运行失败仍须修复。该验收允许消耗本机真实 API，但不进入 CI、发布门禁或无密钥测试，凭据、真实频道内容和模型原始响应不得提交。CI 使用确定性模型与合成页面覆盖相同状态机，真实模型“自称成功”不能替代页面、Tool/RPC、渲染和持久事实证据；

开发阶段真实模型验收创建的频道、Authoring Task、已保存本地扩展和 `.local/real-authoring-evidence/<runId>/` 截图默认保留，便于用户在同一 Host 上复查。自动化收尾不得删除、停用后移除或覆盖这些例子；只有用户明确要求清理，或测试在独立临时数据根内运行且没有复查价值时才可回收。每次运行使用新的稳定名称或 run ID，避免把旧例子修改成新结果；

## 6. 检查阶梯

本地运行最窄且足够的检查，CI 与产品交付复核保留全量门禁：

| 改动 | 默认验证 |
|---|---|
| 文档 | `pnpm check:docs` |
| 局部代码 | 对应测试与类型检查；脚本使用相关 Node 测试和脚本类型检查 |
| 公共契约、跨包行为 | 受影响消费者的测试与 `pnpm check`；跨全局边界时扩大到 `pnpm test` |
| Package 源码、Vitest 场景或覆盖率配置 | 局部运行相关测试，集成阶段执行 `pnpm test:coverage` |
| 构建、导出或 Client Slot | 相关构建与真实组装测试；发布产物变化运行 `pnpm build` |
| 用户可见 Web | 构建 Web/Server 生产入口后运行受影响的 Playwright 旅程；共享壳层/全局状态扩大路由覆盖 |
| 用户可见 UI | 同时完成 §5.1 源码与真实画面验收 |
| 产品交付复核 | `pnpm verify:product`，不删减既有截图基线、Axe 或覆盖率门禁 |
| 发布 | CI 全量检查和平台产物矩阵，见[分发契约](decisions/accepted/2026-08-21-原子产品Release与双宿主分发.md)及[发布规范](09-正式发布与更新日志规范.md) |

`pnpm test:journey` 是完整生产旅程入口。局部反馈可先运行 `pnpm --filter @nekro-nxt/web build`、`pnpm --filter @nekro-nxt/server build`，再用 `pnpm exec playwright test <受影响的 spec> --grep <场景>` 选择覆盖；选择范围必须包括变更的外部结果与失败路径，不能挑选无关通过项。代码或产物未变化时可复用本轮已经验证的生产构建。测试配置、门禁命令或检查脚本变化时，验证实际 CLI 退出码与会改变的失败行为。

根 `pnpm check` 至少包含格式检查、静态 lint、严格类型检查、文档链接/公开边界和工作区约束；`pnpm test` 运行无密钥测试；`pnpm build` 验证可发布入口。需要密钥的真实平台测试必须自跳过并由单独流程运行，凭据和原始 payload 不进入仓库；据此写回归时先改写成合成夹具。格式化、lint 和类型检查只覆盖产品源码与仓库脚本；运行数据根 `data/`、误创建的平行数据根 `apps/*/data/` 和本地分区 `.local/` 必须被忽略。智能体工作区可以包含仓库副本或任意用户文件，把它们当产品源码扫描会把运行产物误判为工程问题。检查脚本的本地相对导入必须指向 Git 已跟踪文件：`.gitignore` 只忽略 `apps/*/lib/` 与 `packages/*/lib/` 这类构建产物，不能用全局 `lib/` 把 `scripts/lib/` 源码排除出仓库；`check:gates` 会核对这一点，避免本机有文件、干净检出却缺模块。

### 6.1 本地开发服务必须仍可访问

本机已经在跑根命令 `pnpm dev`（Web `127.0.0.1:4961` 代理 Server `127.0.0.1:4960`）时，改完会触发重载的代码必须当场确认服务还活着，再结束本轮。这包括改 Server / Web 源码、workspace 包 `dist`、`contracts`、Drizzle 迁移，以及任何会被 `tsx watch --include '../../packages/*/dist/*.mjs'` 看到的产物。运行数据根 `data/` 必须通过 `--exclude '../../data/**'` 整体排除；动态导入过的 Extension 缓存也属于运行数据，安装、更新、回滚或删除它们不能被误判为 Server 源码变化并导致服务重启。

开始检查前先确认长期服务的实际所有者；本机存在 `.local/README.md` 时，从其开发与调试路由读取当前 tmux 会话、窗口和恢复流程。已有服务由 tmux 或其他持久宿主拥有时，测试、构建和临时命令会话不得替换其所有权，也不得为了避免日志干扰先停止服务。确需完整重启时，在原持久宿主中停止、等待端口释放、启动并完成下列探测；从临时执行会话启动到 200 不算恢复。

最低探测：

1. `GET http://127.0.0.1:4961/` 返回 200；
2. `GET http://127.0.0.1:4960/api/snapshot` 返回 200；
3. `GET http://127.0.0.1:4961/api/snapshot` 经过 Web 代理后同样返回 200；
4. 涉及 Web 或浏览器测试时，用真实浏览器打开正在运行的 `4961`，等待宿主数据加载和主内容可见，刷新后仍无运行异常。HTTP 200 不能证明 React 已挂载。

浏览器测试启动的 Vite 使用独立临时 `cacheDir`，关闭后清理；不能复用 Web 开发服务的 `node_modules/.vite`。不同 Vite 配置覆盖同一预构建目录，会让运行中的模块版本信息与文件失配，甚至加载两份 React。

不构成证据：

- 只看到 `tsx watch` / `vite` / `pnpm` 进程还在。watch 父进程可以空转，子进程已经退出，`4960` 不再监听；
- 只看到 Vite 首页 200。Web 活着而代理 `/api` 为 500，表示 Server 挂了，页面不可用；
- 只看到端口 `LISTEN`，没有打过 HTTP；
- 只跑过单测、类型检查或构建。

探测失败时必须读 watch 实际输出、修好启动错误（编译、迁移、端口占用），把 Server / Web 重新拉起并完成上述三个探测，不能把「进程还在」或「以后用户自己重启」当作完成。不要在同一端口再开第二套 watch。端口、数据根和 watch 行为见 `apps/server/README.md`。

检查命令应使用测试自己的临时数据根和隔离端口。若检查会清理 workspace `dist`，先完成构建，再单独运行依赖这些产物的浏览器测试，避免构建清理与测试 Server 竞争；无论命令成功或失败，结束前都要重新确认持久宿主仍拥有服务并完成三个 HTTP 探测。

## 7. 迁移与持久格式

持久格式显式版本化，由唯一所有者维护。读取未知或未来版本时拒绝并保留原始数据；迁移顺序、失败恢复、空库和重复启动行为通过合成 fixture 验证。宿主负责备份、排序、journal 和启动门禁，不把不同格式合并成一个迁移内核，也不修改 DSH 私有表。

### 7.1 统一数据根目录治理

Server 和 Desktop 使用单一明确数据根，容器为 `/data`，本地由宿主配置。顶层项必须有当前所有者、持久或缓存属性和备份恢复语义。测试使用隔离临时根；数据与智能体工作区不参与产品源码扫描。现有布局归并是有备份、迁移和恢复验证的独立任务，不在局部修改中静默移动用户数据。

具体运行布局与恢复能力由 [Server README](../apps/server/README.md) 和[宿主接线](08-接线与Server宿主设计.md)中各自的运行与 API 事实说明；Core schema 由 [storage-sqlite](../packages/storage-sqlite/README.md) 拥有。升级协调边界见[客户端状态与数据迁移](decisions/accepted/2026-08-16-客户端状态与数据迁移基础设施.md)。

### 7.2 AgentRevision 能力格式

字段、校验、版本复用与文件能力边界见[AgentRevision 能力契约](decisions/implemented/2026-08-18-AgentRevision能力格式.md)。此处不复制字段清单或默认值。

### 7.4 DSH 发布族升级

以锁定版本的公开导出和兼容测试解释当前行为。升级依赖或调查上游修复时使用 `pnpm dsh:check-update`，普通接缝修复无需例行联网查询。该命令只报告，不改文件，网络失败不阻断离线构建。

## 8. 工程风险与任务边界

重复可写状态、跨包内部导入、复制默认值或错误映射、卸载后资源残留、无消费者抽象，以及测试只断言成功，都是需要核对所有权和真实结果的信号。

这些问题由本次改动引入或会阻塞本次正确交付时，先解决最小必要范围，再继续任务。与本次独立的历史问题报告位置、影响和证据；不因看到一个征兆就要求全项目停线、画图或删除重复层。无法确定产品选择或不可逆数据处理边界时才等待用户决定，等待期间仍可继续不依赖该决定的工作。

## 9. 规则维护

项目规则记录模型无法从源码可靠推断的边界和反复出现的真实风险。能由类型、测试、lint 或脚本稳定验证的规则优先自动化，文档解释所有者、适用范围和异常处理；一般写作偏好保留为语义审稿建议，不按常用词机械阻断。

新增规则要有具体触发条件与完成标准，删除被工具或现行契约替代的重复说明。不规定固定阅读顺序、审查次数或与任务无关的报告栏目，也不因模型升级降低产品质量门禁。可复用操作在有实际重复需求、稳定步骤和当前消费者时再提炼为短指南或技能。
