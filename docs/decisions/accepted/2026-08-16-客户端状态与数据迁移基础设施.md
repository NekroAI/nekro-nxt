# 决策：客户端状态与数据迁移基础设施

状态：accepted

## 问题

NekroNxt 会持续升级 Core 数据库、DSH Session 依赖、客户端偏好与草稿、Extension Manifest 和本地源码 Revision。Desktop、Server 和 Web 如果各自处理版本升级，容易出现启动顺序不同、半迁移状态、旧客户端覆盖新数据和失败后无法恢复。

客户端 migration 不能被简化为 Drizzle 数据库 migration，也不能演变成一个能够随意修改所有数据的全局脚本系统。

## 决定

采用“格式所有者维护 migration，宿主协调升级”的结构。四条 migration lane 相互独立：

1. Core SQLite schema：由 `storage-sqlite` 拥有，通过 Drizzle migration 和 Core schema version 演进；
2. DSH Session：由锁定的 DSH persistence package 拥有，NekroNxt 只调用其公开启动/迁移接口，不访问或修改私有表；
3. Client persisted state：由 Client migration registry 拥有，处理主题、布局、未提交草稿和其他明确允许持久化的客户端状态；
4. Extension data：Manifest、源码 Revision 和构建缓存分别带格式版本；源码只向前迁移，缓存不迁移，版本不符时删除并重建。

Desktop 与 Server 使用同一个 Host upgrade coordinator。Web 客户端只迁移浏览器本地状态，不迁移 Core 或 DSH 数据。Renderer 在 Host 完成必要 migration 并发布就绪状态前不能连接业务服务。

## Client migration 契约

每个持久 namespace 使用版本信封：

```ts
interface PersistedEnvelope<T> {
  readonly format: string
  readonly version: number
  readonly data: T
}
```

- `format` 是稳定 namespace，`version` 是从 0 开始单调递增的整数；
- migration 只声明一个连续步骤 `from → from + 1`，registry 在启动时验证无重复、无缺口；
- migration 接收未知数据并负责边界校验，输出下一版本的未知数据；最终版本再由当前 schema 校验；
- 当前版本是 no-op；未来版本、未知 format 和缺失步骤必须失败，不尝试降级或猜测；
- migration 必须确定，不访问网络、时间、随机数、DOM、Core Service 或其他 namespace；
- 关键草稿迁移失败时保留原始字节并进入可导出/重置的隔离状态；主题、面板尺寸和缓存等可丢弃状态可以回到默认值，但必须记录原因；
- Local Storage 只保存小型非关键偏好；可恢复草稿使用支持事务的浏览器存储。Core 业务事实不复制到 Client 持久状态。

## 宿主升级协调

Host 在正常 Runtime 启动前执行：

```text
读取安装版本与数据版本
→ 获取单实例升级锁
→ 创建可恢复备份或快照
→ 写入 upgrade journal
→ 按 Core → DSH 公共迁移 → Extension 元数据/缓存检查执行
→ 运行启动前一致性检查
→ 原子标记完成
→ 启动 Runtime 并允许 Client 连接
```

每一步记录 migration ID、输入版本、输出版本、开始/完成状态和错误摘要。失败时不带病启动，不删除原始数据；用户可以重试、恢复备份或进入只读诊断/恢复模式。升级协调器不伪造跨 SQLite 与文件系统事务，而用 journal 和幂等恢复管理崩溃点。

数据库 downgrade 不受支持。应用回滚只能恢复升级前备份，不能让旧二进制直接读取新格式。Desktop 自动更新必须在替换当前可运行版本前确认备份与 migration preflight；Server 镜像升级使用同一数据版本检查。

## 测试与 fixture

- 每条 migration 使用冻结的旧版本 fixture，并断言输入 fixture 不被原地修改；
- 覆盖从每个仍受支持版本逐级迁移到当前版本；
- 覆盖当前版本 no-op、未知 format、未来版本、缺失步骤和重复步骤；
- 在每个 journal 崩溃点重启，结果只能是继续完成或保持可恢复失败，不能重复产生副作用；
- 迁移失败后原始关键数据保持字节一致；
- Desktop 与 Server 对同一数据 fixture 得到相同结果；
- Client migration 包保持纯函数测试，并在浏览器真实存储上增加一条组装测试。

## 备选方案

1. 只使用 Drizzle migration：无法覆盖 Client、Extension 文件和 DSH 独立存储，拒绝。
2. 一个全局 migration 目录直接修改所有数据：所有权模糊、难以独立测试和回滚，拒绝。
3. 启动时尽力读取并静默重置：会丢失草稿或把不兼容数据解释成当前事实，拒绝。
4. 从第一版支持任意 downgrade：成本高且不能保证新语义无损映射，拒绝；应用回滚使用备份恢复。

## 影响

- M0 建立最小 Client migration registry、fixture 测试和 Host upgrade coordinator 接口，但不提前创建尚无消费者的数据库表；
- 每个持久 namespace 必须声明所有者、当前版本、失败策略和 fixture；
- Electron、Server 和 Web 不各自实现业务 migration；
- 构建缓存、请求缓存和可重建索引不进入昂贵迁移，只失效重建；
- 未来多设备同步仍可基于稳定 ID 和不可变 Revision 增加，不要求改变 migration 所有权。

## 未来方向检查

关联方向：Desktop/Server 双宿主、多设备同步、社区扩展、长期升级与恢复。

保留接缝：单调格式版本、独立 namespace、不可变 Revision、升级 journal、备份恢复和 Host 就绪门禁。

本次不做：云端数据迁移、跨设备冲突合并、任意 downgrade、Extension 社区包兼容和在线 schema 协商。
