# 轮次来源固定与成员平台身份

状态：proposed（2026-11-10，待维护者选择方案）

## 提案与范围

建议先确定一轮处理的来源与恢复规则，再讨论扩展读取成员平台账号的能力。来源固定、成员身份、消息调度分别作出选择，实施时分别审查。

本提案承接 #164 的轮次来源审查意见，只提交设计文档。运行时、SDK 类型与等级、依赖版本、数据库格式和现行契约保持当前状态；原提交中的 SDK 16、产品版本映射和迁移 `0063` 均未采用。等待被拒绝仍沿用 #157 的报错与下一步提示。

## 当前事实与缺陷

`apps/server/src/turn-trigger.ts` 的 `turnTriggerOf` 读取 Episode 的 `lastAdmittedEventId`，没有时再读取 `openedAtEventId`。扩展治理的请求者判断与 `context.current().trigger` 共用该结果。工具执行期间，新消息入库并在安全间隙加入后，最新准入游标可能改变本轮的发起者。

虚构场景：成员 A 请智能体执行任务，工具执行时成员 B 插话。B 的话可以成为新的上下文，但不应令 A 发起的这一轮改用 B 的身份判断权限。这是 #156 将 `trigger` 与 `latestInbound` 分开后仍需解决的问题。

当前成员摘要提供频道成员 ID、展示名、`self` 和 `localAgent`，不提供真实平台账号。机器人账号的真实平台 ID 经 `platform.selfPlatformUserId()` 提供，受对应 Adapter 的 `platform.raw` 声明约束。定时任务、后台作业自行唤醒时，SDK 约定没有 `trigger`。这些事实的现行来源是[扩展宿主能力与生态移植](../accepted/2026-10-07-扩展宿主能力与生态移植.md)。

## 1. 固定轮次来源

候选目标是将“本轮由谁发起”与“本轮后来读到谁的消息”分开。新输入继续参与上下文；治理与扩展上下文使用同一份来源。未知来源、其他频道来源和冲突来源不获得管理员权限，也不借用最近发言成员的权限。

| 方案 | 优点 | 代价与待确认边界 |
| --- | --- | --- |
| 在真实轮次开始时保存内存来源 | 改动较小，后续注入不能替换发起者 | 需确认 DSH 公开轮次事件与准入的对应关系；进程重启后缺少来源时按未知处理 |
| 在 Admission 持久化唤醒来源，并在轮次开始时固定 | 可跨恢复保留来源，准入与来源一起验证 | Admission 与 DSH 轮次并非同一实体；多个排队输入、重试和旧记录需要规则，新增格式由存储所有者设计 |
| 从公开会话事件恢复来源，随后增量维护 | 可利用现有日志恢复，不先增加数据库字段 | 需验证日志版本与首步输入语义；缺失、冲突和历史日志不能猜测来源，恢复成本需要评估 |

建议先验证内存固定能否独立完成身份漂移修复，再决定是否增加持久来源。选择持久方案时，冷恢复所读的来源应与正常运行一致，重试不能改变已经固定的发起者。宿主通知与频道输入同时出现时，通知不授予频道成员权限；自行续作是否继承原任务发起者、继承到哪个任务结束点，需要单独定义。

待选择：固定点由轮次开始事件还是 Admission 交付事实拥有；历史记录缺少来源时的降级规则；管理员从客户端发送、内置频道控制事件、等待结束事实和动态创造分别如何确定来源。客户端管理员消息与智能体自己发出的消息继续作为不同事实。

## 2. 成员平台身份的最小能力

扩展有把频道成员映射到平台 API 参数的实际需求。先列出无法用当前 `memberId` 平台动作满足的消费者，再选择能力范围。

| 选择 | 可满足的需求 | 代价 |
| --- | --- | --- |
| 继续使用声明的平台动作与当前成员摘要 | 由宿主代为映射成员，无新增账号读取能力 | 需要为缺少的实际动作补适配器能力 |
| 获准读取当前频道成员的 `platformUserId` | 支持平台账号参数的扩展调用 | 暴露真实平台标识，需独立审查权限或明确复用 `platform.raw` 的依据 |
| 再提供同一 Connection 内跨频道稳定的 `identityId` | 支持确有需求的跨频道成员关联 | 引入新的身份概念、保存与恢复规则；当前尚未证明所有消费者都需要它 |

`platformUserId` 的读取需求与跨频道稳定身份分别决策。候选能力限定于同一 Connection，不把不同平台或连接的同名成员关联起来。查询参数使用宿主提供的成员引用；权限判断继续使用固定来源，不使用模型填写的账号或成员 ID 充当发起者。

如选择开放身份读取，实施方案需同时说明权限摘要、能力扩大后的重新批准、各工具和入站／出站处理器的独立授权、权限撤销后停止读取、恢复后重新核对授权，以及动态试运行的模拟身份边界。平台未提供映射时返回不可用，不生成可冒充真实账号的替代值。SDK 等级、兼容策略和产品版本映射由维护者选择，不预定为 SDK 16 或特定产品版本。

## 3. 后台任务期间的新消息

来源固定本身不要求把新消息全部排队。当前边界要求工具期间新消息可靠入库，在安全间隙加入，普通消息不取消工具。

候选一是保持安全间隙注入：后台任务继续以自己的来源运行，新成员输入不改变它的权限，响应延迟较小；需要明确本轮如何承担新增消息的回应义务。候选二是后台任务期间入库后排队，当前轮结束再处理：来源边界更直观，但长任务会延迟频道回复，属于响应时机变化。

若选择排队，需要先决定适用任务范围、最长等待与长任务反馈。两种方案都需要验证强信号、中信号、`replyRequired` 和多成员回应义务；不能仅以来源固定成功来证明消息响应行为正确。

## 4. 已交付唤醒与积压补收

当前 `ChannelRuntime.#candidateTriggeredEvents` 在旧唤醒的消息已交付时仍返回尚未准入的候选消息。原提交改为返回空，让新候选等待自己的唤醒，改变了原有的补收行为。

需要分别回答两个问题：旧唤醒不能把自己的发起者授予后来消息；后来消息仍应按原响应方式被收入，或有明确的新调度规则。虚构场景中，B 的排队唤醒已经随上一轮交付，之后 C 的消息到来；B 的旧队列项不能将 C 的任务标成 B 发起，C 也不应永久积压。普通上下文消息不一定有独立唤醒，直接返回空可能改变它们被补收的时间。

待选择：保留补收但重新确定新轮来源，还是消费旧唤醒后由独立调度处理积压。补收与来源固定应有各自的测试与提交，避免隐含改变触发规则。

## 5. 恢复与读取成本

从会话日志恢复来源时，若每次 `context.current()` 和每一步开始都从头扫描，成本会随日志增长。验证样本应使用合成的大会话，覆盖数十万规模上下文，记录日志事件数和重复查询次数，不使用真实聊天。

候选方案是冷启动时恢复一次，之后由所属会话生命周期增量维护来源；或读取持久化的来源记录。缓存需有唯一所有者，并在切换轮次、会话关闭和恢复失败时清理。持久方案需说明旧记录读取、失败恢复和索引归属。选型前比较首轮恢复耗时与后续查询成本，避免在常用读取路径反复全量扫描。

## 6. 保留等待拒绝行为

等待结束开启的新一轮继续承担回复义务，再次等待时保留报错“这一轮是等待结束后开始的，不能再等，现在就回复。”其他拒绝原因继续说明发生了什么以及下一步。

本提案不采用静默转换为 `no-response-needed` 的处理。来源或调度修复也不代替智能体结束这一轮，否则等待对象可能收不到回复。当前行为入口见[响应时机与智能响应](../accepted/2026-10-31-响应时机与智能响应.md)和 `finish_channel_turn`。

## 后续实施与验证

维护者选择方案后，按以下边界提交实现：

1. 固定轮次来源与请求者判断；验证 A 发起、B 注入，未知与外频道来源，客户端管理员消息、内置频道控制事件、等待结束和自行唤醒。
2. 如选择持久来源，独立提交格式与恢复；验证空库、旧记录、崩溃重试、多个排队输入、混合宿主通知和会话恢复，并测量合成大会话的读取成本。
3. 如选择成员身份能力，独立提交 SDK、权限摘要与全部消费者；验证最小权限、处理器隔离、撤销与恢复、跨频道范围和动态试运行。
4. 如选择改变后台消息或补收调度，独立提交行为与对应现行契约；验证回应义务、长任务延迟、积压不饿死、工具不中断和 #157 等待拒绝行为。

每一步保留依赖版本；按实际改动运行 Windows 与 Linux 的相关检查。SDK 能力交付清单沿用[扩展宿主能力与生态移植](../accepted/2026-10-07-扩展宿主能力与生态移植.md)的实现交付要求。
