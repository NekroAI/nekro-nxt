# 正式发布与更新日志规范

## 1. 文件分工

正式版更新内容写在[当前更新内容](releases/current.md)。它只保存每个版本会变化的说明和本次需要的配图，发布脚本负责转换图片地址，并补齐版本号、Tag、下载地址、服务端镜像、DSH 版本、Release ID、Commit、许可证、安装文档、贡献者、完整变更和社区入口。

准备下一版时，从[更新内容模板](releases/template.md)复制结构并覆盖 `current.md`。GitHub Release 保存已经发布的最终正文，仓库 Git 历史保存旧版 `current.md`，不再为每个版本复制一份内容相同的 Markdown。

## 2. 用户审查是发布门禁

更新内容必须由用户逐段审查并明确同意后才能发布。测试通过、Preview 发布成功、文案检查无错误或 AI 自己复核，都不能代替用户审查。

AI 可以起草和修改 `current.md`，但不能自行宣告文案已经通过。用户没有明确同意当前文件内容时，禁止运行 `pnpm release <版本>`、创建正式版 Tag 或触发正式发布。用户要求继续改文案后，之前的同意失效；修改后的全文需要重新审查。

`pnpm release <版本>` 会显示指定版本、Commit 和完整更新内容，并要求在交互终端中再次输入同一个版本号。该确认只用于防止误操作，不能替代发布前的用户审查。

## 3. 更新内容怎么写

先写用户能观察到的变化。每一条说明对象、改了什么、使用时有什么结果。实现细节只有在它会影响安装、兼容、数据或操作方式时才进入正文。

可以按“主要变化”“改进和修复”“使用前留意”组织，但不强求每次凑齐三个小节。改动少时，一段正文加几条列表更自然。

更新内容遵循[术语与文案规范](01-术语与文案规范.md)，并额外遵守以下规则：

- 使用 `NekroNXT`、`DSH`、智能体、频道、平台连接和扩展等项目现行术语；
- 写具体行为，少用“全面升级”“重磅更新”“体验焕新”“更智能”“更强大”等宣传词；
- 不用“首先、其次、最后”串起整篇，也不为显得完整而堆出三项排比；
- 不写“不是……而是……”“不仅……还……”等刻意制造转折的句式；
- 不复述 Commit 列表，不把内部类型名和函数名改写成用户价值；
- 同类修复合并描述，保留用户需要知道的对象和结果；
- 已知限制直说触发条件和影响，不写含糊的风险声明；
- 没有可靠证据的性能、兼容范围、平台支持和稳定性结论不进入更新日志。

`current.md` 不得写版本号、Tag、下载或文档链接、Docker 镜像地址、DSH 版本、Release ID、Commit、SHA-256 和许可证。这些固定信息由 Tag 触发的 CI 从真实产物与 Product Release 自动生成。

某个版本需要配图时，将图片放入 `assets/brand/release-images/current/`，并在 `current.md` 中使用对应的仓库相对地址。CI 将本次引用转换为发布 Commit 对应的不可变图片地址；开始准备下一版本后清理或替换整个 `current/`。截图使用虚构数据并清除图片元数据。

CI 从本次发布的 Git 提交范围生成贡献者名单。存在上一个正式 Tag 时，完整变更链接比较两个正式版本；首个正式版本链接到当前 Tag 的完整提交记录。机器人账号不进入贡献者名单。

## 4. 发布命令

正式发布使用显式版本：

```bash
pnpm release 0.1.0
```

脚本验证以下条件后才允许推送不可移动的 `v0.1.0` Tag：

- 参数是无 `v`、无预发布后缀的 `X.Y.Z`；
- 参数与根 `package.json#version` 完全一致；
- 当前分支是 `main`，worktree 干净，`HEAD` 等于 `origin/main`；
- 移动的 `preview` Tag 已经指向同一提交，证明完整 CI、产品旅程和 Preview 产物已通过；
- `current.md` 已移除模板注释、占位符、版本号和固定发布信息；
- 目标 Tag 与 GitHub Release 尚未存在；
- 操作者阅读命令打印的更新内容，并输入同一个版本号确认。

Tag 推送后，[正式发布工作流](../.github/workflows/release.yml)构建 macOS arm64、macOS x64、Windows x64、Linux x64 和 Server 候选。最终任务核对四个客户端的 receipt、文件大小和 SHA-256，生成完整 Release 正文，发布版本镜像和 `latest` 镜像。公开 Release 不附带内部 receipt。

正式 Tag 不得移动。在线构建发生临时错误时重跑同一工作流；源码需要修改时更新根版本，再发布新的 SemVer。
