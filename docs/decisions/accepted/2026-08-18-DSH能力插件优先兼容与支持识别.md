# 已接受：DSH 能力插件优先兼容与加载目录

状态：accepted

## 背景

NekroNXT 以 DSH 为核心引擎，自身体量不足以要求 DSH 插件作者同时维护 NekroNXT 专用适配。如果普通 DSH 能力插件必须额外声明 NekroNXT Contribution、重写配置表单或实现产品专用接口才能使用，NekroNXT 会形成规模更小且与上游分离的插件生态，也会在 DSH 快速演进期间承担逐插件追赶成本。

DSH `0.1.1-rc.2` 已提供 Plugin、Service、Tool、Provider、Settings、Credentials、Scope、Bundle、Preset 和 Client Slot 等公开接缝。其 Settings descriptor 会给配置界面提供脱敏值、分层值、revision 和序列化 Schemastery schema；但当前官方插件配置页仍包含手写卡片与 Host namespace 白名单，不能据此宣称任意插件已经自动获得界面。

## 决定

面向 DSH 本身能力扩展的插件，以不需要任何 NekroNXT 专用适配即可加载、配置和调用为默认目标。NekroNXT 专用元数据、中文文案、产品化表单、风险说明、费用说明和 Client UI 只能增强体验，不能成为 DSH 能力插件进入系统的必要条件。

“尽可能兼容”不是宣称兼容所有 DSH 软件表面。默认优先覆盖使用公开 Host 与模型能力接缝的插件，包括 Tool、Provider、Service、Settings、Scope、Bundle 和 Preset。只扩展 DSH 官方浏览器壳、依赖官方页面结构或私有 Host API 的界面插件不在完整兼容承诺内；插件同时具有 Host 能力和 DSH Client UI 时，Host 能力与 Client UI 分别产生真实加载结果，原生界面失败时回退通用配置。

NekroNXT 特有的 Connection、Channel、Binding、Asset 和可靠投递仍需要对应产品 Contribution，因为这些是 DSH 没有定义的领域语义。缺少 `AdapterContribution` 只表示插件不能自动成为聊天平台连接，不影响其作为普通 DSH 能力插件被识别和运行。

## 零适配配置路径

注册 DSH Settings namespace 的存活插件自动进入通用配置目录，不要求 NekroNXT 元数据。Host 从 `ctx.settings.describe({ redactSecrets: true })` 投影 namespace、schema、resolved/base/user 分层值、revision、应用时机与 secret 位置；Web 按序列化 Schemastery schema 渲染基础字符串、数字、布尔、枚举、集合和对象字段。

`secret` 与 `credential-ref` 角色必须自动走只写或引用式凭据控件，响应不回传值。保存使用路径级 `settings.mutate()` 和 `expectedRevision`，提交后重新读取 Host 接受的结果；不得从脱敏快照重建整个 section，也不得建立第二套插件设置持久层。

Schema 缺少产品文案时，通用界面允许显示稳定字段名和技术说明。NekroNXT 可以为高频插件维护可选的展示覆盖或专用流程，但删除这些覆盖后基础配置仍应可完成。模型发现、OAuth、二维码、平台 Connection 创建等超出普通 Settings 字段的流程可以使用专用 UI，同时保持 DSH 或 NekroNXT 各自的权威配置源。

只有 Cordis Plugin `Config`、没有 DSH Settings namespace 的插件仍可由 Host 组合加载，但不能被虚假描述为支持在线用户配置。普通启动 Config 的持久修改、Fiber 更新、依赖拓扑重建和失败回滚应等待复用 DSH 公开 Loader/Profile 接缝；在此之前不自研平行 Loader。

## Host 加载路径

当前生产 `DshHostRuntime` 仍以代码直接组合固定 roster，尚无任意 DSH 包的安装与加载入口；因此本决定是后续兼容实现的约束，不把“依赖已经出现在 lockfile”冒充通用插件支持。

开放用户安装或启用 DSH 能力插件前，必须先对当前锁定版本的公开 Loader、Profile、Bundle 与作用域组合做兼容 Spike，验证能否在保留 NekroNXT Channel Session setup、每智能体 Revision 授权、私有 Host Service 和静止卸载语义的前提下，叠加一个用户插件层。优先让 DSH 自己的 Loader 拥有模块解析、配置校验、Fiber 状态与重载；NekroNXT 只持有安装来源、用户选择、真实加载诊断和产品授权。

Spike 至少覆盖 Host 单例插件、每 Session/Preset 插件、Settings 注册、Tool/Provider 注册、加载失败回滚、配置变更、冷重启恢复和 dispose。若公开 Loader/Profile 无法与当前 Host 边界可靠组合，才允许设计最薄的 `context.plugin()` 兼容装配器；该装配器仍直接消费 DSH 插件公开入口与 Config，不发明 NekroNXT 专用插件格式，也不得复制 Loader 的解析、依赖图或热重载实现。

## 来源与加载诊断

NekroNXT 的产品界面展示插件来源和真实加载结果，不把开发验收、外部服务调用或配置状态转换成插件评级：

- 固定随 NekroNXT Host 装载的 DSH 包统一标记为“内置”；
- 未来通过 Profile 或 Loader 由用户安装的 DSH 包标明“用户安装”等实际来源；
- 缺少依赖、版本冲突、公开协议不匹配、激活失败或无法静止卸载时显示对应加载错误；
- API Key、Base URL、网络、配额和第三方服务故障进入配置或运行诊断，不改变插件来源；
- 真实组装、外部结果和 UI 渲染证据属于开发与发布门禁，不在普通设置页形成“已验证”“未完整验证”或“部分支持”等标签。

Host 从当前固定 roster 和实时 Settings 注册投影包名、版本、来源及 namespace。namespace 必须归入实际内置包；无法匹配固定 roster 的实时注册项作为“其他扩展”显示，不能称为“未评估归属”。真实加载失败通过 Server 启动或 Loader 错误直接暴露，不能用人工布尔值替代。

未来开放用户安装时，Loader 在执行第三方代码前读取公开 package metadata、exports、peer dependency、DSH client metadata 与版本范围；加载后观察 Tool、Provider、Settings、Slot 等注册，并在 dispose 后确认撤销。会执行第三方代码的探测使用与目标 RuntimeKind 相符的受控环境，不能把进程内隔离宣称为安全沙箱。

## DSH Client UI

插件已经提供 DSH 公共 Client Slot contribution 且所需 Client Runtime/Remote 接缝可安全组合时，NekroNXT 应优先考虑原样承载，避免要求插件作者重写界面。当前不为复用少量官方手写卡片而搬入完整 DSH Web App，也不模拟私有页面结构；没有原生 UI 时，Settings schema 通用表单是零适配 fallback。原生界面失败时显示真实错误并切回通用表单，不改变插件来源标签。

配置界面采用双轨：任意可安全上线的 Settings namespace 自动获得 Schemastery 通用表单；已验证的公开 `dsh.client`/Client Slot 组合可以优先显示“DSH 原生界面”。两条轨道读取和写入同一 DSH Settings/Credentials，不复制配置。原生界面失败时由独立 Error Boundary 和运行时诊断切回通用表单，不能拖垮设置页。

原生界面通过唯一兼容岛映射公开 `--dsw-*` Token；不加载完整 DSH Web 壳或全局 Theme，不覆盖 CSS Modules 哈希类、私有 DOM 和 `body`。兼容岛外的入口、状态、警示、错误和 fallback 使用 NekroNXT 文案；岛内可保留上游原文，术语例外不得扩散。

DSH SlotRegistry 的公开契约只允许 Host 直接渲染 `root`，子 Slot 必须由 root registrant 收到的 `renderSlot` face 向下组合。动态创造 package 和原生设置都拥有 root 表面，不能在一个 SlotRegistry 中同时作为两个产品渲染座位。当前实现因此共享唯一 ClientModuleSystem/模块表，但为动态创造与原生设置建立两个独立 Cordis Context/SlotRegistry；模块加载事实仍单一，Slot 生命周期按产品表面隔离。这是公开 API 约束下的最小边界，不调用私有 Slot 实现。

Client Bridge 只实现官方设置 fixture 实际需要的 settings describe/mutate、credentials describe/set/unset，以及对应 remote invalidation。未知 Remote 明确失败为 unsupported，不挂载或伪装完整 `dsh-host-apiproxy`。第三方 Client bundle 是同进程可执行代码，原生承载不宣称为安全沙箱。

## 智能体自扩展说明书

`cordis-plugin-development` 这个名称只用于兼容 DSH Cordis 固定 Prompt；其 provider 是 `nekro-nxt-runtime`，正文明确要求开发 NekroNXT Extension，而不是 DSH 官方 WebUI 页面。根 Context 挂载 DSH `SkillRegistry`，只有获得动态创造授权的智能体 scope 注册该 Skill 并挂载 Tool Skill。动态 Package 执行 Context 隔离 `skills` Service，因此代码只能消费说明书结果，不能直接读取或篡改 Skill Registry。

说明书、Host Inspect 的 `supportedContributions` / `developmentExample` / `extensionLifecycle` 和契约测试共同读取 `@nekro-nxt/extension-sdk` 的 `NEKRO_NXT_EXTENSION_AUTHORING_REFERENCE`。当前 Client 自扩展面只公布 `agent.workbench.sections` 与 `extension.details.panels`；DSH API catalog 中的官方页面 Slot、`root` 和其他未声明 Slot 不进入产品自扩展能力面。

## 当前落实与 Spike 结论

当前固定生产 roster 提供包身份、版本、来源和实时 Settings namespace 目录，Settings/Credentials 通用 API 和 Schema 表单已以 `web-search-deepseek` 形成真实闭环；网页搜索配置入口为“设置 → DSH 扩展 → DeepSeek 网页搜索”，智能体页开关只控制该智能体授权。未配置凭据时可以先授权并显示等待配置，新建智能体不会默认选择不可用网页搜索。

DSH 0.1.1-rc.2 的 Secret redactor 只覆盖 object/dict/array，且序列化 schema 可能携带 Secret default。Host 会在 descriptor 上线前做结构化 fail-closed 检查；不能证明安全的 namespace 不进入通用配置 API，未知/Secret 子树也禁止整体 JSON 替换。该限制等待上游完备线协议，不能用提示词或前端隐藏代替。

Loader/Profile Spike 通过了公开 Loader create/update/remove、失败激活回滚、官方 inventory 与隔离 Context；Profile patch 能描述插件树，但不包含智能体配置版本、频道或 NekroNXT 私有 Service 授权语义。故本轮明确不开放已安装包的用户启用入口，也不展示占位按钮；固定 roster 不迁移到 Host 全局用户 Loader。只有补齐 Session/Preset 分层、配置更新、冷重启恢复、所有贡献撤销和 Server admission/drain/dispose 后，才重新评估生产用户插件层。

## 实施顺序

1. 建立只读插件目录，投影当前固定 roster 的包身份、版本、来源和实时 Settings namespace；
2. 建立 DSH Settings 通用目录、脱敏 API 和基础 Schema renderer，以 `web-search-deepseek` 作为首个真实消费者；
3. 完成 DSH Loader/Profile 用户插件层 Spike，不通过时保留当前固定 roster，不先开放安装入口；
4. 增加受控兼容探测器，覆盖公开入口、Service 注入、注册贡献和 dispose 静止，结果只进入开发门禁和用户安装时的加载诊断；
5. 让安装或启用入口消费 Loader 的真实结果，明确展示缺失依赖与加载错误，不维护人工支持评级；
6. 评估公共 DSH Client Slot 的兼容承载；只有真实插件消费者出现后才扩大 Client Runtime roster；
7. 普通 Cordis Config 的在线编辑等待 DSH Loader/Profile 接入，不与 Settings renderer 混为一套机制。

每阶段都必须先用当前已安装 DSH 包形成兼容 fixture，并在升级 DSH 时作为回归门禁。支持识别 API、缓存格式或持久记录若需要公开，另行版本化；本决定不提前固定其 JSON schema 或数据库表。

## 未来方向与参考取舍

关联方向：DSH 能力生态、更多 Tool/Provider、社区扩展、Process/Remote Runtime、通用设置界面和智能体自开发。

保留接缝：DSH 公开 Plugin/Service/Tool/Provider/Settings/Credentials/Scope/Bundle/Preset/Client Slot、Cordis 可逆 effect、Host Service 清单和 Loader 加载诊断。NekroNXT 展示覆盖是可删除增强，因此不会锁死插件作者或形成第二套必选生态。

本次明确不提前实现：社区市场、自动安装任意 npm 包、完整 DSH Web App、任意 Loader Config 在线编辑、对未知第三方代码的 in-process 安全承诺和所有 DSH 界面插件兼容。

参考 DSH 0.1.1-rc.2 的公开 Settings descriptor、Credentials、Cordis 生命周期、Bundle/Profile 和 Client Slot；借鉴其公开能力接缝、分层设置、secret 脱敏和可逆注册，拒绝照搬官方页面硬编码卡片与 namespace 白名单，也拒绝要求 DSH 插件专门声明 NekroNXT 元数据才能使用。
