# 原子产品 Release 与双宿主分发

状态：accepted

## 问题

NekroNxt 把 UI、Host、DSH Runtime、Extension Runtime、双 SQLite 和用户本地资源完整部署到用户设备，不存在由平台方先行升级并持续保持最新的中心后端。若 Desktop 独立投放 Web UI，或允许 UI、Host、DSH 和 migration 使用不同版本，旧实例会出现客户端契约不匹配、插件 Client/Host Bridge 分裂和旧二进制读取新数据等不可恢复组合。

Desktop 与 Server 又必须复用同一 Runtime、数据格式和 Web UI，不能各自形成一套发布与迁移实现。

## 决定

NekroNxt 的最小发布单位是原子的 Product Release。每个 Release 同时包含：

- Web UI 生产构建；
- Server Host 与领域 API；
- 锁定版本的 DSH Host/Client 组合；
- Extension Host/Client Bridge、SDK 与 Builder；
- 当前格式所有者的 migration 与升级前检查。

Product Release 使用单一 `releaseId = <产品版本>+<commit 前 12 位>`。Desktop 只启动当前安装包内的 Server 生产入口，并只加载该 Host 同包托管的 Web dist；Host readiness 必须返回相同 `releaseId`。Server 镜像同样把 Server、Web dist 和完整生产依赖构建为一个镜像，不从运行容器执行 `git pull`。

不提供 UI、Host、DSH 或 Extension Runtime 的独立产品更新，也不建立远程 UI 资源投放通道。用户保存的 Extension Revision、Activation、Asset、Credential 和工作区是数据，不并入程序 Release；构建缓存可以按版本失效重建。

## Desktop

Electron 只拥有窗口、单实例、外部链接、系统能力和本地 Host 进程生命周期。Host 在隔离 utility process 中运行；每次 Desktop 运行只分配一个随机 loopback 端口，异常退出后的替代进程继续使用同一 Origin，并受有界退避和滚动崩溃预算约束。Renderer 保持 `contextIsolation: true`、`nodeIntegration: false` 和 `sandbox: true`，直接消费 Host 同源 HTTP/SSE；Host 恢复后由 `EventSource` 重连和权威投影对账恢复页面，不重新加载 BrowserWindow。Desktop 退出会取消恢复任务，并等待 Host 子进程静止。

当前未获得平台证书，因此只产出未签名完整安装包并采用手动完整包更新：Windows x64 NSIS、macOS Universal DMG、Linux x64 AppImage。未来平台签名只改变分发可信度和完整包替换方式，不改变 Product Release 原子边界。

Desktop 只有 `preview` 和 `stable` 两个发行通道，不设置 beta。两者使用独立 appId、Windows NSIS GUID、产品名、可执行文件名和 Electron `userData/data/`，可以同时安装且默认不共享数据库：

- stable：`ai.nekro.nxt`、`2BED256D-E4EA-4EA9-B730-6B63FF416CE8`、`NekroNxt`；
- preview：`ai.nekro.nxt.preview`、`D4FFCCE1-474A-47FC-819B-DA8E5BF5378C`、`NekroNxt Preview`。

仓库根 `package.json#version` 是唯一手工版本源，必须是无预发布后缀的 `X.Y.Z`。stable Release 直接使用 `X.Y.Z`；preview Release 确定性派生为 `X.Y.Z-preview.<commit Unix 秒>`。公开 stable 制品的 `vX.Y.Z` Git tag 必须指向 receipt 记录的 commit。每个平台制品生成包含 channel、版本、commit、大小和 SHA-256 的 receipt；本地构建命令只生成文件，不隐式上传。

`main` 的 push 在完整 CI 通过后分别在 macOS、Windows 与 Linux 原生 GitHub runner 构建 Preview。平台 job 把版本化安装包与 receipt 直接上传到固定 `preview` tag 对应的滚动 Prerelease，不把客户端作为 Actions Artifact 分发。最终发布 job 验证三端附件、receipt 与 Product Release commit 一致，并再次确认候选 commit 仍是远端 `main` 最新 HEAD；满足条件后强制前移可移动的 `preview` tag、更新 Prerelease 身份并删除上一版附件。失败或已被更新 commit 超越的构建只删除自己的候选附件，上一版完整 Preview 保持可下载。`preview` 是唯一允许移动的发布 tag；正式 `vX.Y.Z` tag 永久不可移动。

版本修订遵循 SemVer：兼容性修复递增 patch；新增用户能力或向前迁移递增 minor；公开契约、部署边界或数据恢复语义发生有意破坏时递增 major。发布下一个正式版本前先修改根版本，再从该版本构建任意数量 preview，最后从选定 commit 构建 stable；不得通过修改 Desktop 子包版本制造第二版本源。

## Server

Server 使用 glibc 系 Node 运行镜像、非 root 用户、单一 `/data` 和同包 Web dist。容器启动同一个生产 Server 入口并显式监听 `0.0.0.0`；当前 HTTP Host 在 Runtime 完整恢复后同时发布 liveness 与 readiness，Desktop 和容器都以 readiness 作为可用门禁。镜像构建拒绝脏工作树，版本与 Desktop Product Release 使用同一产品版本和 commit 身份。

## 升级与恢复

正常 Runtime 打开数据库前，宿主必须读取安装 Release 与数据 Release，获取单实例升级锁，并在任何 migration 前创建恢复点。Core、DSH、Client 和 Extension 仍由各格式所有者迁移；宿主只负责顺序、journal、备份、失败恢复和 ready 门禁。

代码 downgrade 不受支持。新 Release migration 失败时，不能让旧二进制读取已经前移的数据；回退程序必须同时恢复升级前备份。DSH Session schema 没有公开迁移路径时，升级入口只能继续使用旧 DSH、拒绝升级，或执行产品明确实现的一致性归档与新库重建；禁止修改 DSH 私有表。当前 schema 15 → 17 路径先归档旧库并关闭引用旧 Session 的 Episode，再由 rc.2 创建 schema 17 新库；未知格式仍在 preflight 阶段拒绝。

当前实验首先验证同一 Server 入口、同包 Web dist、releaseId 握手、生产容器和 migration 前 SQLite 恢复点。完整数据根备份、自动恢复交互、平台签名、整包自动替换、跨设备同步和社区插件分发不在本实验中实现。

## 影响

- `apps/desktop` 是 Product Release 的 Desktop 宿主，不是远程平台客户端；
- `apps/server` 同时提供可由 `node` 启动的生产入口和 Desktop 可启动的无副作用入口；
- Web 只面向当前 Host 契约构建，不维护跨任意历史 Host 的在线协商层；
- Desktop 与 Server 对同一旧数据 fixture 必须得到相同升级结果；
- 产品 Release 签名与未来社区 Extension 供应链是不同问题，本决定不提前建设社区签名或市场。

## 未来方向检查

关联方向：Desktop/Server 双宿主、多设备同步、社区扩展、远程管理与长期升级。

保留接缝：单一 Product Release 身份、稳定数据根、格式所有者 migration、不可变 Extension Revision、Host ready 门禁和完整包替换。

避免的锁死：不把 Desktop 做成中心平台薄客户端；不允许 UI/Host 混搭；不把 Electron IPC 变成第二套领域 API；不让程序 Release 覆盖用户扩展与数据。
