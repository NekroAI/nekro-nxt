# NekroNxt 开发与测试规范

> 文档性质：开发者和 AI 编码工具共同遵循的公共工程规范
>
> 目标：让每次改动保持边界清楚、证据充分、可以回退，避免随着智能体参与开发而积累重复抽象、隐式状态和不可验证行为

## 1. 知识与决策

每个事实只有一个权威来源。产品铁律放在根 `AGENTS.md`，专题协议放在编号文档，跨包决定放在 `docs/decisions/`，包的当前职责放在包 README。现行文档只描述当前为真的规则，使用现在时；过程、纠错和否决理由进入 `docs/archive/` 或 Git，默认不读，也不是现行权威。

冲突按以下顺序处理：用户最新明确决定 → 现行 accepted/implemented Decision → `AGENTS.md` → 编号协议 → 包 README。发现冲突时修正失真的副本或改为链接，不保留两份独立长描述。

Decision 状态含义：

- `proposed`：仍需选择或关键证据；
- `accepted`：设计已经确认，代码可以尚未落地；
- `implemented`：代码与验证证据已经落实，正文保持与当前实现一致；
- `rejected`：明确拒绝；只有仍能阻止现实诱惑时才留在 `decisions/rejected/`，否则迁入 `docs/archive/`。

改变公共协议、跨包职责、持久格式、DSH 集成、Extension/Adapter 生命周期或测试策略时，必须新增或更新 Decision Note。落地后重写为现行契约，不要用“后续说明”打补丁。机械修改和局部修复不需要制造记录。

### 1.1 文档自维护

实现者（包括 AI）在改代码的同一轮维护现行文档，不等到单独的“补文档”任务。

| 改了什么 | 更新哪里 |
|---|---|
| 产品铁律、术语、绑定或消息出口 | 根 `AGENTS.md`；术语细则在 `01` |
| 用户路径、页面对象、按钮后果、未开放主操作 | `NekroNxt界面交互模型.md`；用户路径在产品形态 |
| 消息、投递、媒体、通信工具 | `03` 与该主题现行 Decision |
| 一期缺口或完成标准 | `04` |
| 视觉 Token、布局、动效 | `05` |
| 用户可见界面的像素级验收 | `06` §5.1 |
| 工程纪律、测试、数据根、文档规则、提交说明 | `06` |
| 尚未启动的方向或禁止锁死的接缝 | `02` |
| Server↔Web 路由与宿主接线 | `08` |
| 包职责、消费者、现行语义 | 该包 README |
| 已确认但未落地，或已落地的跨包契约 | `docs/decisions/accepted/` 或 `implemented/` |

怎么改：

1. 先找到该事实现在的唯一权威源，在那里用现在时重写；
2. 其他文件只保留链接或一句指向，删除过期复述；
3. 决策落地后重写 Decision 正文，使路径、符号和默认值与代码一致；
4. 正文不再指导实现时，整份迁入 `docs/archive/`，文首标明冻结，现行层停止链接它作为依据；
5. 发现现行文档仍在教已否决模型、未实现能力或过期路径时，当作缺陷一并修复。

不要做：

- 在现行文档追加变更史、选项对比或“当时/不再/曾错误实现”；
- 为一次实现写 M0–M7 日记，或把验收过程写进 `implemented/`；
- 把未开放能力画进现行按钮表，又不标“未开放”；
- 只改代码或只改文档的一半，使两者互相否定。

### 1.2 提交说明

提交说明使用中文，一行主题，与仓库历史一致：

```text
类型: 动词短语
```

- 类型用 `feat`、`fix`、`refactor`、`docs`、`test`、`merge`；CI 或单包可用 `fix(ci)`、`feat(web)` 这种范围；
- 冒号后是现在时中文动词短语，说明做了什么，例如 `接入`、`分离`、`恢复`、`约定`、`忽略`；
- 不写英文长句、不写 Conventional Commit 英文描述、不加正文堆砌过程；必要时用括号补范围，例如 `docs: 注明创造工作台已接入真实 Host`；
- 一个提交只表达一件能独立理解的事；文档自维护随对应实现提交，不为“补文档”单独制造空提交，除非本轮只有文档变化。

## 2. 实现工作流

```text
读取最近的 AGENTS 与包 README
→ 搜索现有类型、测试和 Decision
→ 核对相关未来接缝与 DSH 当前公开契约
→ 写下最小方案、当前消费者和明确非目标
→ 修改最小拥有范围
→ 用现在时重写该事实的唯一现行文档
→ 用最窄检查形成反馈
→ 验证真实入口和外部结果
→ 用户可见 UI 时完成真实渲染画面的视觉验收（§5.1）
→ 本机已有 `pnpm dev` 时确认开发服务仍可访问（§6.1）
→ 汇报证据、取舍和遗留风险
```

不得只根据文档想象代码，也不得只根据代码覆盖已确认的产品决定。改完代码却不改权威文档，或只追加变更史，都视为未完成。外部项目只提供机制和失败经验；接入前核对当前源码、导出和测试，不依赖相邻仓库、浮动 dist-tag 或私有实现路径。

## 3. 包与代码边界

- 安装代价较小、安全与维护风险较低、且在同类问题中属于主流选择的框架或库，直接引入并在现行文档写明选型；禁止为了少一个依赖或“更可控”而手写拖拽、虚拟列表、富文本、日期解析等同等复杂度的交互或算法内核；
- 每个包必须有当前职责、当前消费者和独立验证价值；不得为了未来可能复用而创建空包、空接口或无消费者的状态机；
- 包之间只通过公开导出、Service、事件或 Contribution 交互，不跨包导入 `src/internal`、读取对方数据库或共享可变单例；
- Core 保存产品事实，DSH 保存自身 Session 事实，Client store 只保存交互状态；同一业务事实不得同时复制到 Runtime、Zustand 和请求缓存；
- 外部输入、配置、持久数据、模型工具 JSON、进程和网络边界必须运行时校验；同进程的已类型化内部调用信任 TypeScript，不堆重复校验和兜底；
- 跨持久或进程边界的 ID 使用不透明类型，不把普通 `string` 当作所有身份；
- 可扩展联合保留明确 discriminant；封闭联合使用穷尽检查，开放联合保留有说明的默认路径；
- 配置默认值在所属实现的一处显式解析，不能散落 `?? default`；错误配置在最早可判定点失败，不静默跳过；
- 注释和 JSDoc 说明非显然的行为、失败、时序、所有权和兼容承诺，不复述代码或保留推理过程。

任何新增抽象都应能回答：“谁拥有它、谁现在使用它、删除它会破坏哪条测试？”无法回答时先不引入。

## 4. 生命周期与并发

- Cordis 注册、监听器、计时器、Slot 和 Tool 都是可撤销 effect；卸载测试必须观察它们全部消失；
- 一个异步操作只有一个生命周期所有者或事务控制器；取消、完成、回滚和释放由同一处收敛；
- dispose 不只发出 abort/kill，还要等待子任务停止并让系统达到静止；先关闭通知入口，再终止可能产生迟到回调的工作；
- 状态和事件只在真实提交点发布；数据库或外部操作失败时不能先让 UI、缓存或下游看到成功；
- 独立结果独立表达，例如 `timedOut`、`exitCode`、`signal`、`partial`、`unknown`，不能用一个布尔值覆盖多个事实；
- 用户或 Extension 回调的异常由调度器隔离和记录，不能阻断同批其他回调或 Core 生命周期；
- 并发测试优先使用 Fake Clock、受控 Promise 和显式 checkpoint，不使用依赖机器速度的长时间 sleep。

涉及消息、工具执行、恢复、迁移和 Extension 卸载时，必须在实现前列出崩溃点、重复输入、乱序、取消和部分成功路径。

## 5. 测试设计

测试分为四层，按改动风险选择最窄且足够的组合：

1. **单元/领域测试**：验证纯逻辑、边界值、错误路径、事件顺序和状态机；
2. **契约场景测试**：用 Fake Adapter、Fake Gateway、Fake Clock 或临时数据库验证跨组件行为；
3. **真实组装测试**：通过实际 Bundle、Loader、公开 package entry 和构建产物启动，外部网络或模型可以替换为可控实现；
4. **产品旅程测试**：驱动真实页面验证用户可见闭环、平台行为和升级恢复；仓库默认入口是 `pnpm test:journey`。

用户可见的布局、样式、路由、客户端状态或渲染数据发生变化时，在上述测试之外还必须完成 §5.1 视觉验收。视觉验收不是第五层可跳过的自动化，而是与四层测试同级的完成条件。

通用规则：

- 仓库内夹具、原型和示例只使用虚构发送者、标题、群名、文件名和 `*.test` 主机。真实入站 dump、个人昵称、群 OpenID、平台临时 CDN、`rkey` 和文件内容哈希不得进入 Git；需要覆盖拍扁协议时，用合成文本复现标记，不粘贴一次真实消息。真实账号旅程在本机运行，原始 payload 不入库。公开边界见 `00-文档公开边界.md`；
- 只 mock 昂贵、不可控或非确定性的边界，边界之后尽量使用真实实现；
- 验证外部世界，不相信智能体或被测代码自称成功：重新读取文件、数据库、频道事件、回执或页面状态；
- 测试描述行为，不锁定私有实现、CSS class、渲染次数和无意义快照；
- 每个回归测试必须证明修改前会失败；每个失败路径必须断言没有发布错误成功状态；
- Registry/Slot/Listener 必须测试注册、更新和 dispose；
- Product-visible Extension 必须有真实组装测试，手工拼一个 `ctx` 的单元测试不能代替；
- React 的 `renderToStaticMarkup` 只验证静态结构，不执行 Effect、事件、浏览器导航、SSE 或外部 Store 订阅生命周期，不得归类为产品旅程或真实浏览器组装；
- 用户可见 Web 改动至少运行一次生产 bundle 产品旅程。每个一级路由断言主内容可见、根节点非空，并把 `pageerror`、React `console.error`、未处理 Promise 拒绝和整页错误兜底视为硬失败；动效相关旅程必须覆盖 `prefers-reduced-motion`，截图须等 Presence 结束；
- 代表性稳定页面使用 Playwright `toHaveScreenshot` 与仓库基线比较；仅附加 PNG 只用于人工验收记录，不算自动视觉回归。频道会话与外观设置至少各保留一份双主题代表基线；
- 频道会话、连接、外观设置和全局命令面板运行 Axe WCAG 2/2.1 A、AA 扫描，critical 或 serious 违规是硬失败。Axe 不能替代键盘、缩放、真实像素和文案验收；
- API、领域测试、类型检查和构建全部通过仍不能替代产品旅程。实现者必须用当前环境能驱动真实页面的手段跑通用户可见闭环；仓库内 `pnpm test:journey` 是默认自动化入口。没有任何真实页面驱动手段时，不得宣称 Web 交付完成；
- 交互测试必须经过真实 DOM 事件和路由切换；仅断言 API 成功不能证明按钮、表单、错误反馈或草稿保留可用；
- Vitest 与 Web Vite 测试服对 workspace 包必须解析到当前源码，不能依赖本机上次留下的 `dist`；别名由 `scripts/workspace-source-aliases.mjs` 统一维护。新增或改名内部包时同步更新该表。`pnpm build` 独立验证发布产物。
- 需要真实页面渲染器的 Vitest 文件只在 quality 的 `pnpm test` 中运行；quality 必须安装仓库旅程所依赖的 Chromium 与 `chromium-headless-shell`。`pnpm test:coverage` 与 `node-compat` 必须排除这些文件：覆盖率只统计 `packages/*/src`，覆盖率插桩会让 Vite 首屏超过默认 5 秒超时；`node-compat` 不安装页面渲染器。新增此类文件时同步更新排除列表，`check:gates` 会核对。
- 产品页中的 Button/IconButton 必须具备真实点击、指针或键盘处理器，或位于 ui-kit 语义触发器内，或承担表单提交 / 永久禁用状态。条件性 `disabled` 不能掩盖无处理器控件；空函数、返回 `undefined` / `null` 的处理器仍视为空操作。根 `check:ui-actions` 对产品入口执行静态门禁，关键动作仍需生产旅程验证外部结果；
- 用户可见 UI 改动必须同时完成源码审查与 §5.1 视觉验收，两者与类型检查、相关测试、产品旅程同级；任一条失败都不能转用户；
- 基础 UI primitive 由唯一 ui-kit owner 提供；业务页面不得直接导入 Radix 或 `motion`，也不得复制 Button、Select、Switch、Tabs、Dialog、Tooltip 的交互状态机。依赖边界由根检查维护；
- Portal 型组件必须使用统一动态层级：同层 `overlay < content < floating`，后打开 Modal 的 overlay 高于前层 floating。层叠修复必须进入 ui-kit 测试，不能在业务页面增加局部 z-index；
- 每个用户可见 mutation 必须覆盖 pending、防连点、失败恢复和成功后的权威结果刷新；处理器内部静默 return、fire-and-forget 或仅乐观改前端状态都不能通过空操作门禁；
- 布局回归按风险加入几何断言：Hover 前后正文宽度稳定、同类状态灯共享视觉轴、内容宽度 Hover 不扩成整行、最后消息不被浮动 Composer 遮挡、消息左右方向符合频道视角、标题不会在窄窗压成逐字竖排。几何断言补充 §5.1，不能替代；
- 迁移测试遵循各格式当前策略：Core SQLite 在早期开发阶段覆盖空库按当前 Drizzle 序列应用、当前迁移 no-op 与旧实验库明确拒绝；仍承诺升级的 Client 或外部格式才保留逐级升级、未来版本拒绝和失败恢复 fixture；
- 不强制项目早期每文件 100% 覆盖率。覆盖率用于发现未测试代码和死分支，不能代替场景与真实入口验证。

### 5.1 用户可见界面的视觉验收

用户可见的布局、样式、路由、客户端状态或渲染数据发生变化时，必须对真实产品画面做像素级验收。视觉验收与类型检查、相关测试、产品旅程同级：功能可用、旅程通过、Console 无错、元素可见、无横向溢出、几何断言通过或源码审查通过，都不能单独视为视觉通过。

源码审查与视觉验收是两条独立证据链。源码审查检查需求层次、状态所有权、mutation、组件复用、文案边界、异常和测试；视觉验收检查真实画面上的布局、可见功能、美观、合理性和可读性。两条链路任一不通过，本轮 UI 即未完成。

#### 必须看见真实像素

验收对象是当前改动实际服务出来的产品画面，不是静态 HTML、组件画板、设计稿、DOM 文本、计算样式或无障碍树。

取画面的手段不限：使用当前环境已经能展示真实渲染结果的可视化界面即可。有内置可视化能力的实现者用该能力；没有时改用任何能得到真实帧的等价手段。本节不规定具体产品、驱动方式或操作步骤。

只要实现者能理解图像（包括多模态模型），就必须亲自阅读这些画面，按本节清单逐项判定。不得只根据测试日志、选择器命中、计算样式或“页面已打开”声称视觉通过。不能阅读图像时，必须由能看见画面的人完成同一份清单，不能由源码审查代签。

#### 覆盖范围

必须按真实用户路径走完改动涉及的功能，并打开共享同一状态、数据或组件的其他页面。只看改动当屏、只看默认态、只看一种宽度，视为未完成。修完视觉缺陷后必须再看真实画面，不能只靠代码 diff 宣称已修好。

每种风险取代表场景，不做全部组合的像素笛卡尔积：

| 风险类 | 代表要求 |
|---|---|
| 视口 | `1100×720`、`1440×900`、`1920×1080` 至少覆盖改动会受压的档 |
| 主题 | 改动触及颜色、描边、表面或对比时，浅色和深色都要看 |
| 动效 | 默认动效下看连续性与是否抖动；动效改动另看 Reduced Motion |
| 状态 | 默认、选中，以及该面存在的空态、错误、禁用、加载 |
| 浮层 | 改动涉及的菜单、对话框、提示、检查器都要打开看 |
| 共享面 | 写入或派生状态后，所有读取该状态的界面都要再看 |

设计语言本身还须覆盖的缩放、键盘和对比组合见 `05` §13；本节管实现改动后是否在真实画面上成立。

#### 判定清单

任一项明显不合格即整轮视觉失败，必须先修再复查，不能带着缺陷转用户。观感目标、Token 和动效等级以 `05` 为准；交互对象和按钮后果以界面交互模型为准。

**布局**

- 行列对齐，同类状态灯、标题、表单标签共享视觉轴；
- 间距来自 Token，没有无意义大块空白，也没有挤成一团；
- 没有重叠、裁切、把标题和副标题压成一行或截到半个字；
- 没有意外横向滚动；该滚动的区域真能滚；
- 浮动 Composer、粘性表头、选中指示不得侵占或遮挡正文；
- 窄窗标题不得被压成逐字竖排；分栏在最小宽度仍可用；
- 图片和媒体有高度上限，不把栏撑破。

**可见功能正确性**

- 页面主对象一眼可辨，选中项不靠读地址栏才能认出；
- 可点击控件看起来可点；禁用看起来禁用；未开放能力标注“尚未开放”；
- 点击、填写、提交、导航后的画面结果与操作一致；
- 检查器、详情、树和标题栏描述的是当前对象；
- 共享壳层（导航轨、对象列、检查器）在相关路由上保持一致。

**美观与工艺**

- 密度、圆角、颜色与相邻页面是同一产品；
- 选中、悬停、焦点只用 Token，没有调试色或残留描边；
- 导航时未改动的区域不整块重挂、不抖动；
- 动效连续交代去向，无弹跳、无整壳滑动、无对话区布局动画。

**合理性**

- 信息层次清楚：标题重于说明，说明重于元数据；
- 相关操作在一起；危险操作与主操作可区分；
- 空态和错误说明对象、范围和下一步；
- 同一动作没有两个互相竞争的主按钮。

**可读性**

- 浅色和深色下正文、标签、次要文字、占位符对比足够；
- 中英混排、长名称用省略号，不把同一行的其他文字挤没；
- 次要文字明显轻于标题，不会和标题抢权重；
- 消息、代码、日志、表格读得下去，行高和换行正常。

#### 不构成证据

- 只说打开过页面或“看过了”；
- 只留最后一张截图，没有按清单读过；
- 只检查 DOM 文本、ARIA、计算样式或 Console；
- 只证明元素存在、可见或没有横向溢出；
- 只跑过旅程、几何断言或源码审查。

完成说明必须写清：看了哪些路由和浮层、什么视口和主题、哪些状态、画面上看到了什么、有无不合格项。截图是附件，不是通过证明。仓库内不得提交真实聊天、个人标识或平台临时 URL 的画面；本机用真实数据做验收可以，那些帧不入库。公开边界见 `00-文档公开边界.md`。

#### 与其他检查的关系

| 检查 | 证明什么 | 不能代替 |
|---|---|---|
| 产品旅程 | 页面能开、动作有外部结果、无整页崩溃 | 看起来对不对 |
| 几何断言 | 若干已登记的布局回归 | 未登记的挤压、层次和美观 |
| 源码审查 | 结构、所有权、文案和复用 | 真实像素 |

## 6. 检查阶梯

本地优先运行覆盖改动的最窄检查，不机械重复全仓检查：

```text
文档：pnpm check:docs
局部代码：对应 package test + typecheck
公共契约或跨包行为：pnpm check + pnpm test
构建、导出或 Client Slot：再运行 pnpm build 和真实组装测试
用户可见 Web：pnpm test:journey（生产 bundle、真实页面）
用户可见 UI：§5.1 真实渲染画面验收（与旅程同等必要，取画面手段不限）
产品交付复核：pnpm verify:product
发布前：CI 全量检查与平台矩阵
```

根 `pnpm check` 至少包含格式检查、静态 lint、严格类型检查、文档链接/公开边界和工作区约束；`pnpm test` 运行无密钥测试；`pnpm build` 验证可发布入口。需要密钥的真实平台测试必须自跳过并由单独流程运行，凭据和原始 payload 不进入仓库；据此写回归时先改写成合成夹具。格式化、lint 和类型检查只覆盖产品源码与仓库脚本；运行数据根 `data/`、误创建的平行数据根 `apps/*/data/` 和本地分区 `.local/` 必须被忽略。智能体工作区可以包含仓库副本或任意用户文件，把它们当产品源码扫描会把运行产物误判为工程问题。检查脚本的本地相对导入必须指向 Git 已跟踪文件：`.gitignore` 只忽略 `apps/*/lib/` 与 `packages/*/lib/` 这类构建产物，不能用全局 `lib/` 把 `scripts/lib/` 源码排除出仓库；`check:gates` 会核对这一点，避免本机有文件、干净检出却缺模块。

### 6.1 本地开发服务必须仍可访问

本机已经在跑根命令 `pnpm dev`（Web `127.0.0.1:4961` 代理 Server `127.0.0.1:4960`）时，改完会触发重载的代码必须当场确认服务还活着，再结束本轮。这包括改 Server / Web 源码、workspace 包 `dist`、`contracts`、Drizzle 迁移，以及任何会被 `tsx watch --include '../../packages/*/dist/*.mjs'` 看到的产物。

最低探测：

1. `GET http://127.0.0.1:4961/` 返回 200；
2. `GET http://127.0.0.1:4960/api/snapshot` 返回 200；若只方便打 Web，则 `GET http://127.0.0.1:4961/api/snapshot` 必须同样 200。

不构成证据：

- 只看到 `tsx watch` / `vite` / `pnpm` 进程还在。watch 父进程可以空转，子进程已经退出，`4960` 不再监听；
- 只看到 Vite 首页 200。Web 活着而代理 `/api` 为 500，表示 Server 挂了，页面不可用；
- 只看到端口 `LISTEN`，没有打过 HTTP；
- 只跑过单测、类型检查或构建。

探测失败时必须读 watch 实际输出、修好启动错误（编译、迁移、端口占用），把 Server / Web 重新拉起到上述两个 200，不能把「进程还在」或「以后用户自己重启」当作完成。不要在同一端口再开第二套 watch。端口、数据根和 watch 行为见 `apps/server/README.md`。

## 7. 迁移与持久格式

所有持久格式使用单调递增整数版本；读取未来版本必须失败并保留原始数据，不猜测降级。迁移必须顺序、确定、可重复验证，并由格式所有者维护：

- Core SQLite schema 由 storage package 与 Drizzle migration 拥有；
- DSH Session 格式由锁定的 DSH package 拥有，NekroNxt 不修改其私有表；
- Client 持久状态由 Client migration registry 拥有；
- Extension Manifest、源码 Revision 和构建缓存各自版本化，缓存可以直接丢弃重建。

宿主升级协调器只负责备份、排序、journal、失败恢复和启动门禁，不把四类 migration 合并成一个巨型脚本。详细决定见 `decisions/accepted/2026-08-16-客户端状态与数据迁移基础设施.md`。

### 7.1 统一数据根目录治理

Server 和 Desktop 只使用一个明确的数据根（容器部署为 `/data`，本地由 `NEKRO_DATA` 或宿主参数确定）。数据根不是临时文件投放区：每个顶层文件或目录必须有唯一所有者、明确的持久/缓存属性、备份恢复语义和当前消费者。新增顶层项必须同步更新组合根、包 README 或对应 Decision；禁止因单次调试、测试、功能捷径或当前工作目录不同而创建平行数据根。

当前 Server 组合根按职责使用 `core.sqlite`、`sessions.sqlite`、`assets/`、`credentials/`、`dsh/`、`extension-data/`、`extension-cache/`、`workspaces/` 和 `backups/`。其中：

- `core.sqlite-{wal,shm}` 与 `sessions.sqlite-{wal,shm}` 是 SQLite 在运行期管理的数据库伴生文件，不是独立数据分区，禁止手工移动或删除；
- `dsh/spill/` 是 DSH 超大工具结果的持久 artifact 存储，随数据根备份恢复；locator 只在 DSH Session 内部使用，不得进入 Adapter、Asset 或用户文件身份。Server 必须以单 artifact、单 Session 和 Host 总量配额阻止无限增长；
- `workspaces/` 只保存智能体显式获准开发能力后的工作文件，默认路径为 `workspaces/<agentId>/`；目录在首次使用时以私有权限自动创建，不同智能体不得共用默认工作区；
- `backups/` 由 Host 升级入口拥有，按 Product Release 保存迁移前恢复点。当前实验只使用 SQLite online backup 覆盖 `core.sqlite` 与 `sessions.sqlite`，不代表完整数据根已经可恢复；未来纳入 Asset、Credential、Extension Source、Spill 与 Workspace 时必须同时提供恢复顺序、空间预算和崩溃 fixture；

Desktop Release 版本只读取仓库根 `package.json#version`。预览版和正式版必须使用不同安装身份与数据根；三端制品必须由 `pnpm desktop:preview|desktop:stable --platform ...` 生成，并保留脚本生成的 SHA-256 receipt。正式版公开前校验 `vX.Y.Z` tag、根版本、receipt commit 三者一致。macOS 只发布 Universal 包，不得把单架构原生 runtime 标记为 Universal。
- 外部工作区根是宿主级高级覆盖，只改变 `workspaces` 根的位置，仍保留 `<agentId>` 子目录作为默认工作目录；DSH rc.6 的 `workspace-write` 只约束写入，不能被描述为读取隔离边界；完整文件访问只改变已启用文件工具或开发 Shell 的策略，不会单独提供工具；
- 测试数据使用测试框架创建的临时根或 `.local/` 专用分区，不进入常驻 `data/`；可丢弃缓存与持久事实不得混放；
- `data/` 不是源码树。ESLint、Prettier 和类型检查 include 必须忽略它，公开边界检查只禁止它被 Git 跟踪，不得把工作区里的仓库副本或运行产物当作产品源码；
- 现有顶层布局的归并必须作为带迁移、备份与恢复验证的独立任务处理，不能在局部功能修改中静默移动用户数据。

### 7.2 AgentRevision 能力格式

`agent_revisions.capabilities_json` 保存六项授权：`subagents`、`fileTools`、`webSearch`、`dynamicCreation`、`developmentShell`、`unrestrictedFileAccess`。读写共用同一个 Zod Schema；未知字段拒绝。语义未变化时不生成新 Revision，切回已有内容复用该智能体的历史 Revision。无法识别的 Core 数据库拒绝打开。

### 7.3 子智能体关闭顺序

Episode rollover、频道换绑导致的旧 Session 关闭以及 Server dispose 都必须先停止新的根 Session admission，再调用 DSH `drainContinuableDescendants([root])` 关闭该根的 descendant admission、取消活跃 child 并按 child-first 顺序等待静止，最后才 dispose 根 `AgentHandle`。同一智能体其他频道的根 Session 是独立树，不得一起取消。当前资源硬边界只采用 DSH 公开配置 `maxDepth=1` 和 child 每次请求 `maxTokens=4096`；本期明确不自研 child 并发、总时长、总轮次或 followup 队列调度器。

## 8. 防止工程腐化的停线条件

出现以下征兆时暂停新增功能，先梳理所有权和事实流：

- 同一状态出现三个以上可写副本，且无法指出权威来源；
- 为绕过包接口开始导入内部路径、读取其他包数据库或传递整个 Context；
- 一个修改需要在多个无关包复制相同 switch、默认值或错误映射；
- dispose 后仍残留 Tool、Listener、Timer、Slot、子进程或后台 Promise；
- 测试大量依赖 sleep、mock 内部实现，或只断言“返回了成功”；
- 新增包、Service、配置项或兼容分支没有当前消费者；
- Decision、协议、类型和测试对同一行为给出不同答案；
- 为赶进度跳过持久化、回执、失败状态或迁移恢复，再计划以后补齐。

停线不是重写整个项目。先画出对象所有者、输入、提交点、派生状态和验证证据，删除重复层，再从最小垂直闭环继续。

## 9. 参考取舍

本规范借鉴 DSH 公开仓库中的分层 AGENTS、一个事实一个家、真实组装测试、可逆 effect、提交点发布、真实入口与外部结果验证、迁移拒绝带病启动等实践。

当前明确不照搬 DSH 成熟仓库的双语配对、每文件 100% 覆盖率、庞大生成目录、全部包 invariant 和完整发布门禁。NekroNxt 只在真实风险和重复操作出现后增加相应自动化。
