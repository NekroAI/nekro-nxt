# DSH 能力插件优先兼容与受管加载

状态：implemented

## 结论

面向 DSH 能力面的插件默认通过公开 Plugin、Service、Tool、Provider、Settings、Credentials、Scope、Bundle 和 Preset 接缝零适配运行。NekroNXT 元数据、中文文案和产品界面只能增强体验，不能成为加载前提。NekroNXT 特有的 Connection、Channel、Binding、Asset 和可靠投递继续使用自身 Contribution，因为 DSH 没有定义这些领域语义。

固定随 Host 交付的包标记为“内置”，不可关闭或移除。用户插件显示安装来源、精确版本、入口、用户确认的作用域、Activation 和实时 Loader 诊断。API Key、网络和第三方服务故障进入配置或运行诊断，不改变来源标签，也不生成“已验证”之类人工评级。

## 受管包安装

用户安装支持 npm registry spec、npm tgz 和 `dsh-plugin-package` `.nxt-extension`。registry range 在检查阶段解析为精确版本；不接受任意 URL 或普通用户本地目录。每个精确版本安装到独立的 `dsh/plugin-packages/<packageInstallId>/project/`，拥有自己的 `package.json`、`pnpm-lock.yaml` 和 `node_modules`，不同版本可以并存。

Server 使用随应用锁定的 pnpm `11.7.0` CLI，通过 `process.execPath` 启动无 shell 子进程，并限制环境、执行时间和输出大小。第一次安装生产依赖使用 `--ignore-scripts`；只有 `pnpm ignored-builds` 与静态生命周期检查确认存在 blocked build 时才提示。用户按依赖名批准后，仅把对应精确 key 写入当前安装项目的 `allowBuilds` 并执行 pending rebuild。批准与插件精确版本和规范化 lockfile 摘要绑定；依赖变化后必须重新确认。

安装在 `plugin-staging/` 完成包身份、exports、Bundle、摘要和入口解析校验，每个入口必须能从当前受管项目解析为目录内普通文件。检查凭证十分钟失效，超时后清理对应 staging；提交时先原子 rename 到正式目录，再写数据库。任何失败不创建正式安装事实；进程重启清理未提交 staging，并把数据库没有对应安装事实的正式目录移入 `plugin-trash/`，保留人工恢复可能。长操作使用进程内 Operation ID，通过 `dsh-plugin-operation` SSE 报告下载、依赖、构建脚本、校验和提交阶段。

DSH 分享包携带根 npm tgz、精确身份、入口、内容摘要、integrity 和 lockfile 摘要，不携带 `node_modules`。目标机器联网重装依赖，并核对包内容、规范化依赖锁和 Bundle 入口；不承诺跨操作系统复用原生构建产物。

## Loader 与作用域

生产 `DshHostRuntime` 建立一个 Host Loader，并在每个智能体 DSH Session 建立 Agent Loader。两者继承 DSH 公开 Service，但通过 Context isolation 隐藏 Core、数据库、Connection、凭据实现和其他私有 Service。模块解析、Config 校验、Fiber、更新、回滚和 dispose 由 Cordis Loader 拥有；NekroNXT 只拥有包来源、用户选择、授权、诊断和产品 UI。

普通入口同一时刻只能使用 Host 或智能体一种作用域，切换前必须关闭旧 Activation。Bundle 通过公开 `composeEntries()` 展开，每个非 group 入口拥有稳定 ID、独立配置和作用域。智能体启用、更新和关闭先等待目标 Session 进入安全间隙，再改变该智能体现有的全部 Loader；任一候选失败时恢复本次已改变的 Loader，数据库不发布新 Activation。无存活 Session 时使用随 Host 生命周期持有的 Probe Loader 验证候选，不 dispose 从根 Context 派生的临时作用域。新 Session 和冷启动按持久 Activation 逐个恢复；单个入口失败保留其启用意图并写 `restore-failed`，但不阻止该智能体 Session 和其他入口恢复。

Loader `create/update/remove` 后必须等待 `await()`，并由官方 Plugin Inventory 确认入口处于 `active`。入口 Config、所选作用域、Activation、NXT 页面权限和页面目录在一个 SQLite 事务中提交；关闭 Host Activation 时也在一个事务中撤销 Activation、权限和页面。加载失败、更新失败和 dispose 失败分别写精确阶段诊断；多 Session 关闭或数据库提交失败时重新挂载此前已成功卸载的入口。移除包前列出并关闭全部 Host/智能体 Activation；任一入口无法静止时保留安装记录和目录。全部成功后删除数据库事实并把安装目录原子移入 `plugin-trash/`。

## 配置与 Secret

DSH Settings namespace 继续使用 `settings.describe()`、路径级 `mutate()`、`expectedRevision` 和现有 Credentials，不建立第二份设置持久层。Host 对序列化 Schema 做 fail-closed 脱敏检查；不能证明安全的 namespace 不进入 Web API。

只有 Cordis Plugin `Config` 的入口在用户确认初始化第三方模块后读取 Config Schema。可安全序列化时使用同一通用 Schema 表单；没有 Schema 时提供高级 JSON。Config 中含 `secret` 或 `credential-ref` 角色，或 JSON 键名表现为 Secret/credential 时拒绝保存，要求插件改用 DSH Settings/Credentials。Config 更新通过 `loader.update()` 事务应用，失败时恢复旧配置。

## DSH Client UI 边界

DSH 原生 WebUI、侧栏、Composer 和页面 Slot 不接入 NekroNXT。检测到 `dsh.client` 只显示“原生界面未接入”，Host 能力和通用 Settings/Config 不受影响。

DSH 包可另行显式声明版本化 `nekroNxt.hostUi`：它绑定一个稳定 `entryKey`、包内自包含 NXT Client ESM、1–8 个页面贡献和完整权限集合。安装检查只校验文件和契约，包安装后页面保持关闭；匹配入口以 Host 作用域启用并批准权限后发布页面，关闭或移除入口时撤销。Client 加载失败只写页面诊断，不伪造 Loader 失败。智能体作用域 Activation 不发布全局页面。

第三方插件与 Client bundle 都是 Server 或浏览器进程内的受信任可执行代码。Context isolation 与 Loader 生命周期不是安全沙箱；Process/Worker/Remote Runtime 属于未来方向。

## 验证矩阵

当前真实组装测试覆盖 tgz 安装后关闭、入口解析拒绝、检查凭证过期、孤儿正式目录恢复、blocked build 检测与逐项批准、Host 激活/关闭/移除/重启恢复、智能体 Tool 作用域隔离、Config Secret 拒绝、Loader Inventory、DSH 分享包导出导入和导入后关闭。升级 DSH、Cordis 或 Loader 时必须重新运行完整 Profile/Scope/Loader 兼容矩阵。

## 未来边界

当前不建设社区市场、签名、发布者等级、SBOM、云审核、完整离线依赖闭包、任意 URL 下载和进程隔离。保留稳定 package/entry ID、不可变精确安装、公开 Loader/Bundle 接缝和来源诊断，未来分发层不得另造插件生命周期。
