# 客户端体验重构与扩展界面统一

状态：accepted（2026-10-04 用户确认；分阶段实施，未落地部分见 §9）

本决定替换现行客户端信息架构、视觉体系、扩展界面贡献模型与配置表单模型。领域不变量保持不变：智能体是长期实体，一个频道同一时间只有一个响应智能体，用户可见发言只来自通信工具，配置与扩展通过不可变 Revision 演进，动态运行、保存和启用是独立动作，Connection 与 Adapter 分离，普通消息不隐式取消工具。

## 1. 理由

旧客户端按内部数据模型组织页面（智能体 → 修订 → 绑定 → 频道），用户的主要问题却是“哪里有动静、智能体刚做了什么、需要我处理什么”。旧视觉体系卡片层层嵌套、装饰与字号碎片化，`product-pages.module.css` 单文件承载全部页面样式。扩展 Slot 按页面位置命名，任何布局调整都会改变扩展契约；三套 Client Runtime 和三种配置格式让扩展难以与产品保持一致。

## 2. 用户已确认的取舍

1. 一级空间为 **现场 / 频道 / 智能体 / 工坊 / 接线**，设置位于导航轨底部。界面实体名称仍为“智能体”。
2. 默认进入现场，不再打开上次频道。
3. 平台用户目录不再是一级页面：频道成员进入接线的频道详情，全局查找进入命令面板。
4. 透视取代独立的工作轨迹视图：同一时间线在常态显示轮次摘要，打开透视后展开思考、工具输入输出与用量。
5. 扩展页面不自动进入导航轨，通过命令面板、所属对象页面或用户钉选进入。（2026-10-09 用户调整：不提供用户钉选；导航入口只在扩展自己注册对应 Slot 时出现，该 Slot 尚未开放。）
6. 扩展 Manifest 只保留 V6；V1–V5 的读取、重建与“需要重建”界面删除。
7. 清理本机测试智能体、测试内置频道、全部本地扩展与创造任务；保留真实智能体、外部频道、连接、模型供应商与凭据。
8. GlinUI 隔离实验不并入；`@glinui/tokens` 依赖随旧视觉体系移除。

## 3. 信息架构

| 空间 | 路由 | 主要对象 |
|---|---|---|
| 现场 | `/live` | 需要关注的事项、活动中的频道、近两小时活动潮汐 |
| 频道 | `/channels/:channelId` | 当前频道的消息时间线 |
| 智能体 | `/agents/:agentId`、`/agents/new` | 智能体资料：设定、频道、技能、版本 |
| 工坊 | `/workshop`、`/workshop/tasks/:taskId`、`/workshop/extensions/:extensionId` | 创造任务与本地扩展 |
| 接线 | `/wiring`、`/wiring/connections/:connectionId`、`/wiring/channels/:channelId` | 平台账号 → 频道 → 智能体的绑定关系 |
| 设置 | `/settings/:section` | 模型供应商、DSH 扩展、通知、外观、关于 |
| 扩展页面 | `/apps/:pageInstanceId/*` | 扩展自有页面 |

旧路由 `/work/*`、`/users`、`/extensions/*`、`/connections/*` 删除，不保留重定向。

外壳由顶栏（服务实例、面包屑、命令面板、关注入口）、导航轨、主画布与状态栏（Host、各 Connection、正在工作的智能体）组成，外壳常驻，切换空间只替换主画布。

频道列表保留“按智能体”（可拖动排序、跨组拖动换绑、拖到未接线解绑，放下后确认）与“最近活动”两种视图。频道行副标题始终显示连接展示名（`alias ?? Adapter displayName`），必要时附 Adapter 名称。

## 4. 设计系统与动效

`apps/web/src/ui-kit/` 是唯一组件所有者，Token 与组件规格以 `05-桌面UI与动效规范.md` 为准。要点：

- 字号 12/13/14/16/20/24/30，最小 12px；圆角三档；阴影三档；智能体身份渐变色；浅色与深色对等。
- 卡片最多一层；装饰只出现在现场潮汐图与品牌标识。
- 动效实现规则：外壳与指示元素常驻；选中、分段、标签、导航指示块用 transform 滑动并始终位于文字下层；局部交互只更新局部；不对含文字区域使用 View Transitions 命名快照；尊重减少动态效果。
- 动效验收使用逐帧录屏：过渡期间文字持续可见、无空白帧、点击后一帧内出现反馈。

智能体外观（身份色、可选头像 Asset）属于 `AgentDefinition` 的非版本化外观字段，不进入 `AgentRevision`。

## 5. 扩展界面贡献 V6

### 5.1 Manifest

`schemaVersion: 6`，`scope` 仍为 `agent | host-adapter | host-ui`。所有 scope 统一声明 `permissions: HostUiPermissionDeclaration`（可为空），可选 `config: { schema: SerializedSchemastery }`。

| 贡献 | 允许的 scope | 声明 |
|---|---|---|
| `tool` / `rpc` | agent | 与 V5 相同 |
| `panel` | agent：`anchor: agent \| channel \| extension`；host-adapter：`anchor: connection \| channel` | `id`、`title`（≤24）、可选 `icon: HostIconName`、`densities: ('compact' \| 'full')[]`、可选 `when: { channelKinds?, }`；connection 锚点另有 `role: setup \| status \| diagnostics` |
| `tool-view` | agent | `tool`：本 Revision 声明的 Tool 名 |
| `message-renderer` | host-adapter | `richKind`：本 Adapter 的 `rich` extension kind |
| `adapter` | host-adapter | 与 V5 相同，恰好一个 |
| `page` | host-adapter、host-ui | 与 V5 `host-page` 相同，最多 8 个 |

`host-ui` 只允许 `page`。宿主按锚点决定放置位置：智能体面板进入智能体资料页（`full`）与该智能体响应频道的检查器（`compact`）；频道面板进入频道检查器；扩展面板进入工坊扩展详情与智能体技能抽屉；连接面板进入接线的账号详情（setup 角色同时用于添加账号）。

### 5.2 Client Runtime

智能体 SlotCore、Adapter SlotCore 与 Host UI Runtime 合并为一个 `ExtensionUiRuntime`，按 owner 隔离，每个贡献独立错误边界。Client factory 接收 `{ React, ui, host }`，通过 `ctx.panels.register(id, Component)`、`ctx.toolViews.register(tool, Component)`、`ctx.messageRenderers.register(richKind, Component)`、`ctx.pages.register(...)` 注册。`ui` 为版本化公开 UI Kit；`host.call` 调用自有 RPC 或权限允许的产品读取与写入；上下文 Hook（`useAgent`、`useChannel`、`useConnection`、`useChannelRuntime`）订阅产品事件流并按权限过滤。注入的 `styles` 类名映射删除。

Props 只携带身份与呈现参数：

- panel：`{ anchor: { kind, id }, density, role? }`
- tool-view：`{ call: { callId, toolName, state, input?, result?, durationMs? }, density: 'chip' | 'card' }`
- message-renderer：`{ part, messageId, channelId }`

宿主 `ContributionFrame` 绘制标题、图标、折叠、加载、失败回退与进出场动效，扩展只渲染内容。

### 5.3 权限与验证

所有 scope 的权限使用与 Host UI 相同的“批准即绑定精确 Artifact 摘要”流程；智能体扩展在给智能体启用时批准。动态预览、保存与导入验证对每个 panel 在声明的密度与两种主题下真实渲染，对 tool-view 渲染 `chip` 与 `card`，对页面执行注册与 Navigation；渲染失败、横向溢出或未捕获错误阻止 `ready`。创造 Preset 的界面参考升级为 `nxt-host-ui-design-v2`。

## 6. 统一配置

- 唯一格式为序列化 Schemastery；`schema.role('secret')` 表示只写凭据，存储为凭据引用，界面只显示是否已配置。
- Adapter Descriptor 的自定义 `configSchema` 改为序列化 Schemastery。
- Web 唯一内部表单模型为 `SchemaNode`，补充分组、`advanced` 折叠、条件显示、枚举标签与校验文案；一个 `ConfigForm` 渲染全部配置。
- 智能体作用域扩展配置按 `(agentId, extensionId)` 随 Activation 保存，在安全间隙生效；宿主作用域随 Installation 保存；连接配置不变。

## 7. 后端投影

| 能力 | 契约 |
|---|---|
| 频道活动 | 快照为每个频道提供 `lastActivityAt`、末条消息预览与未读数；未读按管理设备阅读游标计算，`POST /api/channels/:id/read` 推进游标 |
| 需要关注 | `GET /api/attention` 聚合未确认投递、失败轮次、等待批准的创造任务、异常连接与智能体配置阻塞；条目带稳定指纹，`POST /api/attention/:id/dismiss` 持久忽略；变化通过 SSE 失效信号通知 |
| 排队上下文 | `GET /api/channels/:id/pending` 返回已收录、尚未注入的消息 |
| 停止当前任务 | `POST /api/channels/:id/stop` 取消当前模型或工具，不重置上下文；已收录消息保留 |
| 未确认投递 | `POST /api/outbound/:id/resolve`，`action: retry \| confirm-delivered` |
| 活动潮汐 | `GET /api/activity?window=2h&bucket=5m` 返回每个频道的消息计数序列 |
| 智能体外观 | `PATCH /api/agents/:id/appearance` |
