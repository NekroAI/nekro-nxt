# 按任务加载知识与验证边界

状态：implemented

## 问题与取舍

固定预读链把小改动扩大为长文档阅读；现行规范、Decision 和本地流程重复描述同一规则，形成相反指引。一般中文措辞按词硬拦截，以及扫描整个本地运行目录中的 Markdown，也让无关内容阻塞检查。

项目采用按任务定位知识、按事实所有者维护契约、按风险选择本地验证的方式。保留真实页面与画面验收、覆盖率、截图基线、Axe 和发布审查；减少固定执行步骤，并区分本次回归、交付阻塞和独立历史问题。Decision 的状态用于说明落地程度，不能自动裁决文档冲突；已有独立契约不因本次整理被强制拆成新文件。

文案硬检查只处理明确术语或技术标识泄漏，一般写作建议由语义审稿承担。本地知识检查以维护区域和显式链接为边界，运行产物不因包含 Markdown 被自动纳入。代价是检查器不再替代语言判断，也不能发现维护区域之外尚未入链的临时笔记；需要长期维护的知识应放入受维护区域。

## 当前契约与验证入口

- 文档职责、冲突处理、任务范围与验证选择：[开发规范](../../06-开发与测试规范.md#1-知识与决策)。
- 写作建议与自动门禁：[术语规范](../../01-术语与文案规范.md#47-自动检查与精确例外)。
- 本地发现及公开/私有可达性由 `scripts/check-doc-links.mjs` 实现；`scripts/tests/check-doc-links.spec.mjs` 用临时仓库验证实际退出码、断链、孤岛、运行产物与公开边界。
- `scripts/tests/check-terminology.spec.mjs` 验证自然语言放行、内部术语与技术 ID 回退失败、精确例外及陈旧例外；`pnpm check:docs` 验证仓库实际文档。

参考 [Rethinking skills and prompts for GPT-6 Astra](https://x.com/pvncher/status/2095991462416490862) 对渐进加载和执行边界的讨论；采用与具体模型无关的项目约束，不以模型能力声明替代产品验证。
