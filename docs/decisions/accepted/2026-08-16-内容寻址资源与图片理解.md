# 决策：内容寻址资源与图片理解

状态：accepted

## 问题

群聊会反复出现相同表情包、截图和文件。如果每条消息保存一份副本，长期运行的 Desktop 与 Server 会持续膨胀；如果只保留一个文件记录，又会丢失每次接收的频道来源、文件名和时间。不同模型对图片的原生输入能力也不同，文本模型不能因为不支持多模态就完全看不到图片含义。

视频当前没有独立处理需求，但仍是用户发送的文件，不能在入站阶段丢弃。

## 决定

NekroNxt 建立统一 Asset Service。图片、音频、视频、文档和其他文件先进入同一内容寻址存储，再由 MessagePart、DSH 投影、工具和 Adapter 使用。

一期不增加专用 `video` MessagePart，不做视频转码、抽帧、播放理解或模型专用投影。`video/*` 使用普通 `file` Part，保留验证后的 MIME、字节数、显示名和 `assetId`。未来出现视频理解需求时增加派生处理，不改变原始资源身份和历史消息。

## 物理对象与接收事实分离

Asset 物理对象以流式 SHA-256 内容摘要寻址。相同字节在一个数据目录中只有一个已提交 blob；写入使用私有 staging、完整摘要和长度校验、同文件系统原子提交。并发写入命中相同 digest 时只有一个提交成功，其他 staging 删除。

这里的“相同”严格指字节相同。视觉上相似但经过重新编码、裁剪、改帧或修改元数据的文件具有不同 digest，不能为了节省空间强行合并。未来可以用感知哈希将近似图片聚类并复用经复核的增强结果，但感知哈希不作为 Asset 身份、权限依据或物理删除依据。备份、升级快照和可重建缓存也不计入“一个已提交 blob”的在线存储承诺。

Asset 主记录至少包含：

- `assetId`：不透明稳定 ID；
- `contentDigest`、`byteSize`、验证后的 `mediaType`；
- `blobState`：`present`、`evicted`、`missing`、`quarantined`；
- `firstReceivedAt`、`lastReceivedAt`、`receiveCount`、`lastAccessedAt?`；
- 完整性状态和存储格式版本。

每次入站仍创建独立 `AssetOccurrence`，记录 `channelEventId`、`channelId`、平台消息来源、接收时间、发送方提供的文件名与声明 MIME。Asset 上的 `lastReceivedAt` 和 `receiveCount` 与 Occurrence 在同一个 Core SQLite 事务中更新；blob 提交与数据库通过 operation journal 恢复，不伪造跨介质事务。

物理去重不扩大读取权限。智能体、工具、UI 或 Extension 读取 Asset 前必须通过当前 Channel Event、Episode lineage 或明确授权对象证明引用关系。全局 digest、其他频道的文件名、来源和接收统计不对无权调用方公开。

## 与 DSH Attachment 的关系

DSH rc.6 的 Attachment Service 已提供不可变、SHA-256 内容寻址的图片引用，但当前只接受 PNG、JPEG、WebP 和 GIF，并且 DSH ContentBlock 只有原生 `image`，没有通用 file/video block。

NekroNxt 不把同一图片再复制到第二个 DSH 目录。`dsh-compat` 为受支持的栅格图片提供 DSH AttachmentStore 适配层，使用 NekroNxt Asset blob 作为字节所有者，并生成 DSH `ImageAttachmentRef`。通用文件仍由 NekroNxt Asset Service 拥有，通过工具和文字元数据进入 DSH；如果上游将来增加稳定 FileBlock，再在兼容层映射。

## 图片理解派生

图片增强是派生事实，不写死在 Asset 主记录。`AssetEnrichment` 至少由以下键唯一确定：

```text
(assetId, enhancerId, modelId, promptVersion, schemaVersion)
```

记录状态、元素摘要、可选 OCR 文本、标签、模型与提供方、输入摘要、创建时间、失败分类和来源 digest。更换模型、Prompt 或 Schema 产生新派生版本，不原地覆盖旧结果；相同图片再次出现时直接复用当前有效结果，不重复调用多模态模型。

配置了图片增强器时，首次图片入库后就异步排队增强，不取决于当前聊天模型是否支持图片；同一 enrichment key 只允许一个有效任务或结果。消息和 AssetOccurrence 必须先可靠入库，增强失败不能回滚频道事实。对只包含图片且当前对话模型不支持图片的消息，Admission 可以按 Binding 策略等待一个有上限的增强时间；超时或失败时明确告诉智能体“图片理解结果不可用”，不能假装已经阅读。

一期默认生成简短元素摘要和 OCR 文本，不建立向量索引、人物识别、自动关系图谱或跨频道语义记忆。可跨 Occurrence 复用的增强 Prompt 只能分析 Asset 字节本身，不得注入频道名称、发送者、其他消息或私有来源元数据；需要会话语境的分析必须作为带授权作用域的另一类派生结果，不能写入全局 AssetEnrichment。

增强结果是来源明确但不可信的派生内容。OCR、图片内文字和模型摘要都不能被提升为系统指令或工具授权依据，投影时必须保留类型、来源 assetId 和处理器版本。增强任务使用用户配置的多模态模型和独立 purpose，记录成本与来源；没有配置时保持 `unavailable`，不隐式使用云服务。

## 模型上下文与主动工具

入站投影按当前模型能力执行：

- 当前模型声明 `image` 输入能力时，触发消息中的受支持图片原生投影为 DSH ImageBlock；文本增强可以作为带来源的补充信息，但不替代原图；
- 当前模型不支持图片时，投影缓存的摘要/OCR；结果尚未可用时投影明确状态和 `assetId`，不传宿主路径或 base64；
- 通用文件只投影安全元数据和 `assetId`，具体文本提取由独立派生器按 MIME 增量提供。

提供两个作用清楚的工具接缝：

- `asset_inspect(assetId)`：所有模型可用，返回授权范围内的元数据、当前增强结果和来源引用；
- `asset_view_image(assetId)`：仅在当前模型及其 Provider 适配链支持图片 Tool Result 时注册，把验证后的图片作为 Tool Result ImageBlock 提供给下一 Step，使智能体能主动重读历史图片；它不依赖当前聊天平台 Adapter 是否支持发送图片。

工具只接受 `assetId`，不接受宿主路径、任意 URL 或 digest。模型不支持图片时不注册 `asset_view_image`；调用方不能借工具绕过 Channel/Asset 授权。

触发当前 Turn 的图片在能力允许时直接原生投影，不要求智能体先调用工具。主动工具主要用于回看历史图片、压缩后按需恢复细节，或在一次消息包含大量图片时按策略延迟读取。普通文件和视频没有通用 DSH FileBlock：DSH 中的智能体只能先看到授权元数据，再自行决定转发、下载，或调用已安装的文档提取、ASR、视频处理等 Contribution；“作为文件进入流程”不等于模型已经理解其二进制内容。

## 清理与保留

清理依据 Asset 与引用事实，不只依据目录大小：

- staging、未提交对象和无数据库记录的孤儿 blob 可在恢复扫描后清理；
- `receiveCount`、`lastReceivedAt` 和 `lastAccessedAt` 为保留策略提供热度证据；
- 活跃消息、固定资源、正在运行的 Tool/Job、未完成上传和 Extension Revision 引用形成保护集合；
- 允许未来策略驱逐长期未使用的原始 blob，同时保留 Asset 元数据、Occurrence 和增强结果，历史消息显示资源已清理而不是消失；
- 默认 Alpha 不自动驱逐仍被历史消息引用的 blob，只提供统计、预估和手工清理预览，获得真实空间数据后再确认默认保留期；
- 缓存、缩略图和可重建派生物可以独立 LRU 清理，不改变原始 Asset 的引用计数。

清理必须先生成计划，再在事务中标记待驱逐，最后删除 blob 并提交状态；失败可恢复。接收同一已驱逐 digest 时重新提交 blob、更新计数并复用仍兼容的增强结果。

## 测试

- 同一图片并发接收 100 次只产生一个 blob、一个 Asset、100 个 Occurrence，`receiveCount` 和 `lastReceivedAt` 正确；
- 相同字节使用不同文件名或来自不同频道时不复制 blob，也不泄漏其他频道元数据；
- staging、原子提交和数据库 journal 的每个崩溃点可恢复；
- 图片摘要对同一 enrichment key 只调用模型一次，版本变化产生新记录；
- 全局复用的增强请求只包含 Asset 本身，增强文本作为不可信派生内容进入上下文；
- 多模态模型收到原生 ImageBlock，文本模型只收到缓存增强或明确不可用状态；
- `asset_view_image` 在不支持图片的模型下不可见，在越权 Channel 中拒绝；
- `video/*` 作为 file 完整入库、可下载和转发，但不会被声称已经理解；
- blob 驱逐后历史消息、Occurrence、计数与增强结果仍可查询，再次接收能够恢复 blob。

## 备选方案

1. 每条消息复制一份文件：长期空间不可控，拒绝。
2. 只用 digest 作为消息中的资源身份：内容身份和产品对象身份耦合，难以演进存储与同步，拒绝；Asset 保留稳定 ID 和独立 digest。
3. 把图片摘要直接写在消息正文：无法按模型/Prompt 版本更新，也会污染用户原文，拒绝。
4. 所有图片每次都调用多模态模型：表情包和重复图片成本不可控，拒绝。
5. 为视频立即增加专用协议和转码：没有当前消费需求，拒绝；一期作为普通文件。
6. 用感知哈希合并近似图片的原始 blob：碰撞、编码和动画差异会破坏内容身份，拒绝；只保留未来做派生结果聚类的接缝。

## 影响

- M1 的 Asset Service 必须从第一天按内容寻址，并保存 Occurrence 与统计；
- M2 增加可恢复图片增强队列、文本模型投影和主动读取工具；M5 QQ Adapter 直接复用；
- DSH 图片内容寻址机制被复用，但 NekroNxt 扩展为通用文件、引用权限、接收统计和清理生命周期；
- 未来视频理解、文本提取、缩略图、向量索引和跨设备同步都作为版本化派生器增加，不改变原始消息协议。

## 未来方向检查

关联方向：多媒体、长期记忆、更多 Adapter、多设备同步和资源清理。

保留接缝：稳定 Asset ID、内容 digest、Occurrence、派生版本、blob 状态、模型 modality、工具与 DSH Attachment 适配层。

本次不做：视频理解/转码、向量检索、人脸识别、无限期自动保留、跨设备 blob 去重和社区资源分发。
