# 扩展宿主能力与生态移植

状态：accepted（2026-10-07 用户确认；分批实施，未落地部分见 §11）

本决定扩展本地 Extension 的宿主能力面，使 Nekro Agent 社区插件的功能可以由智能体重写移植到 NekroNXT，并为后续社区发现与分发准备稳定格式。目标是**功能等价**，不是复刻 Nekro Agent 的 API 形状；Nekro Agent 不合理的设计不照搬（§9）。领域不变量保持不变：用户可见发言只来自通信工具，新消息可靠入库，扩展通过不可变 Revision 演进，动态运行、保存和启用是独立动作。

## 1. 理由

Nekro Agent 插件市场有 91 个已上架插件。逐个阅读源码标注后：81 个需要配置（30 个含凭据），65 个需要出站网络，53 个直接导入宿主内部模块或数据库模型，23 个产出图片、语音或文件，22 个使用用户消息回调，19 个使用提示词注入（29 个每轮注入易变文本，缓存风险高），14 个需要定时或主动行为，10 个调用平台原生 API。现行 NekroNXT 扩展契约只能承接其中约三分之一（纯查询工具）。其余卡在六个宿主能力缺口：多模态产出、入站消息钩子、定时与主动行为、扩展私有存储与频道上下文、受控模型调用、平台原生动作；另有扩展配置不支持凭据、动态创造阶段无法联网两个直接阻断。

这些缺口是宿主能力面缺失，不是写法差异。NekroNXT 的核心体验是无开发经验的用户零代码完成扩展的设计、开发、分享和使用，因此每项能力的真正使用者是编写扩展的智能体：能力必须小、声明式、可验证，并且在权限页能用用户听得懂的话说明后果。

## 2. 用户已确认的取舍

1. Manifest 保持 V6，新能力只作为可选字段加入，并引入 `requires`；不再硬切旧格式。社区分发上线后，已发布格式永久可读；真正不兼容的变化走新版本加读取时转换。
2. 出站网络走 SDK 受控请求，支持声明域名、取自用户配置、以及用户显式接受风险的不限域名三种模式；不能限制死。
3. 入站消息始终入库；钩子可以不触发、强制触发、对智能体隐藏或附加标注，允许异步并调用模型，超时放行。
4. 定时任务支持 Manifest 声明和运行时创建，另提供内置提醒；宿主离线期间错过的任务开机后最多补一次并标注延迟。定时任务唤醒智能体，发言仍经通信工具。
5. 扩展私有存储默认按智能体隔离，可细分到频道或成员；跨智能体共享需要显式声明共享区权限。
6. 高风险能力在动态创造运行时遵循创造策略，给智能体启用时始终需要用户确认。
7. 平台动作由 Adapter 声明带参数 schema 和风险等级的类型化动作，同时提供原始 API 透传；透传属于高风险，需要用户显式开启。
8. 扩展上下文贡献遵守上下文缓存纪律（§8）。

## 3. 统一接缝：`nxt` 宿主服务

扩展的 Host 半边通过一个 Cordis Service `nxt` 使用全部新增能力：

```ts
return {
  inject: ['tools', 'nxt'],
  apply(ctx) {
    harness.registerTool(ctx, harness.defineTool({
      name: 'weather_today',
      // ...
      async execute({ city }) {
        const response = await ctx.nxt.http.fetch(`https://api.example.com/weather?city=${city}`)
        return response.text
      },
    }))
  },
}
```

- **同一接缝覆盖三处运行**：正式 Activation 挂载、动态创造运行和保存/导入验证。三处分别提供正式实现与验证替身，扩展源码不需要区分。
  - 正式挂载：`PersistentExtensionMounts` 为每个 Session Fiber 提供按所有者绑定的 `nxt` 实例，并把 `nxt` 加入允许 `inject` 的服务集合。
  - 动态运行：Server 在动态 Runner 的隔离 Context 中注册 `nxt` Cordis Service。DSH 动态沙箱的上下文门面对 `inject` 中声明过的服务按属性放行，方法返回值经过跨 Realm 检查，因此扩展以同样的 `inject: ['nxt']` 访问；`nxt` 不属于被隔离的 DSH 私有服务。沙箱屏蔽全局 `fetch` 与 Node 定时器，网络统一经 `ctx.nxt.http.fetch`。
  - 验证：导入验证器提供实现了全部方法的替身（§10）。
- **所有者绑定**：`nxt` 实例按 `(agentId, extensionId, DSH Session)` 绑定。每个 DSH Session 只属于一个 Episode，即一个 `(channelId, agentId)` 会话；智能体绑定多个频道时各频道是不同 Session，因此调用上下文由 Session 直接得出，不靠猜测。动态运行绑定创造任务，存储使用任务私有的临时空间。
- **只传可序列化数据**：每个方法都是异步、JSON 输入输出，不返回宿主对象、Context、数据库句柄或路径。未来把扩展 Host 半边移入 Worker 或子进程时，公开契约不变。
- **权限在调用时检查**：未在 Manifest 声明或未获批准的能力抛出可读错误，错误说明缺少哪项声明，供创造智能体自我修复。

`nxt` 是 NekroNXT 扩展契约，不是 DSH 能力插件的加载前提；DSH 能力插件继续零适配运行。

## 4. Manifest V6 加法字段

在现有 `permissions`、`config` 之外，`agent` scope 的 Manifest 新增以下可选字段；字段缺省时行为与现状完全一致，已有 Revision 的摘要和权限批准不受影响。

| 字段 | 内容 |
|---|---|
| `requires` | `{ sdk: <最低扩展 SDK 能力版本> }`；版本过旧的宿主在导入时给出“需要升级”的明确错误 |
| `capabilities.network` | `{ mode: 'domains', domains: [...] }`、`{ mode: 'config', fields: [...] }` 或 `{ mode: 'unrestricted', purpose }` |
| `capabilities.storage` | `{ scopes: ['agent' \| 'channel' \| 'member' \| 'shared'], quotaBytes? }` |
| `capabilities.assets` | `{ write: true }`：允许把产物写入当前频道 Asset |
| `capabilities.context` | 上下文贡献声明：名称、层级（`static` / `dynamic`）和长度上限 |
| `capabilities.jobs` | 声明式计划列表与是否允许运行时创建 |
| `capabilities.inboundHook` | `{ reads: 'triggered' \| 'all', mayHide, mayForceTrigger, timeoutMs }` |
| `capabilities.llm` | `{ maxCallsPerTurn, maxOutputTokens }` |
| `capabilities.platform` | `{ actions: [<adapterKey>:<action>], raw: [<adapterKey>] }` |

`config.schema` 允许 `meta.role: 'secret'` 字段：值写入宿主凭据存储，Activation 配置只保存引用；Host 通过 `ctx.nxt.secrets.get(key)` 在运行时读取，Client 永远读不到。凭据字段不得声明默认值。导出 `.nxt-extension` 时不包含任何凭据。

权限摘要只覆盖 `permissions` 与 `capabilities` 的规范化形式，不含 CSS、资源和界面贡献。新 Revision 扩大能力时需要重新批准，缩小时不需要。“扩大”指：新增能力键；网络模式按 `domains < config < unrestricted` 升级或新增域名、配置字段；新增存储作用域；入站钩子从 `triggered` 到 `all` 或新增隐藏、强制触发；新增平台动作或透传；模型调用上限提高。存储配额由宿主上限约束，调整配额不视为扩大。

## 5. 第一批能力

### 5.1 凭据配置

见 §4。凭据只写不读：界面显示“已设置”，修改即覆盖。验证替身提供合成凭据。

### 5.2 出站网络

`ctx.nxt.http.fetch(url, init?)` 返回 `{ status, headers, text?, base64?, contentType }`，统一超时、响应大小上限、重定向次数限制和私网拦截，DNS 解析结果固定后再连接（复用 Host UI 网络代理的实现）。三种模式：

- `domains`：只能访问声明的主机名，支持 `*.example.com` 通配；
- `config`：主机名取自所列配置字段的当前值，用户在配置里填写自建服务地址时无需重新声明；
- `unrestricted`：可访问任意公网地址，启用时显示醒目风险说明并要求用户勾选接受。

私网拦截按解析后的 IP 判定，在所有模式下默认开启；需要访问内网服务时使用 `config` 模式，目标主机名（含端口时按 `host:port`）与用户在所列配置字段填写的值精确相等时，允许解析到私网地址，即用户的显式配置视为放行。每一跳重定向都重新校验策略与私网。进程内运行的扩展仍可能绕过 SDK 直接访问网络：这不是安全沙箱，真正的强制隔离属于 Process Runtime（[未来方向 §4](../../02-未来扩展方向.md)）。动态创造运行不再因 DSH 沙箱屏蔽 `fetch` 而无法联网。

### 5.3 Asset 写入

`ctx.nxt.assets.create({ bytes | base64 | text, mediaType?, name? })` 把产物保存为当前频道 Asset 并返回 `assetId`，复用现有 `asset_create` 的内容寻址、大小上限和频道授权。`ctx.nxt.assets.fromUrl(url)` 经受控网络下载后保存。扩展工具把 `assetId` 返回给模型，由模型通过 `send_channel_message` 的 image、file、audio 块发送；扩展本身不直接发言。

### 5.4 扩展私有存储

`ctx.nxt.storage.get/set/delete/list`，值为 JSON。作用域：

- `agent`（默认）：本智能体的本扩展；
- `channel` / `member`：再按当前频道或成员细分；
- `shared`：同一扩展在所有智能体间共享，需要声明。

数据按 `extensionId` 保存，跨 Revision 保留；删除本地扩展时一并删除，停用不删除。每个扩展有配额（默认 8 MiB），超出时写入失败并给出可读错误。存储属于扩展数据，不进入 Core 产品事实，也不随 `.nxt-extension` 导出。

### 5.5 调用上下文

`ctx.nxt.context.current()` 返回当前智能体、频道（含 kind 和连接展示名）、触发本轮的消息引用与发送成员。成员只给出频道内稳定成员 ID 和展示名，不暴露平台原始账号。

### 5.6 上下文贡献

`ctx.nxt.prompt.static(name, text)` 注册静态说明段，只能在 `apply` 阶段注册固定字符串，宿主把它作为该 Session 的系统提示词段；`ctx.nxt.prompt.dynamic(name, render)` 注册动态上下文，`render` 每轮开始时求值，只获得只读的存储读取与调用上下文，不能联网或调用模型。结果经 DSH `systemPrompt.context()` 合并进运行时上下文快照，宿主以 `[扩展：<显示名>]` 小节标注来源，模型可见。两者都受 Manifest 声明的长度上限约束，超限截断并写诊断。具体纪律见 §8。

### 5.7 频道历史读取

`ctx.nxt.history.list({ limit, before? })` 与 `ctx.nxt.history.search(text)` 读取当前频道已入库的消息，只含当前频道、只读，复用频道上下文工具的分页与可见性规则。超过一半的社区插件直接查询聊天记录数据库，本接口替代这种访问。

## 6. 第二批能力

### 6.1 定时任务

- **声明式**：Manifest 列出 `{ id, schedule, timezone, target }`，`target` 为该智能体已绑定的频道或“所有绑定频道”。
- **运行时创建**：`ctx.nxt.jobs.schedule({ at | cron, payload, channel: 'current' })` 返回任务 ID，可列出与取消；数量受配额限制。内置提醒工具基于同一机制，不依赖任何扩展。
- **触发**：到期时宿主经 Core 在目标频道提交一条 `kind: 'control'` 的 Channel Event，`facts.extensionJob` 携带扩展、任务 ID、payload 和计划时间，没有发送成员。它与普通入站一样经 Channel Runtime 的 Admission 唤醒智能体；触发判定对该事实总是成立（`observe-only` 绑定除外），但不计入 `replyRequired`，是否发言由智能体经通信工具决定。频道时间线以系统行展示。
- **离线**：宿主恢复后，每个错过的任务只补触发一次（无论错过多少次周期），事件标注原定时间与延迟；一次性任务过期超过 7 天时不补触发，改为写诊断。
- 任务事实由宿主持久保存，扩展停用时暂停、删除时清除。

### 6.2 入站钩子

- 钩子在 Channel Event **提交之后**、Admission 之前运行；消息始终入库，不存在阻止入库。
- 返回 `{ trigger?: 'default' | 'suppress' | 'force', hideFromAgent?: boolean, annotation?: string }`。多个扩展的决定按“隐藏 > 不触发 > 强制触发 > 默认”合并，标注按扩展顺序拼接并受长度上限约束。
- 决定以 `(channel_event_id, agent_id)` 为键写入独立的 Runtime 表 `inbound_hook_decisions`，不改写不可变的 Channel Event。Admission 在钩子完成或超时后才创建；恢复与重算 `isTriggered`、`replyRequired` 时读取已保存决定，不重新执行钩子。决定尚未保存的事件在恢复时重新执行钩子。超时或抛错按“默认”处理并写诊断。
- `reads: 'all'` 表示钩子能看到频道内全部消息（包括不触发智能体的消息），权限页按隐私敏感能力说明；默认只看到原本会触发智能体的消息。
- 对智能体隐藏的消息仍出现在频道时间线中，并标注被哪个扩展隐藏。

### 6.3 受控模型调用

`ctx.nxt.llm.complete({ messages, maxOutputTokens? })` 使用该智能体当前配置的模型，计入该智能体的用量统计并标注扩展来源；受 Manifest 声明的每轮调用次数和输出上限约束。不提供选择其他供应商、读取 API Key 或流式输出。

### 6.4 平台动作

- **类型化动作**：Adapter 在 Descriptor 中声明动作目录，每个动作有参数 schema、风险等级（`low` / `admin`）和适用的频道 kind。扩展通过 `ctx.nxt.platform.invoke(action, args)` 调用，仅限当前频道。`admin` 级动作（禁言、移出成员等）需要单独授权。
- **原始透传**：Adapter 可选择支持 `ctx.nxt.platform.raw(api, params)`，只作用于当前频道所属连接，可调用的 API 范围由 Adapter 决定（可为全部）。扩展声明 `platform.raw` 后，启用时按高风险处理；单次调用不再逐次确认，但每次调用都作为互动意图留痕，可在频道诊断中审计。
- 两者都沿用现有互动意图机制：先持久化 `planned` 与 `sending`，结果不确定时记为 `unknown` 且不自动重试，按 `clientRequestId` 去重。Adapter 未声明的动作或不支持透传时返回 `unsupported`。

## 7. 权限与审批

| 等级 | 能力 | 启用时 |
|---|---|---|
| 普通 | 工具、凭据配置、`domains`/`config` 网络、Asset 写入、按智能体存储、调用上下文、读取当前频道历史、上下文贡献、声明式定时任务 | 随扩展启用一次批准 |
| 敏感 | `shared` 存储、运行时定时任务、入站钩子（`triggered`）、模型调用、`low` 平台动作 | 权限页逐项列出 |
| 高风险 | `unrestricted` 网络、入站钩子（`all`）、`admin` 平台动作、原始透传 | 必须逐项勾选接受风险 |

动态创造运行按当前创造策略执行。验证阶段的存储、定时任务、模型调用和平台动作使用替身；网络请求真实发出，因此 `verificationInput` 必须是无副作用的样例（例如查询而非提交）。给智能体启用时，敏感与高风险能力总是需要用户确认，“完全自动”策略不能跳过这一步。

## 8. 上下文缓存纪律

Nekro Agent 每次触发都重新渲染插件注入，易变文本位于提示词前部，导致模型提供方的前缀缓存频繁失效。NekroNXT 的 DSH Session 历史只追加，系统提示词未变时保持原样，运行时上下文只在变化时追加快照；扩展契约必须保持这一性质：

1. 扩展只能注册**固定字符串**的系统提示词段，变化只发生在 Revision 或配置切换时，而这本身就在安全间隙。
2. 易变状态只走运行时上下文，每轮开始求值，变化时才追加；所有扩展的动态上下文合并为一份快照，有总长度预算。
3. 消息级事实（钩子标注）附在对应消息上随历史追加。
4. 大块或按需内容通过工具让智能体主动查询，不主动推送。
5. 工具集合在一个 Session 内稳定；启停扩展在安全间隙生效，不提供按轮过滤工具的能力。
6. 保存与导入验证会用相同的存储快照和调用上下文渲染两次动态上下文，结果必须逐字节一致；编写参考明确禁止在上下文中写入时间戳、随机数和精确计数。这是运行时确定性检查，不是静态证明：`render` 只拿到只读接口，无法联网或调用模型，残余的非确定性（例如读取全局时间）由验证和预算兜底。

## 9. 相对 Nekro Agent 的设计修正

| Nekro Agent 的做法 | 问题 | NekroNXT 的做法 |
|---|---|---|
| 插件直接导入内部模块与数据库模型 | 没有稳定 API，核心重构即破坏插件 | 只能导入 SDK，能力经 `nxt` 声明式获取 |
| 插件全局启用，工具与配置全频道共享 | 工具过多撑大提示词，只能以休眠策略补救 | 按智能体启用与配置 |
| 提示词注入为每轮自由文本 | 无预算、无顺序、破坏缓存、用户不可见 | 分层上下文贡献，带预算，在轨迹中可见 |
| `PluginStore` 只存字符串、无配额、卸载不清理 | 数据无结构、无限增长 | JSON 存储，有作用域、配额和生命周期 |
| 消息回调可阻止入库 | 误拦消息无法找回 | 始终入库，最多对智能体隐藏 |
| 插件自挂 HTTP 路由 | 接口缺少统一鉴权 | 界面数据走宿主鉴权 RPC；Webhook 将使用宿主签发的独立令牌 |
| 原地热重载模块 | 残留状态、半加载 | 不可变 Revision，安全间隙切换，dispose 等待静止 |
| 市场直接克隆仓库最新代码，运行时安装依赖 | 无版本锁定和完整性校验 | 精确 Revision、内容摘要、本机重新验证 |
| 平台调用散落在插件中 | 换平台即失效、无审计 | 类型化平台动作与透传都经持久互动意图 |
| 用插件补核心缺口（防抖、过滤、回复判断、统计、帮助） | 基础体验依赖用户自行寻找插件 | 收进产品内置功能或触发策略 |

## 10. 验证要求

每项能力随实现同时交付：SDK 类型、Manifest 字段与权限摘要、正式实现、验证替身、编写参考与示例、权限页文案，以及覆盖启用、停用、Revision 切换和删除的测试。编写参考是创造智能体的工作提示，必须与 SDK 同步更新；新增能力没有示例和可运行的验证替身时不能对创造智能体开放。

移植基准：从 91 个插件中选出覆盖各能力类别的黄金集，记录移植能否通过本机导入验证、使用了哪些能力、哪些体验优于或劣于原插件；用真实模型执行零代码创造链路，记录成功率、失败原因和缓存命中情况。
