# 决策：客户端状态与数据迁移基础设施

状态：accepted

## 问题

NekroNXT 会持续升级 Core 数据库、DSH Session 依赖、客户端偏好与草稿、Extension Manifest 和本地源码 Revision。Desktop、Server 和 Web 如果各自处理版本升级，容易出现启动顺序不同、半迁移状态、旧客户端覆盖新数据和失败后无法恢复。

客户端 migration 不能被简化为 Drizzle 数据库 migration，也不能演变成一个能够随意修改所有数据的全局脚本系统。

## 决定

采用“格式所有者维护 migration，宿主协调升级”的结构。以下格式演进相互独立：

1. Core SQLite schema：由 `storage-sqlite` 拥有，通过 Drizzle migration 和 Core schema version 演进；
2. DSH Session：由锁定的 DSH persistence package 拥有，NekroNXT 调用公开 Provider/API；已授权的不兼容旧存储可整体归档并重置 Core 引用，不改写私有表；
3. Client persisted state：由 Client migration registry 拥有，处理主题、布局、未提交草稿和其他明确允许持久化的客户端状态；
4. DSH Host Profile：由 Server 拥有旧设置到稳定 Loader/Profile 入口的转换，凭据仍由凭据存储拥有；
5. Extension data：Manifest、源码 Revision 和构建缓存分别带格式版本；源码只向前迁移，缓存不迁移，运行环境指纹或 ABI 变化后重建；旧验证证据保留原环境身份。

Desktop 与 Server 使用同一个 Host upgrade coordinator。Web 客户端只迁移浏览器本地状态，不迁移 Core 或 DSH 数据。Renderer 在 Host 完成必要 migration 并发布就绪状态前不能连接业务服务。

## Client migration 契约

每个持久 namespace 使用版本信封：

```ts
interface PersistedEnvelope<T> {
  readonly format: string
  readonly version: number
  readonly data: T
}
```

- `format` 是稳定 namespace，`version` 是从 0 开始单调递增的整数；
- migration 只声明一个连续步骤 `from → from + 1`，registry 在启动时验证无重复、无缺口；
- migration 接收未知数据并负责边界校验，输出下一版本的未知数据；最终版本再由当前 schema 校验；
- 当前版本是 no-op；未来版本、未知 format 和缺失步骤必须失败，不尝试降级或猜测；
- migration 必须确定，不访问网络、时间、随机数、DOM、Core Service 或其他 namespace；
- 关键草稿迁移失败时保留原始字节并进入可导出/重置的隔离状态；主题、面板尺寸和缓存等可丢弃状态可以回到默认值，但必须记录原因；
- Local Storage 只保存小型非关键偏好；关键客户端状态的跨格式迁移需具备验证和恢复语义。Core 业务事实不复制到 Client 持久状态。

当前频道消息草稿用同一标签页的 sessionStorage 暂存文本，刷新后不恢复旧请求身份；其他表单不承诺自动恢复，刷新前明确提示保留输入。通用 registry 不等于所有现有客户端状态都已接入版本信封或事务存储。

## 宿主升级协调

进程先取得数据根独占权，并在整个运行及离线恢复期间持有。升级协调器按以下约束调用格式所有者：

```text
获取升级锁 → preflight → 创建并校验完整恢复点
→ 打开存储所有者并执行已登记迁移
→ 必需服务恢复、可选对象兼容检查
→ 开放运行 → HTTP readiness
```

通用步骤具有稳定 ID，可声明输入/输出版本和结果验证。持久 checkpoint 只有在版本与产物验证都匹配时跳过；进程内装配每次启动重做。当前生产 journal 记录存储打开、Runtime 检查恢复和开放 Admission 三个步骤，具体 Session 重置和 Profile 转换分别持有自己的幂等凭据。不能把通用接口已经支持 checkpoint 写成全部所有者已采用。

失败不删除原数据，不伪造跨 SQLite 与文件系统事务。必需服务失败进入恢复状态，可选组件可以隔离后继续启动；任何无法确认资源静止的失败都不能按隔离成功处理。诊断身份绑定对象、版本、配置修订与运行环境指纹，安装和启用意图不因诊断失败被删除。显式重试执行实际恢复，不只清除状态。

### Session 重置与关闭事务

当前明确支持将旧 SQLite schema 15/17 归档并切换到 `jsonl-v4`；未知格式拒绝。迁移身份绑定旧存储内容，Core 在一次事务中退休活动 Episode、取消未完成 Admission、中断创造任务、记录现有绑定的入站截止边界和完成凭据。聊天、配置、绑定与资源保留，旧积压不补答；下一条新消息按触发策略进入新上下文。出站投递继续使用原有去重和不确定结果规则，不重跑旧工具。

正常重启不采用上述重置规则。上游句柄 dispose 会清空 inbox，NXT 在取消但保留 inbox、等待静止后写入 `dsh/shutdown-inbox/` 关闭 journal；同一 Session 下次创建时通过公开 `inbox.append()` 按消息 ID 去重恢复，flush 后删除。这是关闭事务暂存，必须随完整备份恢复，不成为第二个长期会话事实源，也不重新激活升级已退休的 Session。

### 恢复点与程序回退

完整恢复点覆盖 Core、DSH Session/Profile/关闭 journal、凭据、附件、扩展、Spill 与工作区；缓存、未提交 staging 和既有备份按清单排除。数据库通过 SQLite backup API 快照，普通文件校验后发布，符号链接不追随。外置根必须明确登记且不得重叠。

恢复必须离线持有数据根锁，先保留失败现场，再按 manifest 和恢复 journal 执行；完成后退出并使用匹配的旧程序包。数据库 downgrade 不受支持，不自动撤销已经开放运行后的新数据。Desktop 使用同包 Server 的维护入口，Server 也使用同一实现。

当前仍存在源程序身份、外置工作区恢复续跑、Admission 与最终 HTTP 就绪之间的窗口等限制，见 [DSH 升级维护指南](../../dsh-upgrade.md#5-验收要求与实现限制)。因此本决定保持 accepted；实现入口不等于所有中断点、浏览器存储和平台产物已经完成验收。

## 测试与 fixture

- 每条 migration 使用冻结的旧版本 fixture，并断言输入 fixture 不被原地修改；
- 覆盖从每个仍受支持版本逐级迁移到当前版本；
- 覆盖当前版本 no-op、未知 format、未来版本、缺失步骤和重复步骤；
- 在每个 journal 崩溃点重启，结果只能是继续完成或保持可恢复失败，不能重复产生副作用；
- 在数据提交前失败时原始关键数据保持字节一致；已开始提交后失败须保留经过校验的恢复点与可解释的 journal，不承诺跨存储自动回滚；
- Desktop 与 Server 对同一数据 fixture 得到相同结果；
- Client migration 包保持纯函数测试，并在浏览器真实存储上增加一条组装测试。

## 备选方案

1. 只使用 Drizzle migration：无法覆盖 Client、Extension 文件和 DSH 独立存储，拒绝。
2. 一个全局 migration 目录直接修改所有数据：所有权模糊、难以独立测试和回滚，拒绝。
3. 启动时对未知数据尽力读取并静默重置：会丢失草稿或把不兼容数据解释成当前事实，拒绝；明确授权、受支持格式的 Session 重置使用上述独立路径。
4. 从第一版支持任意 downgrade：成本高且不能保证新语义无损映射，拒绝；应用回滚使用备份恢复。

## 影响

- Client migration registry 与 Host upgrade coordinator 作为共享能力，具体格式仍由实际所有者实现和验证；
- 每个持久 namespace 必须声明所有者、当前版本、失败策略和 fixture；
- Electron、Server 和 Web 不各自实现业务 migration；
- 构建缓存、请求缓存和可重建索引不进入昂贵迁移，只失效重建；
- 未来多设备同步仍可基于稳定 ID 和不可变 Revision 增加，不要求改变 migration 所有权。

## 未来方向检查

关联方向：Desktop/Server 双宿主、多设备同步、社区扩展、长期升级与恢复。

保留接缝：单调格式版本、独立 namespace、不可变 Revision、升级 journal、备份恢复和 Host 就绪门禁。

本次不做：云端数据迁移、跨设备冲突合并、任意 downgrade、Extension 社区包兼容和在线 schema 协商。
