# 本地扩展持久化

状态：implemented

## 结论

当前闭环把动态运行、保存不可变 Revision、给智能体启用、把 Adapter 安装到 Host、导入导出和删除作为独立动作。导入后处于关闭状态；删除必须先让所有运行关系静止。当前没有 Draft、社区市场或 Activation 历史状态机。

## 当前领域事实

`LocalExtension` 保存稳定 `id`、`scope: agent | host-adapter | host-ui`、`slug`、`displayName`、`description`、可选 `createdByAgentId` 和 `createdAt`。scope 属于 Extension 身份；后续 Revision 不得跨 scope，Adapter Extension 也不得改变 key。

`ExtensionRevision` 保存稳定 `id`、`extensionId`、扩展内递增 `revisionNumber`、本地 `contentDigest`、不含 Extension/Revision 身份的 `payloadDigest` 和 `createdAt`。Revision 不可变；同一 Extension 内相同 payload 复用已有 Revision。动态保存可以创建新 Extension，也可以用 `targetExtensionId` 追加下一版本。

智能体 Revision 写入 Manifest V2。Adapter Revision 使用 Manifest V3，固定 `scope: host-adapter`，包含一个 Adapter Contribution，并可附带 Host Client Slot 或页面。纯页面 Revision 使用 Manifest V4，固定 `scope: host-ui`，包含必填 Client、完整权限声明和最多 8 个 `host-page`。Builder 继续只读旧 V1；旧不可变目录不重写。

`extension_revision_verifications` 以 Revision 为主键持久保存 DSH/契约版本、Episode/Plugin/Package/Run 来源、构建结果、合成 Tool 调用、RPC 方法和实际渲染 Slot。验证输入输出限制为 16 KiB。源码发布后必须先完成构建与运行时验证，随后 Extension、Revision 和 Verification 在一个 SQLite immediate transaction 中可见；任何验证失败都不发布数据库 Revision。

`AgentActivation` 以 `(agentId, extensionId)` 为复合主键，只保存当前成功启用的 `extensionRevisionId`、配置和 `activatedAt`。它不保存 Activation ID、pending/waiting/failed/disabled 状态、默认 Revision、兼容范围、来源类型或单值 `runtimeKind`。

智能体 Client、Activation Runtime、Host Installation Runtime 和 Host Client 分别保存最近诊断。冷启动恢复失败保留数据库中的启用意图，并显示 `restore-failed`；dispose 失败显示 `dispose-failed`，不能删除运行事实或源码。诊断不是启用事实源。

## 文件与数据库提交顺序

保存 API 使用 `taskId + attemptId + displayName + slug + description` 指向持久任务的当前精确候选；旧 `agentId + episodeId + pluginId + packageId` 只保留过渡兼容。其他动态审批、Host half、Client 源码、调用、Guard 和渲染证据请求继续携带 `episodeId`，Server 校验 Agent、活动 Episode、DSH Session、Plugin 和 Package 完整归属。宿主只接受任务最后一个 `active` Attempt，且 Task 必须已经完成真实验证并进入 `ready`；当前 Runner 仍须满足 `currentPackageId`、active Run 和最新成功 Run 都指向该候选。

Define 通过 NekroNXT Authoring Facade 同时捕获 Host/Client 源码、页面 Contribution、权限和 CSS/SVG 资源，先进行结构、路径、摘要、CSS 和 SVG 预检，再把 Attempt 原子发布到智能体工作区并写 SQLite 账本。含 Client 半边的 Run 在浏览器审批后提交产品 Slot 或页面渲染证据，实际页面与权限必须等于候选风险声明，并要求 Client 真实调用每个 Host RPC；Host-only 候选同样真实调用 Tool/RPC。Web Host seam 将 `{ ok, value }` API envelope 解包为 DSH Client Runner 的直接 RPC 返回值。验证完成后，保存流程在临时目录完成规范化和最小构建验证，以原子 rename 发布完整源码目录，最后用一个数据库事务保存 Extension、Revision 与 Verification，并把 Authoring Task 标记为完成。

文件系统与 SQLite 不伪装成跨介质事务。源码发布失败时数据库不可见；数据库提交失败或进程在提交前崩溃时，已发布但无人引用的目录可以安全忽略。当前不建立 save operation journal、staging 恢复状态机或 quarantine 领域状态。

源码 Revision 是持久事实；构建 bundle 和 `build.json` 是可删除缓存，缺失或损坏时从源码重建。所有持久 JSON 和缓存清单读取都必须经过其 Zod Schema。

## 动态创造策略

每个 Episode 同时只维护一个动态 Plugin；创建后只能以 `kind:existing` 向同一 Plugin 追加不可变 Package，显式 `undefine` 后才允许创建另一个。策略按普通用户 Turn 计数：连续失败最多三次，相同 `phase + 规范化 message` 出现两次立即熔断。熔断只拒绝 define/run，仍允许 Inspect、Stop、Undefine 和频道通信；新的普通用户 Turn 重置失败预算但保留 Plugin。产品快照投影全部活动 Episode，并把 Package 历史和策略状态一起交给创造工作台。

每个 Episode 的动态 Plugin 同时对应一个持久 Authoring Task；每次不可变 Package 对应一个 Attempt。任务投影的 candidate 始终取最后一次 Attempt；最后一次 Attempt 成功运行时，它同时也是 active，不制造空 candidate。普通策略首次确认后保存 `riskDigest`，同任务后续 Attempt 的 Host/Client 半边、权限、Contribution 和资源种类不变时由 Web 自动运行，风险扩大重新确认；完全自动策略始终自动运行。审批、拒绝、技术失败和验证结果写入 Event 账本，并在原 Session 安全间隙注入结构化 Host 事件，使智能体自动继续，不依赖用户补发“继续”；相同 Task、Package、Run 和状态只注入一次。冷启动用最新 Attempt 原始源码重新 Define，重绑新的 Runner Plugin/Package ID 并恢复原运行意图；缺失源码或预检失败标记为 `interrupted`。

## Activation

启用新 Revision 时先构建，在智能体的安全间隙挂载新版本；挂载成功后才事务 upsert 当前 Activation。失败时恢复旧挂载，数据库仍指向旧 Revision。停用删除当前 `(agentId, extensionId)` 关系；同一 Extension 可由多个智能体独立启停。

Server 重启只恢复数据库中的当前 Activation。运行期注册、Fiber、Tool、Slot 和监听器都是可撤销 effect；停用与 dispose 必须等待它们静止。

每个 Activation 只执行一次 Host factory；`harness.handle` 只能在 factory 阶段注册 RPC，handler 生命周期属于 Activation。factory 返回的 Cordis Plugin 按该智能体每个 DSH Session 挂载 Tool Fiber，Session dispose 只撤销自己的 Fiber。停用或 Revision 切换才撤销全部 Fiber 与 RPC。

智能体 Client Artifact 通过精确 `extensionId + revisionId + 当前本机构建 key + agentId` 提供，每个智能体拥有独立 SlotCore；来源 Verification 的历史 build key 不充当升级后的当前 Artifact 地址。现行智能体 Catalog 包含 `agent.workbench.sections`、`extension.activation.panels`、`channel.inspector.agent.sections` 和 keyed `conversation.tool.card`；`extension.details.panels` 保留兼容映射。Adapter Client 与 Host UI 页面分别使用独立全局 Runtime。动态预览与持久 Runtime 使用同一名称、Props 和验证规则；浏览器刷新从 Host 权威 active Run 重新加载 Client，不重复启动 Host 或审批。Revision 更新 dispose 旧 Client 后 mount 新 Client；Client 失败由单扩展或单页面 Error Boundary 隔离并写最近诊断，Server Host Activation 保持。

Adapter 动态验证使用结构化 Contribution 识别，不扫描源码字符串。Fake Host 覆盖 HTTP、WebSocket、状态存储、入站、出站、凭据隔离和静止停止；含 Client 半边时，浏览器必须真实渲染 Manifest 声明的富消息、连接、频道检查器 Slot 和页面。纯 `host-ui` 动态包在创造工作台验证页面、声明式对象列、权限和停止清理。只有完整证据、源码发布和构建都成功时，Extension、Revision 与 Verification 才在同一数据库事务中可见。

## 导入、导出与删除

`.nxt-extension` 使用版本化 ZIP 和根 `manifest.json`。Extension 导出只包含一个选定 Revision 的身份、scope、展示元数据、规范化源码、payload/content digest、文件清单与来源验证证据；来源证据只用于追溯，不成为目标机器的有效 Verification。导入先限制压缩大小、解压大小、文件数和单文件大小，并拒绝绝对路径、`..`、反斜线、重复文件、符号链接、损坏中央目录和校验和不一致。

同 Extension/Revision 身份和摘要是幂等导入；同身份不同内容拒绝覆盖；同 Extension 的新 Revision 追加为下一本地版本；slug 被其他身份占用时要求新的本地 slug。导入在 staging 完成本机物化与构建后才提交，且不创建 Activation 或 Installation。

删除本地 Extension 先逐一关闭全部 Agent Activation，或卸载 Host Adapter Installation；任一 dispose 失败都会中止。运行关系静止后，源码目录先移动到受管 trash，再事务删除 Extension、Revision、Verification 与诊断，并清理 Revision 构建缓存。数据库提交失败时恢复源码和原运行关系。Connection、频道、消息和凭据引用保留。

## 磁盘边界

源码归 `extension-data/extensions/<extensionId>/revisions/<revisionId>/`，临时发布目录归 `extension-data/staging/`，构建缓存归独立 `extension-cache/`。Extension 只能通过公开 SDK 和 Service/Contribution 接缝访问宿主，不能读取 Core 数据库或依赖宿主绝对路径作为身份。

## 当前不做

当前不实现 Extension Draft、社区市场、签名、兼容范围、Activation 历史、失败队列或未来 Runtime 类型预留。分享协议只包含用户选择的单 Revision，不导出 Secret、Activation、Installation、Connection、消息、诊断和构建缓存。
