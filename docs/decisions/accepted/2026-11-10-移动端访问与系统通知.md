# 移动端访问与系统通知

状态：accepted（2026-11-10 用户确认）；尚未实施

## 问题

用户想在手机上管理自己搭建的 NXT 实例，并在需要处理时收到系统通知。现状：

- 登录已经具备：管理密钥登录、浏览器设备、登录设备列表与撤销（见[服务器网页访问与浏览器登录](../implemented/2026-10-07-服务器网页访问与浏览器登录.md)）。浏览器设备的 Cookie 固定 30 天到期，不续期。
- Web 有手机版式（760px 以下）、`site.webmanifest` 和图标，没有 Service Worker。
- 通知有四类事件和两个通道（系统通知、Bark）。系统通知只有 Desktop 会弹，浏览器用户只能用 Bark。
- Desktop 用自签名证书加证书指纹固定连接远程实例，浏览器做不到这一点。

两条外部约束决定了方案：

- Service Worker 和 Web Push 只在受信任的 HTTPS（或 `localhost`）下可用。局域网 HTTP 和自签名证书都不行。
- Android 与桌面版 Chrome 的 Web Push 经 Google 的推送服务送达，中国大陆基本收不到。iOS 经 Apple 的推送服务，可用。

## 用户已确认的取舍

1. 公网访问方式由用户自己选择和搭建，NXT 提供文档和产品内指引。
2. Android 提供 APK；iOS 和桌面浏览器使用 PWA。
3. Android 通知栏的常驻通知可以接受，界面要说明它的用途。
4. APK 用原生 Kotlin 和系统 WebView 实现，不用 Capacitor。
5. APK 的数据结构按多实例设计，第一版界面只做当前实例和简单切换。
6. Desktop 本机实例暂不开放给手机连接，APK 可用之后再评估。

## 决定

### 第一批：服务端与 Web（先于 APK）

| # | 决定 |
| --- | --- |
| M1 | **Web Push 通道**：Web 增加一个只处理推送的 Service Worker，不拦截请求、不做离线缓存，安装后立即接管（`skipWaiting` 与 `clients.claim`）。服务端在现有通知管线里增加「浏览器推送」通道，与系统通知、Bark 并列，共用事件开关。VAPID 密钥首次用到时生成，私钥按本机凭据保存。推送内容只有标题、正文、站内路由和用于合并的标签，发出前经过脱敏。推送服务返回 404 或 410 时删除该订阅 |
| M2 | **订阅属于登录设备**：订阅记录挂在登录设备（`x-nxt-viewer` 的设备）下，记录最近一次送达成功的时间。撤销设备或退出登录时删除它的订阅。「设置 → 通知」按设备列出订阅，可以测试和移除 |
| M3 | **开启推送的界面状态**：不支持、需要先添加到主屏幕（iOS 浏览器标签页）、已被拒绝、未开启、已开启，各有说明。只在用户点击时请求通知权限。当前连接不是受信任的 HTTPS 时说明原因并链接到远程访问文档 |
| M4 | **通用推送通道**：通知通道增加企业微信群机器人和 ntfy。地址与令牌按本机凭据保存，各有测试按钮。国内 Android 用户不装 APK 也能收到通知 |
| M5 | **浏览器设备续期**：用设备 Cookie 续开会话时重新下发 `nxt_device`，有效期从这一刻起再算 30 天。持续使用的设备不再需要重新输入管理密钥 |
| M6 | **通知游标**：`GET /api/client-notifications` 的响应增加本次启动的标识。客户端发现标识变化时丢弃旧游标并重新取基线。修复服务重启后客户端拿着更大的旧游标收不到通知的问题，Desktop 同样改用 |
| M7 | **通知长轮询**：`GET /api/client-notifications` 接受等待参数，没有新通知时挂起，有新通知立即返回，最长不超过 30 秒。不带参数时行为不变 |

M1 需要服务端能访问浏览器厂商的推送服务；实例所在网络访问不到时，测试按钮要给出明确的失败原因。

### Android APK

| # | 决定 |
| --- | --- |
| A1 | **形态**：原生 Kotlin 薄壳，放在 `apps/android`，用 Gradle 独立构建。界面由系统 WebView 加载实例自己的 Web，随实例更新。最低 Android 10（API 29）。壳的版本独立于 NXT，用实例描述里的协议版本判断兼容 |
| A2 | **连接**：支持三种地址。自签名证书的 HTTPS 走 Desktop 的配对协议并固定证书指纹；受信任证书的 HTTPS 直接连接；HTTP 先确认风险。原生请求和 WebView 都要校验同一个指纹，校验不通过不发送任何凭据 |
| A3 | **登录**：输入地址和管理密钥完成配对，得到设备 ID 与设备密钥。管理密钥不保存，设备密钥用 Android Keystore 加密保存。会话由原生侧建立后写入 WebView；WebView 遇到未登录时交给壳重建会话，不跳转 `/login`。Web 判断「在客户端壳里」的方式从只认 Desktop 改为同时认 Android 壳 |
| A4 | **后台通知**：前台服务保持与实例的连接，用 M7 的长轮询读取通知并发出系统通知，点击后打开对应路由。常驻通知用单独的低打扰通知类别，各类事件分设类别。首次开启时说明常驻通知的用途，并引导关闭电池优化、允许自启动 |
| A5 | **扫码配对**：已登录设备在「登录设备」页生成配对码，5 分钟内有效、只能用一次。二维码包含实例地址、证书指纹和配对码。登记设备的接口接受两种证明：管理密钥的 HMAC 证明，或配对码。配对码与登录共用限流 |
| A6 | **WebView 行为**：站外链接交给系统浏览器；文件选择接系统选择器；下载由壳自己的请求完成并校验指纹；返回键在页面内后退；状态栏颜色跟随 Web 主题 |
| A7 | **签名与发布**：正式签名密钥存放在 GitHub Actions 的受保护环境里，发布工作流每次运行需要所有者批准。密钥由所有者在本机生成并自行备份，不进仓库。开发构建使用不同的包名和单独的密钥，可以与正式版同时安装。APK 随 GitHub Release 和下载镜像分发，应用内提示更新。下载页公布签名证书的 SHA-256 指纹 |

### 公网访问指引

| # | 决定 |
| --- | --- |
| R1 | **文档**：`docs/guide` 增加远程访问一篇，按情况给出做法：Tailscale（含 `serve` 提供的受信任证书）、Cloudflare Tunnel、自有服务器反向代理、IPv6 加动态域名、组网工具。每种做法先用真实实例验证登录、事件流和 `NEKRO_TRUST_PROXY` 后再写入 |
| R2 | **产品内指引**：设置里说明当前访问方式的状态（是否加密、证书是否受信任、PWA 和推送是否可用），不可用时给出原因和文档链接；检测到经过反向代理但未开启信任代理时给出提示。扫码配对的入口也在这里可达 |

## 实施顺序

1. 第一批 M1–M7。
2. APK 验证（一到两天，结论写回本文件）：
   - WebView 在自签名证书加指纹校验下，事件流、文件上传下载、媒体资源是否都正常。不可靠时改为壳内本机代理：WebView 访问本机地址，由代理完成带指纹校验的连接。
   - 国产手机的系统 WebView 版本是否满足 Web 的最低内核要求。不满足时壳要给出明确提示。
   - 前台服务的类型声明在 Android 14、15 上的限制，以及常见国产系统的后台存活情况。
3. APK 第一期：A1–A3、A6，开发版签名。
4. APK 第二期：A4。
5. APK 第三期：A5。
6. APK 第四期：A7 的正式发布与应用内更新。
7. R1、R2 随各期推进，APK 第一期前至少完成 Tailscale 一种做法的验证与文档。

## 不在此决定内

- Desktop 本机实例开放给局域网手机。
- 原生 iOS 应用。
- 厂商推送通道（小米、华为等）和 UnifiedPush。
- PWA 的离线使用。
- 多用户、角色与权限。

## 验证

- 第一批：Server 测试覆盖订阅的登记、随设备撤销删除、失效清理、通道开关、Cookie 续期、启动标识与长轮询；浏览器测试覆盖推送设置的各状态。受信任 HTTPS 下在 iOS 主屏幕应用和桌面浏览器实测收到通知并点击跳转。
- APK：每期在真机验收，至少覆盖一台原生 Android 和两台国产系统手机；后台通知要验证锁屏一段时间后仍能送达。
