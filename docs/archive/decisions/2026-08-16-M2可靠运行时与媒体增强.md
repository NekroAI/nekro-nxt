# 已实施：M2 可靠运行时与媒体增强

> 归档日期：2026-08-19。过程日记，已冻结，不是现行规范。

状态：implemented

## 结论

一期 M2 已在 M1 的同一 Channel Runtime 状态机上补齐安全间隙、崩溃恢复、必要的 Episode 交接和原生图片投影链路。连续对话仍使用原 DSH Session 及其原生压缩；只有长期空闲、明确不兼容的 Revision、人工新会话或不可恢复边界才创建新 Session。

## 已落实边界

- 每个 `(channelId, agentId)` 使用独立串行 lane；事件可以并发入库，但 Episode、Admission 和 rollover 提交不会并发竞争；
- DSH 空闲时通过 `followup()` 准入，运行中的普通消息通过 `inject()` 排入下一安全 Step，不取消正在执行的模型请求或 Tool；
- pending/claimed Admission 可恢复。DSH 已提交而 Core 尚未完成时，Runtime 按 `admissionId` 从 Session 日志补偿，不重复准入；
- planned Outbox 可继续执行；已经进入 sending 且没有确定回执的 PhysicalDelivery 恢复为 `unknown`，不会盲目重发；
- 显式停止、权限撤销和宿主释放使用 DSH 取消边界，关闭后的 Episode 不能继续发送；
- 默认空闲阈值为 6 小时，可按 Binding 配置或关闭；阈值只在下一条消息到达时判断，不建立后台定时关闭任务；
- 仅展示名等兼容 Revision 在原 Session 的安全间隙切换；人设、模型和能力契约等不兼容变化触发 handoff rollover；人工新会话也使用同一交接状态机；
- handoff 使用当前对话模型和确定性摘要模板，记录来源 Episode、Channel Event、Provider 与 Model；旧 Episode 关闭、新 Episode 创建、摘要保存和活动指针切换在一个 Core SQLite 事务中提交；
- 新 DSH Session 通过 `nekro-nxt-handoff` 来源注入交接摘要，旧 Channel Event 与 Session 日志保持只读可查；单纯上下文压力继续使用 DSH 原 Session compaction，不触发 rollover；
- 入站 blob 先原子发布，再在同一个数据库事务提交 Channel Event 与准确 `(channelEventId, partIndex)` AssetOccurrence；Admission 只在该事务完成后启动；
- 当前不实现图片增强队列、OCR、标签或派生内容表；`asset_inspect` 只返回当前 Channel 来源授权的资源元数据，图片能力明确可用时才注册 `asset_view_image`；两个工具都只接受稳定 `assetId`；
- 自定义 Asset-backed DSH Attachment Store 直接引用同一规范 blob，不复制第二份图片。图片模型获得 DSH `ImageBlock`，文本模型获得可用的增强文本或明确的未处理/失败状态；
- `video/*` 仍作为普通 file 完整入库，不增加虚假的视频理解能力。

## 后续修订：Handoff 最近窗口与失败降级（2026-08-18）

Episode handoff 不覆盖 DSH 原生 Compaction 的默认配置。NekroNxt 自有 handoff 摘要请求不设置 `maxTokens`，只在提示层建议压缩程度，并使用 180 秒取消边界；摘要失败时使用结构化 fallback，继续完成 Session 切换和消息准入。新 Session 同时接收 `summary` 与独立持久化的最近 Channel Event 原文窗口，较早内容通过当前频道的历史搜索/读取工具回查。详见《Handoff 失败降级与最近窗口恢复》实施记录。

## 恢复与原子性

Core SQLite 与 DSH Session SQLite 仍是两个独立事实所有者，不伪造跨库事务。恢复顺序先恢复 DSH Session，再按稳定来源 ID 核对 Admission，最后恢复 Outbox；所有可重放动作都有业务幂等键。

Episode rollover 生成摘要和新 Session 期间，旧 Episode 始终保持 `active`，不持久化中间状态。只有单库事务一次提交旧 Episode 关闭、新 Episode、Handoff 与来源事件后，新 Episode 才对后续消息可见；提交前崩溃仍恢复旧 Episode。

## 验证证据

- 20 条运行中消息并发进入同一 lane 时最大 Admission 并发为 1，全部使用运行中注入且无取消；
- 冷启动可以恢复真实 DSH SQLite Session，已写入 DSH 的 claimed Admission 不重复追加；
- 模拟发送提交后崩溃时，PhysicalDelivery 变为 `unknown` 且 Adapter 调用次数不增加；
- 不兼容 Revision 会关闭旧 Episode、生成一条 handoff、创建不同的 DSH Session，并在新日志中出现 `nekro-nxt-handoff`；
- 空闲阈值、人工新会话、显式停止和权限撤销均有确定性测试；
- 相同图片并发导入只保留一个规范 blob，各消息仍保留独立且精确的授权 Occurrence；
- 图片模型的首轮输入包含原生 image block，并且只在该模型上暴露 `asset_view_image`；
- `pnpm check`、`pnpm test` 与 `pnpm build` 通过；M2 收口时共有 12 个测试文件、50 个无密钥测试。

## M3-M4 接缝与明确未做

M2 保留智能体独立 Scope、安全切换点、不可变 Revision、来源授权和可恢复状态机，供动态 Package、本地 Extension Revision 与 AgentActivation 复用。它没有提前实现创造权限、开发 Shell、完整文件访问、扩展源码保存、构建缓存或 Activation；这些属于 M3-M4，不能塞入 Channel Runtime 或 Asset Service。

## 未来方向与参考取舍

关联方向：更多 Adapter、长期历史、多媒体、长期 Job、多设备恢复和智能体自开发。

保留接缝：稳定 Episode lineage、Admission 来源、可扩展 close reason、Adapter 回执、受权 `assetId` 和可替换 Attachment Store。当前没有为图片增强器或更多媒体处理器预建表、队列和版本字段。

本次明确不提前实现：向量记忆、专用视频理解/转码、任意文件直接进入模型、`unknown` 自动重发、分布式队列和跨数据库事务。

参考 DSH 的 `followup()`、`inject()`、Session 持久化、Agent Loop、Attachment Store 和原 Session compaction；拒绝 Fork、读取私有 Session 表和复制媒体。参考历史群聊系统的并发、重放和媒体积累风险；拒绝文本 Mention、宿主路径媒体和平台逻辑进入 Core。
