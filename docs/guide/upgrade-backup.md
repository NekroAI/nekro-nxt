# 升级、备份与恢复

NekroNXT 通过完整程序包升级。升级前停止旧实例，保留旧程序包及独立备份；新实例在打开业务存储前创建自动恢复点。不要在运行容器中执行 `git pull`，也不要让两个版本同时使用一个数据根。

## 升级后会发生什么

本次 DSH 升级将已识别的旧 SQLite Session 自动归档，并创建 JSONL 会话。聊天记录、附件、智能体配置及版本、连接、绑定、凭据、扩展源码和安装/启用记录保留。

旧模型上下文、未完成运行和未完成创造任务不会自动继续；升级前积压消息不会补答。下一条符合触发策略的新消息开始新的上下文。已经提交的消息投递仍按原有去重与回执规则恢复，不重跑旧模型工具。

不兼容的模型配置或扩展会暂停并显示原因。到现有设置、智能体或扩展页面修复配置、重新构建或点击“重新检查兼容性”；重试会实际执行检查，失败时保留原配置和原因，不会自动换模型。

这不代表每次升级都清空上下文。同一 Session 兼容格式可继续使用，只有实现中明确支持的格式转换或重置才会执行；未知格式会停止启动并保留数据。

## 自动恢复点包含什么

恢复点位于当前数据根的 `backups/runtime-<摘要>/`，包括 `manifest.json` 与按根目录组织的文件。摘要绑定目标 Release 与运行环境指纹；同一目标启动时只复用通过校验的恢复点，不持续覆盖它。

| 内容 | 处理方式 |
| --- | --- |
| Core SQLite、存在时的旧 Session SQLite | 使用 SQLite backup API 生成一致性快照，并检查数据库完整性 |
| JSONL Session、DSH Profile、凭据、插件安装项目 | 复制持久文件，记录大小、校验和与权限 |
| 附件、扩展源码、Spill、智能体工作区、TLS 文件 | 纳入恢复点；外置工作区只覆盖明确配置且属于现有智能体的子目录 |
| `dsh/shutdown-inbox/` | 纳入恢复点；它是正常关闭期间的待处理消息 journal，不是缓存 |
| `extension-cache/`、`dsh/request-images/`、`dsh/plugin-staging/`、既有 `backups/` | 排除；前两项可重建，staging 尚未提交，旧备份独立保留 |
| SQLite WAL/SHM、Unix socket | 不作为普通文件复制；SQLite 已由 backup API 形成快照 |
| 符号链接 | 保留链接本身，不跟随到未声明的外部目录 |

恢复点先在私有暂存目录生成，校验后再发布。空间不足、文件在备份期间被外部修改、数据库或文件校验失败时，停止升级，不用不完整备份覆盖原数据。不要只复制主数据库而遗漏凭据、资源、工作区和会话。

恢复点含凭据与聊天等私有内容，应按原数据根保护，不上传到 Issue 或公开仓库。清单保存目标 Release，但没有完整的旧程序身份；请另行记录升级前版本并保留对应完整包。自动恢复点不能替代独立存放的定期备份。

## 桌面版

- 同一通道安装新的完整包；stable 与 preview 可以并装，分别使用既有 `NekroNxt` 和 `NekroNxt Preview` 数据目录，默认不共享数据。
- 手动备份前完全退出应用，再复制当前通道的 `userData/data/`；有外置工作区时一并保护。卸载默认保留数据。
- 启动窗口显示当前阶段和备份信息。升级有有效心跳时不会被普通 60 秒启动期限打断；长时间无实际进展会提示停滞，可以查看诊断或安全取消。
- 启动失败后可以重试；只有本次可信进度带有有效恢复点时才显示“恢复升级前备份”。恢复前会等待本地服务退出。
- 恢复成功后退出新版本，改用匹配的旧程序包；应用不会立即重启新版本再次迁移。

Desktop 只在本地 Host 的 `/health/ready` 返回同包 Release 后开放产品页面。进度文件显示 `ready` 不等于 HTTP 已就绪；远程实例使用它自己的 Web 与 Host，不要求与本地实例 Release 相同。

## 服务端

1. 停止旧容器，保留旧镜像身份，并备份完整命名卷或绑定目录；外置工作区也要备份。
2. 使用新镜像创建替代容器，挂载同一主要数据根。不要并行启动旧、新容器。
3. 等待 `/health/ready`，核对 Release ID，再检查认证快照、隔离原因与实际消息旅程。长备份期间暂时没有业务健康端点，不要仅凭短健康超时反复强杀进程。
4. 必需服务失败时业务入口不开放；先查看启动诊断与恢复点，修复问题后可以重试。不要直接删除活跃进程或另一台宿主拥有的锁文件。

需要回退时，停止服务并保留失败现场，使用带恢复能力的新包离线运行 Server 入口，传入 `--restore-upgrade <backupId>`。容器内入口为 `/opt/nekro/server/dist/main.mjs`；维护容器须挂载相同数据根、相同外置工作区并保留对应配置，只运行恢复命令，不同时启动正常服务。

恢复先校验备份及根目录身份，检查空间并在独立暂存树准备完整待恢复文件；验证完成后才将当前数据移入 `backups/before-restore-<backupId>/`；外置工作区的失败现场保留在原根旁边。随后按 manifest 发布文件并校验完整恢复结果，以 `restore-<backupId>.json` 记录阶段。成功后维护进程退出，使用旧程序包启动；已完成的同一恢复不会再次覆盖当前数据。数据库 downgrade 不受支持，不能只回退程序而继续使用新格式数据。

当前外置工作区恢复范围仍从 Core 的智能体记录推导。Core 损坏、已在中断恢复中被移走，或智能体目录发生变化时，恢复可能因根目录身份不匹配停止；请保留备份与失败现场，核对 manifest 后再处理，不能假定重复命令总能续跑。恢复不是自动故障回滚，尤其在新版本已经处理过消息之后，必须评估恢复点之后的数据变化。

## 正常重启与版本重置的区别

当前上游 `AgentHandle.dispose()` 会清空待处理 inbox。NXT 正常关闭先取消执行但保留 inbox、等待静止，把待处理消息暂存到 `dsh/shutdown-inbox/<Session摘要>.json`，再释放句柄。下次创建同一个智能体会话时，通过公开 `inbox.append()` 按消息 ID 去重恢复，flush 成功后删除 journal。

这是关闭事务的短期暂存，不是第二套长期会话库。它必须随完整备份恢复，但不会让已经因不兼容升级而退休的旧 Session 重新运行，也不改变“旧上下文重置、积压不补答”的规则。

升级机制与贡献者验收要求见 [DSH 升级维护指南](../dsh-upgrade.md)。恢复功能已经有对应实现和合成测试入口；是否可交付仍需对候选容器、Desktop 各平台产物和真实界面完成验收，本文不代表这些验收已经通过。
