# NekroNXT 术语与文案规范

## 1. 品牌

| 场景 | 唯一写法 |
|---|---|
| 产品名 | NekroNXT |
| 根包名/仓库名 | `nekro-nxt` |
| 所属品牌 | NekroAI |
| 不再使用 | Nekro Harness、Nekro 新平台、Nekro Agent 2 |

## 2. 用户实体称呼

产品面对用户时只使用“智能体”。同一个对象不得根据页面随意改称 Agent、AI 成员、机器人、Bot 或助手。

正确示例：

- 创建智能体；
- 管理智能体；
- 小奈正在使用工具；
- 将此频道交给小奈响应；
- 为小奈启用“网页摘要”扩展；
- 2 个智能体正在使用此扩展。

错误示例：

- 创建 Agent；
- 管理 AI 成员；
- 当前 Bot 在线；
- Agent 配置；
- 给助手安装插件。

“助手”可以出现在具体名称中，例如“开发助手”，但不能作为实体类型。

## 3. 用户术语与内部类型映射

| 用户界面 | 内部 TypeScript 类型建议 | 说明 |
|---|---|---|
| 智能体 | `AgentDefinition` | 长期存在的身份和配置实体 |
| 智能体配置版本 / 配置版本 | `AgentRevision` | 不可变配置快照 |
| 会话 | `AgentSession` | 某配置版本在频道上下文中的运行实例 |
| 频道 | `Channel` | 单一消息事实流 |
| 频道绑定 | `ChannelBinding` | 指定谁响应及触发规则 |
| 平台连接 | `Connection` | 已登录的平台账号连接 |
| 平台用户 | `PlatformIdentity` | 某个平台连接内观测到的稳定用户身份；不同连接不合并 |
| 扩展 | `Extension` | 统一能力包 |
| 扩展版本 | `ExtensionRevision` | 不可变扩展版本 |
| 为智能体启用 / 智能体启用关系 | `AgentActivation` | 智能体对指定扩展版本的引用 |
| 动态包 | `DynamicPackage` | 创造会话中的临时可运行产物 |
| 工具 | `ToolContribution` | 扩展提供的一种贡献 |
| 适配器 | `AdapterContribution` | 扩展提供的消息平台贡献 |

内部类型使用 Agent 是为了与 DSH、生态 API 和英文代码保持一致，不构成产品文案例外。

NekroNXT 不加载 DSH 的 `dsh.client`、原生 WebUI、侧栏、Composer 和页面 Slot，也不设置允许上游术语泄漏的“兼容岛”。DSH 包只有显式声明 `nekroNxt.hostUi` 才能贡献 NXT 页面，用户可见文案遵守本规范。加载边界见[扩展应用页面与 Host UI 运行时](decisions/implemented/2026-08-28-扩展应用页面与HostUI运行时.md)。

## 4. 其他文案约束

- `Revision` 在普通界面写“版本”或“配置版本”，高级详情可附 `r12`；
- `Activation` 使用动作“为小奈启用”，管理页可写“智能体启用关系”；
- `Binding` 写“频道绑定”；
- `Connection` 写“平台连接”或具体账号；
- 一级“用户”页中的“用户”只指平台消息中已观测并持久化的身份，不表示 NekroNXT 后台登录账号；不得把昵称或裸平台 ID 当作跨连接人员身份；
- 由 NekroNXT 自带、独立于外部平台账号的频道统一写“内置频道”。不得写“网页频道”“网页聊天”“本地 Web”或“本地频道”；领域 kind 使用 `internal`，具体 Adapter key 只属于 Adapter 包，不进入用户界面或主应用分支；
- `Extension` 写“扩展”，不混用插件、Skill、能力包；用户动作统一写“保存为本地扩展”；
- `Agent Loop` 只出现在开发文档，产品界面写“思考与工具执行过程”；
- 检测到 DSH Client UI 时标记“原生界面未接入”，不暗示上游页面可用；显式 `nekroNxt.hostUi` 贡献的页面称“扩展应用”，不新增智能体实体称呼；
- 状态要说明对象：智能体空闲、平台已连接、频道监听中、工具执行中；不得用一个“在线”混合所有状态；
- 不得在产品壳写死 QQ、Discord 等平台名。选择平台时展示 Adapter 贡献的名称；频道来源、检查器和 Composer 使用该连接的展示名；无名群聊/私聊只写“群聊”“私聊”，可附尾号。开发文档可以写明某个 Adapter 的实现，那不是产品文案。
- Composer 常态只保留一个发送模式短标签、输入框和真实动作。不得同时重复“发给谁”“写在哪里”“对方会看到什么”等同义说明；必须常驻的阻塞原因压缩成一句，补充后果放入可聚焦的信息 Tooltip。
- Tooltip 只补充图标含义、快捷键或已经有短标签概括的发送后果，不能隐藏完成任务所必需的字段、错误或前置条件。
- 管理员从客户端向外部频道发言统一标记为“管理员从客户端发出”；不得写成智能体自己的发言，也不得泄漏内部 `admin-console` 值。

### 4.1 界面文案只说明对象、范围和结果

标题下说明、区块说明、空态和操作提示只保留用户完成当前任务所需的信息：正在操作什么、作用于谁、提交后发生什么，以及真正阻塞操作的前置条件。

以下是按语义使用的审稿建议，不是禁词表。审稿时判断信息是否真实、必要、清楚；“不会”“继续”“仍”“之后”“才能”、破折号和导航口语本身都不构成错误，不需要逐条登记例外。

- 导航说明应帮助用户找到操作入口。避免把“少进入一个页面”当作产品价值；“到「连接」添加账号”和“前往「连接」添加账号”都可按上下文使用。
- 否定句应解释用户关心的真实后果。避免臆测用户担忧后自行辩护；涉及保存与启用、删除与保留的边界时，可以明确写“保存后不会自动启用”或说明实际保留的对象。
- 时序应有可理解的事件锚点。“保存之后启用”可以使用；孤立的“之后再操作”应补明等待什么事件。
- 状态延续应有上下文或对比对象。“连接中断后，已保存配置仍然可用”说明了恢复结果；没有信息增量的“仍保持可用，请继续操作”可简化。
- 前置条件应告诉用户如何完成任务。“连接成功后才能发送”可以说明真实限制；字段缺失时，“请输入名称”通常更直接。
- 动作名称应具体。“重开”若无法区分重新打开页面和开始新上下文，应改成对应动作；涉及上下文时使用“压缩上下文”“清空上下文”或“开始新上下文”。
- 破折号按句意和可读性使用。缺失数据优先写“暂无”“未统计”或“不适用”，让用户理解缺失原因；符号占位需结合字段和可访问性判断。

审稿时先看对象、动作、作用范围和真实结果是否清楚，再删去重复解释；不要为了避开某个词而改成更生硬或隐去操作后果的表达。

### 4.2 自动检查与精确例外

`scripts/check-terminology.mjs` 通过 `pnpm check:docs` 和根 `pnpm check` 执行硬门禁：检查产品壳用户可见文本中的明确内部术语、硬编码平台名，以及用技术 ID 作为展示名称回退的表达式。扫描包括直接 JSX 文本、用户可见属性及其引用的文案变量、展示集合和展示映射。一般写作风格由 §4.1 指导人工审稿，不产生逐词错误或警告，也不要求例外配置。

Adapter Contribution 源码允许声明平台展示名，不套用产品壳术语禁词；其展示表达式仍检查技术 ID 回退。扫描动态发现 `packages/adapter-*/src`，排除 SDK 和仅负责组合的 `adapter-builtin-roster`。产品壳消费 Adapter 展示名，不硬编码具体平台名称。

硬门禁误识别非展示内容，或某个具体位置确需保留术语时，在 `scripts/baselines/user-visible-copy-exceptions.json` 集中登记精确例外。例如：

```json
{
  "file": "apps/web/src/example.tsx",
  "rule": "term:Adapter",
  "text": "/users?adapter=",
  "reason": "内部 URL 查询参数用于持久化平台筛选，不作为用户可见文案。"
}
```

例外按规范化后的完整文案精确匹配 `file + rule + text`，不得使用文件级跳过、宽泛正则或源码内忽略注释。`reason` 必须可审查；文案删除、改写或不再命中规则后，陈旧例外会使检查失败，必须同时清理。未知规则和重复例外同样使检查失败。

## 5. 创造状态

- “创造”是同一智能体启用动态创造相关能力后的运行状态，不是另一种用户实体；
- 不创建或展示“创造助手”“创造智能体”等类型名；
- 工作台应直接显示原智能体，例如“小奈 · 已启用创造能力”“与小奈协作创造”；
- 面向用户把系统访问组织为四段快捷预设：“基础权限（Lv.0）→ 文件读写（Lv.1）→ 运行命令（Lv.2）→ 完整访问（Lv.3）”。预设逐级包含左侧能力；展开后仍可逐项控制，组合不匹配预设时显示“自定义权限（Lv.C）”。列表中的轻量 Chip 只显示等级码，完整名称与说明放在悬浮提示中。内部字段继续使用 `fileTools`、`developmentShell`、`unrestrictedFileAccess`，不得把这些实现名泄漏到界面；
- 动态创造是授权能力中的扩展能力子区；子智能体与网页搜索位于“更多能力”，两项互不依赖。不能用“进入创造模式”暗示同时获得系统访问；
- 内部实现可以使用 DSH Preset 组合相关 Tool，但 Preset 名称不得改变用户可见的智能体身份。

## 6. 文案审查范围

审查本次改动实际显示的文字，包括错误、空态和操作后果。自动检查按 §4.2 执行；需要补查动态文案时，在相关来源中搜索旧称或内部标识，并结合上下文判断。无需每次界面修改都重复全仓禁词搜索，也不能把脚本通过视为所有动态文案都已验证。

技术诊断区域允许显示定位问题必需的协议名称与错误标识，例如 `Session`、`Revision`、RPC 方法和错误码。使用 `code`、`pre` 或明确的 `data-technical-diagnostic` 区域表达诊断语境；普通产品导航、对象名称与操作文案继续使用约定术语。
