# 实例登录与访问入口

状态：accepted（2026-11-10 用户确认）；L1–L7 已实施，真机验收进行中

## 问题

用户想用 `nxt.example.com` 这样的地址在手机上直接打开自己的实例，日常开发用的实例也要能这样访问。现状：

- 浏览器只能用管理密钥登录（见[服务器网页访问与浏览器登录](../implemented/2026-10-07-服务器网页访问与浏览器登录.md)）。密钥长、难记，在手机上输入尤其麻烦。登录后设备 Cookie 会续期，麻烦集中在每台新设备第一次登录。
- 登录层只在设置了 `NEKRO_MANAGEMENT_KEY` 时存在。开发实例 `pnpm dev` 不设密钥，没有登录层。
- 没有登录层时，本机来的请求都按本机控制台对待。反向代理和实例在同一台机器上时，公网请求经代理转发后同样被当成本机请求，等于完全开放。
- 开发模式下浏览器访问的是 Vite，只有 `/api` 经过服务端。代理直接指向 Vite 时，页面源码和 Vite 的文件接口都不经过登录。
- 登录限流按连接的来源地址计数。经过代理后所有人都算成 `127.0.0.1`，攻击者反复输错会把管理员也挡在外面。

## 用户已确认的取舍

1. 管理密钥保留，用于首次初始化、丢失其他登录方式时找回，以及 Desktop 配对。日常登录不依赖它。
2. 不提供用户名和密码。
3. 通行密钥对 iPhone、Mac 用户方便；Android 和 Windows 用户多半用扫码或管理密钥，三种方式同样完整。
4. 实例只配一个公网访问地址，本机地址始终可用。
5. 开发实例本身就是对外访问的实例，不另外部署正式实例来迭代。
6. 多用户、角色与权限仍不在范围内。

## 决定

| # | 决定 |
| --- | --- |
| L1 | **开发实例启用登录层**：开发模式下也可以设置管理密钥，启用后登录层是唯一入口。页面请求（包括热更新的 WebSocket）由登录层转给 Vite，反向代理指向登录层的端口。Vite 代理不再改写 Host，来源校验按浏览器实际访问的地址进行。本机开发同样需要登录一次，之后靠设备 Cookie 保持 |
| L2 | **没有登录层时拒绝代理请求**：没有设置管理密钥却设置了信任代理时拒绝启动；没有登录层时，带 `X-Forwarded-*` 头的请求返回说明，不再按本机控制台放行 |
| L3 | **登录限流按真实客户端**：开启信任代理时，按代理给出的客户端地址计数；没有开启时仍按连接地址 |
| L4 | **访问地址**：「设置 → 登录与访问」可以填写一个公网访问地址，例如 `https://nxt.example.com`。通行密钥绑定的域名、扫码登录的链接、通知里的跳转链接、来源校验和访问状态检查都用它。本机地址始终允许。信任代理仍由启动参数决定，不放进界面 |
| L5 | **通行密钥**：已登录的设备可以添加通行密钥，可以添加多个，各有名称，可以单独删除。登录页有通行密钥时把它放在首页，作为扫码之外的第二个按钮。通行密钥按域名生效：访问地址的通行密钥和本机地址的通行密钥互不通用，修改访问地址后，原地址的通行密钥在新地址上不能用，界面在修改前说明这一点 |
| L6 | **扫码登录**：两个方向，最后都在已登录的设备上确认。<br>· 新设备扫码：已登录的设备显示二维码，新设备用系统相机扫描，打开的链接即登录页；已登录设备确认后，新设备完成登录。<br>· 已登录手机扫码：新设备的登录页显示二维码，已登录的手机扫描后确认。<br>二维码里是一次性登录码，5 分钟内有效，只能用一次，与登录共用限流。没有相机时可以手动输入短码。<br>· 登录页按设备给出首选方向：手机首页是「扫码登录」，用页面内相机扫已登录设备上的二维码；电脑和平板首页显示本机的二维码和登录码。另一个方向、输入登录码和管理密钥都在首页底部的入口里。手机上页面不能使用相机（非 HTTPS、没有权限或没有相机）时，首页改为显示本机登录码并说明原因 |
| L7 | **网页登录只用通行密钥和扫码**：设置里可以关闭「用管理密钥在网页登录」，默认不关。关闭后管理密钥仍可用于找回：登录页的找回入口要求管理密钥，并在登录后提示添加通行密钥或扫码设备。Desktop 配对不受影响 |

L6 中「已登录手机扫码」在不同客户端的做法：

- Android 浏览器与 Android PWA 共用浏览器的登录状态，用系统相机扫码打开链接即可。
- iPhone 主屏幕应用与 Safari 的登录状态分开。系统相机会在 Safari 中打开链接，Safari 没有登录时无法确认，所以「设置 → 登录设备」提供应用内扫码：通过页面调用相机，解码使用成熟的二维码库（部分浏览器没有内置的条码识别）。应用内扫码需要 HTTPS。
- APK 用原生相机扫码，不依赖 Google Play 服务。

## 实施补充

- 通行密钥使用 `@simplewebauthn/server` 与 `@simplewebauthn/browser`，可被发现凭据（不需要用户名），每个通行密钥记录添加时的域名，登录时只接受当前域名的通行密钥。
- 二维码由服务端生成 SVG（`qrcode`），应用内扫码用 `jsqr` 识别相机画面。登录页的扫码同样用 `jsqr`，由登录层在 `/login/qr-decode.js` 提供它的浏览器构建，登录页的 CSP 只为此在 `script-src` 加上 `'self'`。
- `@simplewebauthn/server` 带来的 `@peculiar/asn1-*` 与生成实例证书用的 `selfsigned` 共用，版本统一锁定在 `pnpm-workspace.yaml`，否则两份 ASN.1 注册表会让证书无法生成。
- 登录码的状态保存在登录层内存中，服务重启后失效，需要重新生成。
- `NEKRO_TRUST_PROXY` 可以写反向代理的地址或网段，只采用这些地址发来的转发头；写 `1` 仍表示信任所有连接。实例端口对代理以外的机器开放时应写地址。
- 通行密钥的添加和登录都要求验证本人（指纹、面容或 PIN）。没有设置 PIN 的硬件安全密钥不能使用。
- 登录页显示登录码有单独的限流（每个地址每分钟 20 次），不占用管理密钥和通行密钥登录的次数。未登录浏览器申请的登录码和已登录设备生成的邀请各有 100 个名额。
- 修改类请求的来源校验接受请求自身的地址，也接受设置里的访问地址。

## 实施顺序

1. L1–L4：开发实例启用登录层、两处安全兜底、访问地址。完成后可以先用管理密钥通过 `nxt.example.com` 访问。
2. L5：通行密钥。
3. L6：扫码登录，与[移动端访问与系统通知](2026-11-10-移动端访问与系统通知.md)的 A5 共用一次性登录码。
4. L7：关闭管理密钥网页登录的开关。

## 不在此决定内

- 用户名和密码登录。
- 多用户、角色与权限。
- 多个访问地址并存。
- 第三方身份登录（OAuth、社区账号登录实例）。

## 验证

- Server 测试覆盖：开发模式经登录层访问页面与热更新、没有登录层时拒绝代理请求、按真实客户端限流、访问地址校验、通行密钥的注册与登录与删除、一次性登录码的有效期与单次使用、关闭管理密钥登录后的找回。
- 浏览器测试覆盖登录页各种方式的状态和登录设备页的管理操作。
- 真机：iPhone 主屏幕应用、Android 浏览器、Windows 浏览器各完成一次扫码登录；iPhone 和 Mac 各完成一次通行密钥登录。
